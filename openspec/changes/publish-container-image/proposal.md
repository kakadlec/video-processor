## Why

Two facts about this repository's delivery, both true today and neither visible from the outside.

**The image is never built by any gate.** `.github/workflows/ci.yml` runs `go vet`, `go test`, `gosec` and `govulncheck` on the runner, with `ffmpeg` installed by `apt`. The only `docker` invocations in it start MinIO and create the test databases. Nothing builds the `Dockerfile`. A break in it — a `runtime` stage missing a dependency a new code path needs, a `COPY` that stops matching, a base tag that goes away — merges to `main` with three green checks and surfaces the next time a human runs `docker compose up --build`. The repository pins its architectural invariants with tests rather than convention; the artifact it ships as is the one thing no check compiles.

**The image is never published.** `release-please` computes the version, tags it, and writes `CHANGELOG.md`; nothing carries the build any further. The image exists only as a recipe, so every consumer builds it, and "works on my machine" is the only evidence that it builds at all. `docs/operations.md` opens its deployment section with `docker build -t video-processor .` — a locally-built, unversioned, unreproducible artifact is the current deployment unit.

The second reason is the honest one to state: the assignment brief asks for **CI/CD of the application**, and this repository has CI and no D. There is deliberately no deployment target — this change does not invent one, and no deployment is in scope. What it delivers is the half that is real without a target: a versioned, immutable, pullable artifact that anyone can run without a Go toolchain, built by the same pipeline that gates the code.

## What Changes

- **A new required check builds the image on every pull request.** It builds the `runtime` target for both published platforms and pushes nothing. Its purpose is the gate, not the artifact: a `Dockerfile` that does not build stops being mergeable.
- **The image is published to GHCR on release.** `ghcr.io/kakadlec/video-processor`, tagged with the release version and `latest`, triggered by `release-please` actually creating a release rather than by a merge. Authentication is the workflow's own `GITHUB_TOKEN` with `packages: write` — no registry account, no new secret.
- **A manual publish path for a tag that already exists.** A `workflow_dispatch` input naming a git tag publishes that tag's tree. Without it this change ships an inert workflow: `v4.0.0` is already released, and this change's own commits (`ci:`/`build:`) produce no version bump, so nothing would be pullable until some unrelated `feat:`/`fix:` lands. Documentation that names a pull command no registry answers is the same defect class this change exists to close.
- **The image becomes multi-platform: `linux/amd64` and `linux/arm64`.** The builder cross-compiles rather than emulating — `CGO_ENABLED=0` already makes every binary cross-compilable, so pinning the builder stage to the *build* platform and passing the *target* architecture to `go build` costs nothing at compile time.
- **`docs/operations.md` and `README.md` gain the pull path** as the documented way to obtain the image, alongside the local build, which stays: a contributor building from a working tree is not doing the same thing as an operator running a release.
- **`docker-compose.yml` is unchanged.** It keeps building from the working tree, and `app-test` keeps requiring `--build`. Pointing local development at a published tag would run the developer's tests against an image that is not their code — the exact failure `--build` is documented to prevent.
- **Explicitly not in scope**: any deployment, any target environment, image signing (cosign), SBOM or provenance attestations, and image vulnerability scanning (Trivy/Grype). Each is a separate decision with its own failure modes; none is required by the brief, and bundling them would make the one verifiable claim here — *the image builds and is pullable* — harder to check.

## Capabilities

### New Capabilities
- `container-image-publication`: what the published artifact is and what may be assumed about it — the registry and repository name, the tag set and what each tag means, that a version tag is immutable once published, that publication is triggered by a release rather than by a merge, that a tag that already exists can be published deliberately, and that publication carries no deployment.

### Modified Capabilities
- `container-image`: gains a requirement that the image is buildable for more than one platform and that every binary in it matches the platform it was built for. `ADDED` rather than a modification of "Multi-Stage Image Build": that requirement's present wording makes no claim about architecture at all — it says which stages exist, which entrypoints are compiled, and how dependencies resolve — so nothing in it contradicts a second platform, and rewriting it would restate settled text to insert one clause. The new requirement also carries the constraint the existing spec would otherwise silently lose: the test stage must keep building **natively**, because `docker compose run --build --rm app-test go test ./... -v` is the documented local test path and an emulated Go toolchain would make it unusably slow.
- `development-workflow`: gains a "Container Image Build Gate" requirement, beside the existing "SAST Gate" and "Vulnerability Scan Gate", which it deliberately mirrors in shape. `ADDED` for the same reason: "Automated Test Gate" describes what `go vet`/`go test` cover and would become false if edited to claim an image build it does not perform. This is one coherent delta with the two above rather than a separate change — the gate exists because the artifact is published, and publishing an image no check ever built is the arrangement this change refuses.

## Impact

- **New file**: a publish workflow under `.github/workflows/`. Whether it is a job appended to `release-please.yml` or a workflow of its own is a `design.md` decision, not a proposal one.
- **Changed**: `.github/workflows/ci.yml` (one job), `Dockerfile` (the builder stage's `FROM` and the `go build` invocations — no new stage, no new package, no change to `runtime`).
- **No Go code, no test code, no new dependency.** The diff carries no Go module input, so `development-workflow`'s exemption from the local test-run requirement applies. Verification is behavioural and stated in `tasks.md`: the image builds for both platforms, the five binaries in each are the right architecture, the `test` target still runs the suite, and the published tag is pullable and runnable.
- **Accepted cost, named rather than discovered**: the `runtime` stage's `apk add ffmpeg` runs under emulation for the non-native platform, on every pull request and every publish. It is one small layer and it is cached, but it is also a single point of flakiness — an emulated failure fails the whole manifest list, so a transient `apk` error blocks a merge or a publish rather than degrading to one platform. Building only the runner's platform on pull requests is the tuning knob if that proves noisy; the cost of taking it is that an `arm64`-only break reaches `main` and surfaces at release.
- **Registry visibility**: a GHCR package inherits its repository's visibility on first publish. A public repository yields a public image, which is the intent — an evaluator must be able to pull without credentials — and is worth confirming after the first push rather than assuming.
- **`docs/roadmap.md` gets a Change Backlog row.** `development-workflow`'s "Roadmap Change Backlog Is Scoped To Product/Architecture Work" excludes changes *about* the development workflow itself; this one's subject is the artifact the product ships as — the `container-image` capability — and the CI gate is the means, not the subject. `harden-dockerfile` and `separate-context-databases` are the precedents: both are config/CI-only diffs that carry rows because their subject is the product's build and runtime shape. Like `split-api-by-bounded-context`, it belongs to no phase.
- **Docs** (finalization PR only): `docs/operations.md`'s deployment section and its CI/CD section, `README.md`'s quickstart, `CLAUDE.md`'s container-image bullet (which states that one image carries all five binaries and would now also state where that image is published), and the roadmap row.
- **Dependencies**: none. Independent of Phase 8, which remains the larger open gap.
