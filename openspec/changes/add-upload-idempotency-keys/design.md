## Context

`POST /upload` (`cmd/api/video.go`'s `handleVideoUpload`) is synchronous and in-request: it saves the upload, calls `CreateVideoJob`, then blocks on `ProcessVideoJob` (which runs `ffmpeg`) before responding. A client-side timeout or dropped connection during that blocking window is indistinguishable, from the client's perspective, from the request never having been received — so a client retry with the identical file is a realistic, not hypothetical, scenario. `openspec/specs/ddd-architecture/spec.md`'s "Redis Responsibilities Are Additive" requirement already documents the target: a retry with the same content returns the existing `VideoJobID` instead of creating a duplicate. `add-redis-infrastructure` (Phase 4) shipped `internal/platform/redis` for exactly this kind of consumer; this is its first real caller.

## Goals / Non-Goals

**Goals:**
- Detect a retried upload by content, scoped per user, without a second full read of the file.
- Prevent two concurrent identical uploads (same user, same content, in flight at the same time) from both running `ffmpeg` and creating separate `VideoJob` rows.
- Let a legitimate retry proceed normally after a prior attempt with the same content failed.
- Keep the mechanism entirely inside `handleVideoUpload`/its composition root — no change to `VideoJob`'s domain state machine or to `ProcessVideoJob`'s own contract.

**Non-Goals:**
- No idempotency for `POST /api/video-jobs` (the preview API) — it has no processing trigger today and stays out of scope, per `videojob-http-api`'s existing documented behavior.
- No client-supplied `Idempotency-Key` header. The canonical spec's scenario already commits this feature to a "same content" (hash-based) definition of duplicate, not a client-asserted one — see Decision 1.
- No cross-request deduplication across different users uploading the same bytes (e.g. two people uploading the same stock video) — the key is scoped per user, so this is intentionally not deduplicated.
- No general request-level idempotency framework for the rest of the API — this is scoped to `POST /upload` specifically.

## Decisions

**1. Idempotency key: `sha256(content)` scoped per user (`idempotency:{userID}:{hash}`), computed via `io.TeeReader` during the existing upload-to-disk copy — not a client-supplied header, not a partial/prefix hash.**
The canonical spec's scenario text ("a client retries `POST /upload` with the same content") already commits this feature to content-based identity rather than a client-asserted key. A prefix hash (first N bytes only) was considered and rejected: video files sharing a codec/container/recording-app configuration commonly share long near-identical headers (MP4 `ftyp`/`moov` boxes, MKV headers) despite completely different frame content, so a prefix hash risks false-positive collisions between genuinely different uploads — a correctness bug, not just a missed optimization, and one this handler has no cheap way to fall back and verify against (unlike file-dedup tools that use a partial hash as a candidate filter and fall back to a full byte comparison). The handler already reads every byte of the upload once to save it to `uploads/`; hashing through the same `io.Copy` via `io.TeeReader` costs no extra I/O pass — SHA-256 throughput (several hundred MB/s per core) is not the bottleneck in a request whose bytes arrive at network upload speed. The key is scoped per user (not global) so two different users uploading identical bytes don't collide with each other.

**2. Two-phase key value with an ownership token: `SET key "processing:{token}" NX EX <short-ttl>` reserved atomically before `CreateVideoJob`, finalized to the real `VideoJobID` via a token-checked compare-and-set once `CreateVideoJob` succeeds.**
The key can't hold the real `VideoJobID` from the start, because the ID doesn't exist until `CreateVideoJob` runs — but the reservation has to happen *before* `CreateVideoJob` to actually close the race between two concurrent identical requests (reserving after creation would let both requests pass a "does the key exist" check and both create a job). A plain literal `"processing"` sentinel (an earlier draft of this decision) has a real bug: if the sentinel's short TTL expires before the original handler finishes (e.g. it's unusually slow, or crashes without ever calling `Finalize`/`Clear`), a second request can legitimately re-reserve the same key — and then the *original*, now-stale handler can still call `Finalize` or `Clear` later, unconditionally overwriting or deleting the second request's live reservation. `Reserve` therefore generates a random per-request token (`uuid.NewString()`) and stores `"processing:{token}"` as the value; `Finalize(ctx, key, token, jobID)` and `Clear(ctx, key, token)` both perform a Lua-scripted compare-and-set/delete (`GET key == "processing:{token}"` before writing) — the same pattern Redis's own docs recommend for safe distributed-lock release — so a stale handler's late `Finalize`/`Clear` call is a no-op against a key someone else now owns, never a silent overwrite. `internal/platform/redis`'s `*redis.Client` exposes `Eval`/`EvalSha` for this; no new package dependency needed.

**2a. A failed `Reserve` triggers a bounded wait-and-retry against `Lookup`, not an immediate `409` — `409` is a last-resort timeout, not the designed response to a duplicate.**
`openspec/specs/ddd-architecture/spec.md`'s existing "Idempotency key prevents duplicate job creation" scenario says a retry "returns the existing `VideoJobID`," with no carve-out for an in-flight request. An immediate `409` on a failed `Reserve` would contradict that scenario for the (common) case where the key has already finalized to a real job by the time a near-simultaneous duplicate arrives — and naively checking "is the sentinel still `processing`" first (an earlier draft's task 3.5) has its own race: the key can finalize *between* that check and the `Reserve` call. Instead: when `Reserve` fails, the handler calls `Lookup` in a short bounded retry loop (e.g. every 100ms, up to 2 seconds — well under the sentinel's own TTL). If `Lookup` resolves to a real `VideoJobID` within that bound, the handler returns that job's status, translated per Decision 8 — matching the canonical scenario exactly, no spec delta needed. Only if the bound is exceeded (the original handler is abnormally slow or has crashed before finalizing or clearing) does the handler give up and return `409`, as a genuine "try again shortly" signal for a real edge case, not the primary duplicate-handling path.

**3. On `FailJob`, delete the idempotency key immediately rather than letting it expire naturally.**
The 24-hour window (Decision 4) exists to deduplicate retries of a *successful* (or in-flight) submission. A failed extraction (e.g. a corrupt or unsupported video slipping past extension validation) is exactly the case where the user needs to be able to retry — including retrying with the identical file, if the failure was transient (e.g. a container restart mid-`ffmpeg`). Leaving the key in place for the full window would silently turn every failure into a 24-hour lockout on that exact file, which is worse than the duplicate-processing problem this feature exists to solve.

**4. Fixed 24-hour TTL for the finalized (real-`VideoJobID`) key, not configurable via env var.**
24 hours is the de facto default idempotency-key window in the systems this pattern is best known from (e.g. Stripe's Idempotency-Key header defaults to a 24h window), and comfortably covers the realistic "client retried after a network blip or a restart" scenario this feature targets. No requirement or stakeholder need surfaced during explore that called for a shorter or longer window, so a fixed constant avoids adding configuration surface for a value nothing currently depends on tuning. If a real need to tune it emerges later, this is a small, backward-compatible follow-up (add an env var, default unchanged).

**5. On a finalized duplicate, delete the redundant file the current request just saved; never touch the original request's artifacts.**
Detecting the duplicate requires the full upload to have already landed on disk (Decision 1 — the hash isn't known until the copy completes), so by the time a duplicate is detected, a redundant copy of the same bytes already exists at this request's own `uploads/<uploadID>_<filename>` path. Each request mints its own `uploadID` (`uuid.NewString()`) independent of content, so this delete only ever removes the current request's own file — it cannot collide with or delete the original request's `uploads/` file or `outputs/` artifact, which live under a different `uploadID`.

**6. Idempotency logic lives in `internal/video/infrastructure/idempotency` behind a new `domain.IdempotencyStore` port, not as ad-hoc Redis calls inline in `cmd/api/video.go`.**
`add-redis-infrastructure`'s proposal already scoped this: "idempotency and status-cache logic under `internal/video/infrastructure/`, since both wrap video-context use cases" (as opposed to rate-limiting middleware, scoped directly to `cmd/api` since it isn't a bounded-context concern at all). This also matches the existing pattern every other Video Processing dependency follows — `domain.VideoJobRepository`/`domain.FrameExtractor` are ports defined in `internal/video/domain`, implemented by concrete adapters in `internal/video/infrastructure/{postgres,ffmpeg}`, and wired at `cmd/api`'s composition root (`setupVideo`). `IdempotencyStore` (`Reserve`, `Finalize`, `Lookup`, `Clear`) follows the same shape. The key itself becomes a small domain value object, `domain.IdempotencyKey` (constructed from `UserID` + content hash, mirroring `OriginalFilename`/`StorageKey`'s existing style), so `handleVideoUpload` builds a `Key`, not a raw string. `handleVideoUpload` calls the port directly around its existing `CreateVideoJob`/`FailJob` calls — this is control flow around use cases, not itself a use case, so no new `videoapplication` type is introduced (matching how `recordArtifactOwner`/ownership-sidecar logic is already transport-layer code called directly from the handler, not modeled as its own use case).

**7. Post-reservation failures: `CreateVideoJob` failure clears the reservation (best-effort); `Finalize` failure is logged, not fatal — the sentinel's own short TTL is the backstop.**
Two failure points sit between a successful `Reserve` and a successful `Finalize`, and both need an explicit answer instead of being left implicit: (a) `CreateVideoJob` itself fails (e.g. a PostgreSQL error) — no job was created, so the reservation is now blocking a content+user combination that has no job behind it. The handler calls `Clear(ctx, key, token)` in this path so an immediate retry isn't forced to wait out the sentinel TTL; if `Clear` itself fails (Redis unreachable), the sentinel's short TTL (Decision 2) still bounds the damage to a few minutes. (b) `CreateVideoJob` succeeds but the subsequent `Finalize` call fails (e.g. a transient Redis error) — a real, valid `VideoJob` now exists in PostgreSQL (the authoritative store) with no idempotency mapping pointing at it. Per `ddd-architecture`'s own framing of Redis as a non-authoritative performance/reliability layer, this is treated as best-effort: the handler logs the failure and proceeds to `ProcessVideoJob` normally — the job is still valid and will complete/fail on its own, it just won't be found by a future duplicate lookup until its sentinel naturally expires. Failing the whole request over a Redis write failure for an otherwise-good job would make idempotency (a reliability feature) a new source of unreliability, which defeats its purpose.

**8. Duplicate responses are translated from `GetJobStatusResult` into `ProcessingResult` — never returned as `GetJobStatusResult`'s own JSON shape.**
`POST /upload`'s existing client (`cmd/api/web/app.js`) only understands `ProcessingResult`'s fields (`success`/`message`/`zip_path` — `app.js` reads exactly those three; `frame_count`/`images` are accepted but not rendered). `GetJobStatusResult` (`job_id`/`status`/`frame_count`/`error_reason`/`storage_key`) is a different shape entirely; returning it directly for a duplicate would make `app.js`'s `result.success` check `undefined` and render `"Erro: undefined"` for what should read as a normal completed response. The handler instead maps the looked-up job's state into `ProcessingResult`: `completed` → `{Success: true, Message: <English>, ZipPath: StorageKey, FrameCount: FrameCount}` (per-frame `Images` names aren't persisted anywhere `VideoJob`/`GetJobStatusResult` expose, and `app.js` never reads that field regardless, so it's simply omitted — not a regression); `failed` → `{Success: false, Message: <English, incorporating ErrorReason>}`; still `pending`/`queued`/`processing` (only reachable via the 2a timeout path, since the common case already resolves to a terminal-or-processing job through the bounded wait) → `{Success: false, Message: <English: "already being processed, try again shortly">}`. All new `Message` strings follow `CLAUDE.md`'s language policy: they're constructed in Go code (not `index.html`/`app.js`'s own visible markup), so they're new English strings, not Portuguese, even though the page around them is otherwise Portuguese — the policy's UI-copy exception is scoped to the two frontend files specifically, not to "any string a user sees."

## Risks / Trade-offs

- **[Risk]** A duplicate can only be detected after the full file has already been transferred and written to disk — there's no way to reject earlier, since the key is content-derived rather than asserted upfront by the client. → **Mitigation:** accepted trade-off, discussed explicitly during explore; the alternative (a client-supplied header) was rejected in Decision 1 because the canonical spec already commits this feature to content-based identity. The `ffmpeg` cost is still avoided, which is the dominant cost this feature targets.
- **[Risk]** `REDIS_ADDR` becomes a new required startup dependency for `cmd/api` — if Redis is unreachable, does the whole API fail to start, or does `/upload` degrade? → **Mitigation:** startup requires `REDIS_ADDR` to be set (matching `VIDEO_POSTGRES_DSN`'s existing required-at-startup precedent) but does not itself verify Redis connectivity at boot (`internal/platform/redis.Open` never did); a `Ping`/command failure at request time surfaces as a 500 on `/upload`, not a startup crash — see tasks.md for the concrete failure-handling task.
- **[Risk]** The short TTL on the `"processing:{token}"` sentinel (Decision 2) needs to be long enough that `CreateVideoJob` never legitimately outlives it (which would let a second request through). → **Mitigation:** `CreateVideoJob` only writes to PostgreSQL (fast, sub-second under normal conditions); a multi-minute sentinel TTL leaves generous headroom, and tasks.md pins a concrete value.
- **[Risk]** The bounded wait-and-retry (Decision 2a) adds up to ~2 seconds of latency to a duplicate request's response, on top of the time it already spent uploading. → **Mitigation:** accepted — this only affects the narrow-window duplicate case (not the common path, which resolves via a single `Lookup` before any wait), and 2 seconds is small next to the multi-second-to-minutes `ffmpeg` cost this feature exists to avoid re-paying.
- **[Risk]** Token-checked compare-and-set (Decision 2) requires a Lua script (`EVAL`) rather than a plain `SET`/`DEL` — one more thing to get right (script correctness, `EvalSha` caching behavior) than the simplest possible implementation. → **Mitigation:** this is Redis's own documented pattern for safe lock release, not a novel design; the script is a few lines and is covered by the adapter tests in tasks.md.

## Migration Plan

No data migration. Rollout: merge → `cmd/api`'s composition root gains a `REDIS_ADDR` requirement → `docker-compose.yml`'s `app`/`app-test` services need `REDIS_ADDR` added (they don't have it yet — only `internal/platform/redis`'s own tests did, from `add-redis-infrastructure`) and a `depends_on: redis` entry, mirroring the pattern already used for `postgres`. Rollback is a plain revert of the handler change; `REDIS_ADDR` can stay required or be removed from `cmd/api`'s startup check as part of that same revert, whichever the revert commit chooses — no persisted Redis state depends on this feature (all keys carry their own TTL and expire on their own even if the code is rolled back first).
