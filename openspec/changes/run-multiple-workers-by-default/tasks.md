## 2. Verification (implementation PR)

The diff carries no Go module input, so `development-workflow`'s "A non-build change is exempt from the local test-run requirement" applies and there is no `go test` obligation. Verification is behavioural instead, and every step below is run, not reasoned about — the previous change's finding was that documentation asserting unverified behaviour is exactly what goes wrong here.

- [ ] 2.1 `docker compose config` parses without error or warning about the `deploy` key.
- [ ] 2.2 `docker compose up -d --build` with no scaling flag starts `worker-1`, `worker-2`, and `worker-3`. Confirm via `docker compose ps`, not by inference from the up output.
- [ ] 2.3 Each of the three worker containers logs its own connected consumer **and** its own connected terminal relay — three consumers on one queue, three relays claiming with `SKIP LOCKED`. A container that started but never connected is not a working replica.
- [ ] 2.4 `docker compose up -d --scale worker=1` collapses the running project to a single worker, and `--scale worker=5` raises it to five, proving the documented override still wins over `deploy.replicas` in both directions (this is what the finalization docs will claim).
- [ ] 2.5 Demonstrate RF1 itself — the only step that proves the change did what it was for — and do it deterministically, because the obvious version of this check fails for reasons that have nothing to do with replication. Two constraints make it deterministic:
  - **Distinct content per upload.** `POST /upload` reserves an idempotency key scoped to `UserID` + the SHA-256 of the bytes, so the same file uploaded twice by one user resolves to the *same* `VideoJob` and runs `ffmpeg` once. Three byte-identical uploads would prove nothing. Use three different videos (or three files with genuinely different bytes).
  - **Queue before consuming.** Prefetch is 1 and extraction of a short clip can finish before the next upload is even dispatched, so a serial trace is a possible outcome of a correctly replicated stack. Remove the race instead of hoping to win it: `docker compose stop worker`, upload the three videos (they accumulate in `queued` — the API answers `202` with no worker running), then `docker compose start worker` and let all three claim at once.
- [ ] 2.6 The discriminating assertion for 2.5 is three *distinct* job IDs claimed by three *distinct* container names, observed simultaneously — not merely that three jobs eventually completed, which one worker in a loop also produces. Confirm it from both sides: the three containers' logs, and the jobs reporting `processing` at the same moment (`GET /api/video-jobs` for that user, or a direct `SELECT status FROM video_jobs`).
- [ ] 2.7 Note any failure that is a property of the machine rather than of this change (e.g. host port 8080 already taken by an unrelated container) explicitly as such, and re-run the affected step after clearing it rather than reporting around it.
