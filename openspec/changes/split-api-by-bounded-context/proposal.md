## Why

The validation report classifies "Desenvolvimento de microsserviços" as ⚠️ *Parcial*, and the finding survives inspection. The packaging it objects to — one Go module, one image, a shared `internal/` — is not what makes this a monolith; `go list -deps` shows `cmd/worker` and `cmd/notifier` sharing exactly one package (`internal/platform/rabbitmq`), so the sharing already follows the bounded-context lines. What is genuinely monolithic is **`cmd/api`**: one process serves Identity, Video Processing and Notification, holds three PostgreSQL pools, and cannot be deployed, scaled, restarted or secured per context. `cmd/worker` and `cmd/notifier` are already single-context services. The HTTP tier is the only place where the architecture the specs describe is not the architecture that runs.

Splitting it is the smallest change that makes the claim true rather than aspirational, and it is not cosmetic: today a MinIO outage takes down `/api/auth/login`, a rate-limit change redeploys the login path, and the JWT signing key sits in a process whose Notification half only ever needs to *verify*. Each of those is a coupling that the split removes rather than documents.

## What Changes

- **`cmd/api` becomes three HTTP composition roots.** `cmd/identity-api` (`/api/auth/*`), `cmd/video-api` (`/`, `/upload`, `/download/:filename`, `/api/status`, `/api/video-jobs*`, plus the frontend and the dispatch outbox relay) and `cmd/notification-api` (`/api/notification-preferences`). The per-context files already exist as `identity.go`, `video.go` and `notification.go`; the split moves them into their own `main` packages rather than restructuring them. `main.go` and `ratelimit.go` are what actually divide: each service gets its own router, its own signal handling and its own shutdown ordering, and each requires only the configuration it uses. `cmd/worker` and `cmd/notifier` are untouched.
- **nginx becomes the ingress.** A `gateway` service publishes `127.0.0.1:8080:8080` and routes by path prefix to the three services, which each listen on 8080 inside their own container and publish nothing. The external contract does not move: the same URLs on the same host port, so `cmd/video-api/web/app.js`, `README.md`'s curl sequence and every documented flow keep working unchanged. Two nginx defaults would silently break `POST /upload` and are therefore requirements, not configuration notes: `client_max_body_size` (1 MB by default) and `proxy_request_buffering` (on by default, which would spool the whole upload to the gateway's disk and undo the single-pass streaming `videojob-source-storage` requires).
- **BREAKING — access tokens are signed RS256, and only Identity holds a private key.** Three services cannot share one HMAC secret without giving Video Processing and Notification the ability to *mint* tokens, which is a privilege they have no reason to hold and which today's single process makes meaningless. `IDENTITY_JWT_SIGNING_KEY` is replaced by an `IDENTITY_JWT_PRIVATE_KEY` and an `IDENTITY_JWT_KEY_ID` read only by `cmd/identity-api`, and an `IDENTITY_JWT_PUBLIC_KEYS` **set** of `kid`-to-PEM entries read by every service that verifies. The public key is distributed **by configuration**, not by a JWKS endpoint: JWKS would reintroduce a synchronous verifier→Identity call on every cold cache and make Identity's availability a dependency of every other service's authorization decision, which is precisely the coupling this change exists to remove. Tokens carry a `kid` header and the verifier holds a keyed set from the first commit, so rotation is a configuration change rather than a later migration.
- **The cross-context pin tests move to a test-only package.** `TestNotificationEventTypesMatchTheEmittedTerminalEventTypes`, `TestNotificationTerminalTopologyMatchesTheEmittedTopology` and `TestNotificationTerminalMessagesDecodeTheEmittedPayloads` live in `cmd/api/notification_test.go` because it is "the composition root that legitimately imports both contexts". After the split no production process imports both, so the justification they were given evaporates while the drift they prevent does not. They move to `internal/contracts`, a package with no non-test declarations beyond its doc comment, whose sole purpose is to hold them. `ddd-architecture`'s dependency rule is amended to name it, because a package that imports two contexts is otherwise exactly what that rule forbids.
- **`TestTheHTTPCompositionRootDoesNotLoadTheSecret` is re-targeted, not moved.** It asserts that no file under `cmd/api` calls `FindDeliverable`. Its subject becomes `cmd/notification-api`, the only HTTP root that could reach the secret at all — a narrower and stronger claim than the one it makes today, since the other two services no longer link the Notification repository.
- **Rate limiting stays one budget.** `cmd/video-api` and `cmd/notification-api` each mount `internal/platform/ratelimit` against the same Redis with the same key format, so a user's 60 requests/minute remains 60 across the system rather than becoming 60 per service. The middleware pair (`requireBearerAuth` then the limiter, in that order) is the invariant `cmd/api` already states; the split preserves it per service instead of per group.

Not in scope: any change to `cmd/worker`, `cmd/notifier`, the two RabbitMQ topologies, the job state machine, the HTTP request/response shapes, or the database schema. A client cannot observe this change except by the token's `alg`.

## Dependency

`separate-context-databases` SHALL land first. The split is mechanically fine against one shared `identity` database, which is exactly the risk: three services each holding a pool onto the same database would satisfy every test here while leaving the storage coupling the other change exists to remove. Ordering them makes the end state one service, one database, one context.

## Capabilities

### New Capabilities
- None. This change relocates and reconfigures what exists; the one genuinely new behavior — asymmetric token signing — belongs to `identity-authentication`, which already owns token issuance and verification.

### Modified Capabilities
- `ddd-architecture`: `Monorepo Package Topology Is the Target Structure` names three entrypoints and there will be five; `Package Dependency Rules` enumerates the composition roots permitted to translate a cross-context identifier and must admit the test-only pin package; `Frontend as Presentation/Delivery Layer` hard-codes `cmd/api/web/`. A new requirement states the property the change exists to establish: each bounded context's HTTP surface is its own process with its own configuration surface.
- `identity-authentication` (**breaking**): token signing becomes asymmetric, the private key is held by exactly one service, and `Configuration does not provide insecure defaults` gains the rule that a verifier configured with a private key — or with no key at all — fails startup rather than starting able to mint.
- `development-workflow`: `Local Full-Stack Development Service` promises one documented command reaching `/api/auth/register` and `/api/auth/login`. It still does, through the gateway; the requirement has to say so, and has to say that no application service publishes a host port.
- `container-image`: the runtime image carries five binaries instead of three, and the compose stack gains a service built from a different base image (nginx) for the first time.
- `rate-limiting`: `Authenticated Video Routes Are Rate Limited Per User` is written against one process. The budget is unchanged and the middleware is unchanged; what changes is that two processes mount it and share the counter.
- `notification-preferences`, `notification-persistence`, `notification-event-consumer`: three requirements pin their guarantees to "the composition root that legitimately imports both contexts" or to "the HTTP composition root". Both phrases have exactly one referent today and none after the split, so each is re-anchored to the concrete package that carries the test.

## Impact

- **Code**: `cmd/api/` is deleted and replaced by `cmd/identity-api/`, `cmd/video-api/` and `cmd/notification-api/`. 1631 lines of production Go move (identity.go 230, video.go 910, notification.go 215, ratelimit.go 58, main.go 218) and 4863 lines of test Go are redistributed (identity_test.go 711, main_test.go 874, notification_test.go 1170, ratelimit_test.go 239, video_test.go 1869). `cmd/api/web/` moves to `cmd/video-api/web/`. `internal/identity/infrastructure/jwtauth` splits its issuing and verifying halves. New: `internal/contracts` (test-only) and `docker/nginx/`. Nothing under `internal/video`, `internal/notification`, `cmd/worker` or `cmd/notifier` changes.
- **Configuration**: `IDENTITY_JWT_SIGNING_KEY` is removed; `IDENTITY_JWT_PRIVATE_KEY`, `IDENTITY_JWT_KEY_ID` and `IDENTITY_JWT_PUBLIC_KEYS` replace it, distributed per service — the first two to Identity alone, the key set to every verifier. `RATE_LIMIT_*` is supplied to the two limiter-mounting services from one place, because the counter they share is only one budget if the threshold and the window are identical. `docker-compose.yml` loses `app` and gains `gateway`, `identity-api`, `video-api` and `notification-api`; only `gateway` publishes a port. `app-test` keeps its role unchanged — the test stage still builds the whole module.
- **Data**: none. No schema change, no migration, no backfill. Existing tokens signed with the old key stop verifying at deploy, which for a hackathon deployment means users log in again; there is no dual-verification window and none is proposed, because carrying an HMAC verifier into the split would keep the minting capability the change removes.
- **Security**: strictly narrowing. Two of three HTTP services lose the ability to mint tokens; `cmd/identity-api` loses MinIO, Redis and broker credentials; `cmd/video-api` and `cmd/notification-api` lose the identity database DSN. `gosec` and `govulncheck` run on every PR as usual.
- **Docs**: `docs/architecture.md` (the request flow now starts at the gateway), `docs/operations.md` (five services, the new variables, the key-generation step), `docs/development.md` (five `go run` targets), `docs/flows.md`, `README.md`, `docs/roadmap.md` and `CLAUDE.md`. All of these belong to the finalization PR.
- **Specs**: eight capabilities carry delta specs. A further set — `videojob-result-storage`, `videojob-outbox-relay`, `videojob-worker`, `videojob-source-storage`, `rabbitmq-infrastructure`, `videojob-terminal-events`, `minio-infrastructure`, `videojob-lifecycle`, and `videojob-http-api`'s Purpose line — names `cmd/api` only as the process that happens to run something, with no requirement changing. Those are a name substitution and are handled as a documentation-accuracy sweep in the finalization PR; see `design.md` for why they are not delta entries.
