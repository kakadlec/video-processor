## Why

Two changes built the halves of a notification and left the gap between them empty. `emit-videojob-terminal-events` put `video_job.completed.v1` and `video_job.failed.v1` on a durable queue and declared that queue explicitly ahead of a consumer; `add-notification-domain-and-preferences` gave a user somewhere to say where they want to be told and with which secret the message should be signed. Nothing joins the two, so the queue accumulates by design and a registered preference delivers nothing.

This change closes it: a third process reads that queue, resolves each event against the owner's preferences, and delivers a signed webhook. It is the first thing in the system that dials an address a user supplied, which is why two questions the earlier changes deferred with a named forwarding address — the SSRF posture of an arbitrary destination, and the retry policy for an endpoint that is simply down — are answered here rather than inherited.

## What Changes

- **`cmd/notifier`, a third entrypoint in the same image.** It consumes `video.jobs.terminal.events.v1`, requires only `NOTIFICATION_POSTGRES_DSN` and `RABBITMQ_URL`, and listens on nothing. It is a separate process rather than a goroutine in `cmd/api` or `cmd/worker` for the reason the terminal relay lives in the worker: a delivery attempt against a slow third-party endpoint should not share a lifecycle with request serving or with `ffmpeg`, and the three scale on different axes.
- **Its own copy of the terminal wire contract.** `ddd-architecture` forbids Notification importing Video Processing — a rule about imports at rest, not only while handling an event — so `internal/notification/infrastructure/messaging` declares the topology names and the two message structs itself. Both duplications are pinned against Video Processing's originals by a test in `cmd/api`, the composition root that legitimately imports both contexts, in the same spirit as the existing `TestNotificationEventTypesMatchTheEmittedTerminalEventTypes`. An unpinned copy would let a rename leave the consumer binding to a queue nothing publishes to.
- **Resolution against preferences, with the preference's own age as the enrolment boundary.** An event is delivered only to preferences that are `enabled`, name its event type, and were created **before the event occurred**. The queue has been accumulating since `emit-videojob-terminal-events` shipped, so the first deploy drains a backlog; `videojob-outbox-relay` met the same problem and answered it with an explicit `occurred_at` cutoff, but a cutoff pinned to a deploy date would also discard legitimate events if the notifier were down for a day. A preference's `created_at` is the better boundary and needs no constant: a standing instruction does not announce what happened before it was given, and the rule keeps holding after the backlog is gone.
- **A signed webhook with the context's own payload.** `POST` to the destination carrying a versioned Notification envelope — not the Video Processing wire payload forwarded verbatim, which would make an internal contract into a public one and couple every future producer change to every registered endpoint. Headers carry the event type, a stable delivery id, a timestamp, and `X-FiapX-Signature: sha256=<hex>` over `timestamp.body`, so a captured request cannot be replayed indefinitely. The secret reaches exactly one function through `Secret.Reveal()` and appears in no log line.
- **Delivery records that carry deduplication.** `videojob-terminal-events` states that at-least-once delivery makes dedup the consumer's obligation, and this change is that consumer. A new `notification_deliveries` table keyed on `(user_id, event_type, channel, job_id)` is **claimed before the attempt, not written after it**, so a redelivered message finds the claim and delivers nothing. The row carries two identifiers: a stable `delivery_id` the receiver deduplicates on, preserved across a takeover, and a `claim_token` reissued on every grant that fences resolution — the reclaim bound proves a claim is old, not that the process holding it stopped, so without the fence a slow first claimant could overwrite its successor's outcome. The fence covers the write and nothing else, so the bound is sized from the attempt budget rather than chosen independently — a bound shorter than one claimant's maximum hold would produce two live requests to one destination, and `cmd/notifier` refuses to start when it is. It doubles as the record of how each delivery ended, which is what the retry policy reports into.
- **A retry policy stated rather than inherited.** `cmd/worker`'s "dead-letter, never requeue" is calibrated for a claim-fenced job, and a 5xx from a user's endpoint is not that failure. Delivery is attempted a bounded number of times in-process with backoff under a bounded total budget; the outcome — delivered or exhausted — is recorded and the message is **acked either way**, because a user's broken endpoint is not a defect in this system and must not fill a dead-letter queue. The dead-letter path is reserved for a message this process can never act on (an undecodable body, an unrecognized event type), and a **transient dependency failure** — the notification database unreachable — is neither: it requeues with a pause, which is the one disposition `cmd/worker` deliberately does not have, because there a redelivery could only lose the claim again while here the condition clears on its own. That requeue is defined by **this handler having attempted nothing** — so it covers every pre-attempt repository failure, and also a claim another consumer still holds, which is requeued rather than acked because a crashed claimant's redelivery arrives seconds later, far inside the reclaim bound, and acking it would strand the row and drop the notification silently. Once the claim is held and a request has gone out the disposition inverts: a failure to *record* an outcome is retried on a detached context and then acknowledged with a logged loss rather than requeued.
- **BREAKING — an SSRF posture, now that something dials.** `add-notification-domain-and-preferences` recorded this as out of scope "until something dials it" and named this change. A destination policy permits only globally-reachable unicast addresses **at the resolved IP, in the dialer** — an allow-list, and one that adds an explicit prefix table on top of the standard predicates, since those accept CGNAT, benchmarking, and reserved space that routes inside real networks, plus a separate IPv6 list rather than "the v4 equivalents", since documentation, discard-only, 6to4 and Teredo space has no v4 counterpart and the last two carry a request to an embedded IPv4 address through a relay — follows no redirects, bounds the response body, and requires `https` — with one opt-out variable, defaulting to closed, that the compose stack sets so local development over `http` to a container hostname keeps working. The same policy is applied at write time in `PUT /api/notification-preferences`, so a destination that could never be delivered to is refused where the user can see the error rather than accepted into silence — the argument the closed `Channel` set already makes about `email`. That is the breaking part: a destination the route accepts today — any absolute `http` URL, and any address on a private or loopback network — is answered with `400` after this change, under the default policy. Existing stored rows are not rewritten or validated retroactively; what changes is what a new write is allowed to store, and an already-stored destination the policy refuses is simply never dialled.
- **The first read path that loads a secret.** Every existing read projects `secret <> '' AS has_secret` and never selects the column, which is what makes `PreferenceView`'s missing field a guarantee. HMAC needs the bytes, so a second, separately named port method returns the full `NotificationPreference` aggregate — the type `add-notification-domain-and-preferences` built for exactly this caller and left unused. This is a deliberate, narrow exception to a documented invariant and is written as one: the new method has one caller, and a test asserts no HTTP-facing path reaches it.

No change to `POST /upload`, to the worker, to the job or terminal topologies, or to any `VideoJob` state. A delivery that fails never touches a job. `email` remains a rejected channel.

## Capabilities

### New Capabilities
- `notification-webhook-delivery`: what a delivered notification is — the enrolment boundary that decides whether an event reaches a preference, the outbound request and its versioned payload, the HMAC signature and what it covers, the destination policy applied at both write and dial, the bounded attempt budget, and the deduplication guarantee the terminal-event capability assigns to its consumer.
- `notification-event-consumer`: the `cmd/notifier` process — the topology it declares on every dial, its startup requirements and the ones it deliberately lacks, its three-way disposition table and why it differs from `cmd/worker`'s two, and the shutdown ordering that joins an in-flight delivery before closing the pool it borrows.

### Modified Capabilities
- `notification-persistence`: gains the `notification_deliveries` table and its claim semantics, and the secret-loading read path — an explicit, narrowly scoped exception to the requirement that no read path loads the secret, rather than a relaxation of it.
- `notification-preferences` (**breaking**): `Destination` currently accepts `http` unconditionally, with its own documentation naming this change as the one that would restrict it. The write path gains the destination policy, and `created_at` gains a second meaning as the enrolment boundary a delivery is evaluated against.
- `container-image`: the runtime image carries a **third** binary, `/app/notifier`, built by the same builder stage and started as the same image with a different command.
- `ddd-architecture`: `Monorepo Package Topology Is the Target Structure` names `cmd/api` and `cmd/worker` as the entrypoints. A third joins them, and the requirement that each composition root wires only the configuration it uses applies to it unchanged.

## Impact

- **Code**: new `cmd/notifier/` (composition root, consumer wiring, disposition table); new `internal/notification/infrastructure/{messaging,webhook}` and `internal/notification/application`'s delivery use case; new domain pieces for the destination policy, the delivery record, and the signature. `cmd/api/notification.go` applies the destination policy on write; `cmd/api`'s pinning test grows. Nothing under `internal/video`, `internal/identity`, or `cmd/worker` changes.
- **Data**: one new table, `notification_deliveries`, in the Notification database, created by the context's existing advisory-locked `Migrate`. No change to `notification_preferences`. No backfill: a delivery that never happened cannot be reconstructed.
- **Configuration**: `NOTIFICATION_POSTGRES_DSN` and `RABBITMQ_URL` required at `cmd/notifier` startup; optional, defaulted knobs for the attempt budget, per-attempt timeout, the delivery reclaim bound (validated at startup against the attempt budget rather than tunable independently of it), and the destination-policy opt-out. `docker-compose.yml` gains a `notifier` service and the opt-out for local `http` destinations; `Dockerfile` builds and ships the third binary.
- **Security**: the first outbound request to a user-supplied address, and the first code path that reads a stored secret. Both are the substance of the change rather than a side effect — the destination policy and the non-logging of `Secret` are requirements, not implementation notes. `gosec` runs on every PR.
- **Docs**: `docs/architecture.md` gains the third process and the delivery flow, `docs/domain-model.md` the delivery record, `docs/operations.md` the new service, its variables, and the fact that a stored secret is now read at delivery time, `docs/development.md` the third binary in the build commands, `docs/roadmap.md` the row's status, and `CLAUDE.md` the third composition root.
