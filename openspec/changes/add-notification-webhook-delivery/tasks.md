# Tasks

Implementation order follows the dependency chain: the domain pieces first (they carry the policy and the record every other layer defers to), then persistence, then the context's own copy of the wire contract, then the outbound adapter and the use case that drives it, then the third composition root and the image, then the write-time half of the destination policy on `cmd/api`.

Each numbered group is sized to be one implementation PR. Group 7 is finalization and belongs to the change's closure PR, not to any implementation PR.

## 1. `internal/notification/domain`

- [ ] 1.1 `terminal_event.go`: the context's own model of a consumed terminal outcome — event type, job id, user id, occurred-at, and the outcome-specific fields (frame count and result key for a completion, reason for a failure). It is built from a decoded message at the composition root; it is not the message type itself, so nothing downstream of it knows a wire format exists.
- [ ] 1.2 `destination_policy.go`: a `DestinationPolicy` deciding whether a destination may be registered and whether a resolved address may be dialled. Restrictive by default: scheme must be `https`; hostname must not be `localhost`; an address is permitted only if it is globally reachable unicast. One boolean relaxes both the scheme rule and the address rule together, per `design.md`; do not split it into two knobs.
- [ ] 1.2b The address check is **an explicit prefix table in addition to the standard-library predicates, not instead of them**. `IsGlobalUnicast()` returns true for `100.64.0.0/10`, `198.18.0.0/15`, and `240.0.0.0/4`, so a check built only from the stdlib predicates reintroduces exactly the gap this task closes. IPv4: loopback, unspecified, link-local, multicast, RFC 1918, `100.64.0.0/10`, `198.18.0.0/15`, `192.0.0.0/24`, `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`, `240.0.0.0/4`, `0.0.0.0/8`.
- [ ] 1.2b-i IPv6 is **its own list, not "the v4 equivalents"** — the same predicate accepts native special-use space with no v4 counterpart. Enumerate: `::/128`, `::1/128`, link-local `fe80::/10`, unique-local `fc00::/7`, multicast and interface-local `ff00::/8`, documentation `2001:db8::/32`, discard-only `100::/64`, 6to4 `2002::/16`, and Teredo `2001::/32`. The last two carry an embedded IPv4 address to a relay, so refuse the **prefix** outright rather than unwrapping and evaluating what it embeds — the relay is not ours to reason about. Only IPv4-mapped (`::ffff:0:0/96`) and NAT64 (`64:ff9b::/96`) are unwrapped to the IPv4 address they embed and evaluated as that address, **before** any other check, so a refused address cannot be reached by rewriting it. Prefer `net/netip` over `net.IP` throughout.
- [ ] 1.2a Give the policy two entry points, one over a `Destination` (registration) and one over a `netip.Addr` (dial), so the dial-side caller cannot accidentally check the hostname instead of the address it resolved to. Table-driven tests over both, with **one case per refused prefix named in 1.2b and 1.2b-i** plus a mapped and a NAT64 form of a refused address, a 6to4 and a Teredo address embedding a *public* IPv4 address (still refused), and a public v4 and a public v6 address that are accepted.
- [ ] 1.3 `delivery.go`: the delivery record — its identity (`UserID`, `EventType`, `Channel`, job id), a stable `DeliveryID`, a `ClaimToken` reissued on every grant, a status (`pending`, `delivered`, `failed`), an attempt count, a claimed-at and a resolved-at, and the last observed reason. The reason is free text written by this system, never a response body echoed back from a third party.
- [ ] 1.4 `delivery_repository.go`: the port — `ClaimDelivery(ctx, identity, now, staleBefore) (Delivery, ClaimOutcome, error)` and `ResolveDelivery(ctx, deliveryID, claimToken, status, attempts, reason, now) (bool, error)` where the boolean reports whether the fence applied the write. Document on the port that claiming is one atomic statement that reads no row first, and why (`design.md`): the guarantee has to hold across processes, and a check followed by an insert loses that race. Document the fence too — the reclaim bound proves age, not that the prior holder stopped.
- [ ] 1.4a `ClaimOutcome` is **three-valued, not a boolean**: `ClaimGranted` (the returned `Delivery` carries the stable `DeliveryID` and the freshly-issued `ClaimToken`), `ClaimAlreadyResolved`, and `ClaimHeldByAnother`. Collapsing the last two into one `false` is the bug: the caller acks a resolved delivery and must *not* ack a held one, because a crashed claimant's redelivery arrives seconds later — far inside the reclaim bound — and acking it would strand the row and drop the notification. Say that on the port, where the caller reads it.
- [ ] 1.5 Extend `repository.go` with `FindDeliverable(ctx, userID, eventType) ([]*NotificationPreference, error)`, returning the aggregate with its `Secret`, for `enabled` preferences only. Document it as the one read path permitted to load the secret and name the test that pins that. Leave `ListByUser` and its `has_secret` projection untouched.
- [ ] 1.6 `deliverer.go`: the outbound port — `Deliver(ctx, preference, event, deliveryID) error` — so the application layer never names `net/http`. Its error type distinguishes a policy refusal from a transport failure from a non-`2xx`, because the recorded reason has to say which.
- [ ] 1.7 Extend `internal/notification/dependency_rules_test.go` to walk **every** package under `internal/notification`, not just `domain` and `application`. Infrastructure keeps its existing allowances (`database/sql`, `net/http`), but the cross-context prohibition applies to all of them — the infrastructure package added in group 3 is exactly where importing `internal/video` would be tempting.

## 2. `internal/notification/infrastructure/postgres`

- [ ] 2.1 `schema.sql`: add `notification_deliveries` with primary key `(user_id, event_type, channel, job_id)`, a `delivery_id UUID NOT NULL`, a `claim_token UUID NOT NULL`, `status TEXT NOT NULL`, `attempts INT NOT NULL`, `claimed_at TIMESTAMPTZ NOT NULL`, `resolved_at TIMESTAMPTZ`, and a nullable `reason TEXT`. `CREATE TABLE IF NOT EXISTS` only; do not `ALTER` `notification_preferences`.
- [ ] 2.2 The grant decision is **one statement**: `INSERT ... ON CONFLICT (user_id, event_type, channel, job_id) DO UPDATE SET claimed_at = $now, attempts = 0, claim_token = $token WHERE notification_deliveries.status = 'pending' AND notification_deliveries.claimed_at < $stale RETURNING delivery_id, claim_token`. Zero rows means the claim was refused. The `DO UPDATE` must not overwrite `delivery_id` — a reclaim keeps the identifier the receiver may already have deduplicated on — and **must** overwrite `claim_token`, which is what fences the prior holder out of resolving.
- [ ] 2.2b Classifying a refusal is a **second, deliberately non-authoritative** `SELECT status` on the refusal path only, mapping `pending` to `ClaimHeldByAnother` and anything else to `ClaimAlreadyResolved`. It does not weaken 2.2: grant-or-refuse stays one statement, and this read only picks ack versus requeue — reading it stale costs one extra pass through the handler, never a second outbound request. If the row has vanished between the two statements, treat it as `ClaimHeldByAnother`; requeueing re-runs the claim, which is the correct recovery.
- [ ] 2.2a Verify against a real PostgreSQL that the conflict clause's `WHERE` behaves as intended for all four cases before relying on it: no row, a resolved row, a fresh `pending` row, a stale `pending` row — asserting the *outcome value* in each, not just that it was refused. Add a fifth: a reclaim issues a new token, and a resolve carrying the prior token is refused and changes nothing. The equivalent assumption was wrong once already in this context (`2.5a` of the previous change).
- [ ] 2.3 `ResolveDelivery`: an `UPDATE ... WHERE delivery_id = $1 AND claim_token = $2 AND status = 'pending'` setting status, attempts, reason, and `resolved_at`, reporting whether a row was affected. It **is** fenced, and the fence is not optional: the reclaim bound proves a claim is old, not that the process holding it stopped, so a slow first claimant can still be running when a second is granted. Zero rows means this claimant was superseded — the caller logs and acknowledges rather than retrying.
- [ ] 2.4 `FindDeliverable`: `SELECT event_type, channel, enabled, destination, secret, created_at, updated_at WHERE user_id = $1 AND event_type = $2 AND enabled` — the only query in this package that names `secret`. Restore full aggregates through `RestoreNotificationPreference`.
- [ ] 2.5 `migrate.go` needs no structural change — the embedded schema grows — but confirm the advisory-locked transaction still covers both `CREATE TABLE IF NOT EXISTS` statements as one unit.
- [ ] 2.6 Adapter tests gated on `NOTIFICATION_POSTGRES_TEST_DSN`, following the existing file exactly: the five claim cases from 2.2a with their three-valued outcomes, a concurrent double claim converging on one grant and one `ClaimHeldByAnother`, resolve-then-claim being refused, a superseded claimant's resolve being refused while the successor's is applied, and `FindDeliverable` returning the secret while `ListByUser` still does not.
- [ ] 2.7 A test asserting the delivery table holds no secret column and that no statement in this package selects `secret` outside `FindDeliverable` — a source-level assertion, the way the dependency rules are enforced, since a runtime test cannot see a query that was never run.

## 4. `internal/notification/infrastructure/webhook` and the delivery use case

- [ ] 4.1 `payload.go`: the delivered envelope — a top-level `version` field, delivery id, event type, occurred-at, and a `data` object carrying the job id plus the outcome's own fields. No `user_id`, no secret, no relay bookkeeping. The version is the Notification payload's own, independent of the event type's `.v1`, and it goes in the **body** rather than a header so the signature covers it. A test asserts it is present and is not derived from the event type.
- [ ] 4.2 `signature.go`: HMAC-SHA256 over `<unix timestamp>.<body>`, hex-encoded, rendered as `sha256=<hex>`. This is the only function in the codebase that calls `Secret.Reveal()`; a test asserts that.
- [ ] 4.3 `client.go`: the `Deliverer` implementation. An `http.Client` whose transport carries a `net.Dialer` with a `Control` function applying the destination policy to the **resolved** address, a `CheckRedirect` that refuses every redirect, a per-attempt timeout, and a response body read under a small cap and discarded. Headers per `design.md`. Returns the typed errors 1.6 defines.
- [ ] 4.3a Test the dial-side policy with a hostname that resolves to a loopback address, asserting no connection is made — a test that passes because the request merely failed proves nothing, so assert on the policy error, not on the request outcome.
- [ ] 4.4 `application/deliver_notification.go`: given a `TerminalEvent`, load deliverable preferences, drop any whose `CreatedAt` is not before the event's `OccurredAt`, and for each remaining one claim, attempt within the budget, and resolve. Returns a disposition-shaped result the composition root maps to `Ack`/`Reject`/`Requeue` — the use case decides *what happened*, the composition root decides *what to tell the broker*, matching how `cmd/worker` splits those two.
- [ ] 4.4a Attempts, backoff, and the per-attempt timeout come from injected configuration with the documented defaults (3 attempts, 5s). Time comes from the existing `Clock` port; do not call `time.Now` in the use case.
- [ ] 4.4a-i The reclaim bound is configuration too — `NOTIFICATION_DELIVERY_RECLAIM_SECONDS`, default 120 — and it is **not independent** of 4.4a. Expose the maximum a claimant can hold a claim as a computed value on the delivery configuration (`MaxAttempts × (Timeout + backoff)` plus the resolve-retry budget of 4.4c), and give it a validator that refuses a bound below twice that. The claim token fences only the database write; it cannot recall a request already sent, so a bound under the budget produces concurrent requests to one destination in *normal* operation. Two-to-three times, not ten — the same value bounds the head-of-line stall of 4.4b. `cmd/notifier` calls the validator at startup (5.1); unit-test both sides of the threshold.
- [ ] 4.4b The requeue disposition is defined by **"this handler has attempted nothing"**, not by "the claim failed". It covers *every* pre-attempt repository error — `FindDeliverable`'s included, which runs before anything can be claimed — and it also covers `ClaimHeldByAnother`, which is not an error at all. `ClaimAlreadyResolved` acknowledges. A repository error while *resolving* must not requeue: the claim is already held, so a redelivery would be refused as held and requeued forever, and could re-send the webhook first.
- [ ] 4.4b-i Note in the code why `ClaimHeldByAnother` requeues rather than acking, since acking looks obviously right: RabbitMQ redelivers an unacked message within seconds of a crashed consumer's channel closing, so a redelivery meets a *fresh* `pending` row, is refused, and acking there strands the row and drops the notification. The loop terminates because the holder either resolves it (next refusal is `ClaimAlreadyResolved`) or does not (the bound expires and the claim is granted). Accepted cost, at prefetch 1: an abandoned claim stalls the queue for the reclaim bound — which is why 4.4a-i sizes it tightly.
- [ ] 4.4c A resolve that fails is retried a bounded number of times with backoff on a context detached from shutdown, mirroring `cmd/worker`'s `CompleteJob` retry. If it still fails, log the delivery id and the lost outcome and report the acknowledge disposition — the row stays `pending` and will not be resolved by anything, which is the accepted accounting loss the spec records. A resolve refused by the fence is *not* retried: the successor owns the outcome.
- [ ] 4.5 Table-driven tests over fakes for: event before enrolment, disabled preference, a preference disabled and re-enabled before handling (delivered), no preference, `ClaimAlreadyResolved` acknowledged, `ClaimHeldByAnother` requeued, `2xx` on the first attempt, `5xx` on every attempt exhausting the budget, a policy refusal recorded with its reason, a `FindDeliverable` error producing the requeue disposition, a claim error producing the requeue disposition, a repository error while resolving producing the acknowledge disposition after its bounded retries, and a fenced resolve acknowledged without retry. Assert the delivery id is identical across attempts.
- [ ] 4.6 A test asserting the log output of a full delivery contains neither the secret nor the request body.

## 5. `cmd/notifier`, the image, and compose

- [ ] 5.1 `cmd/notifier/main.go`: `run(ctx)` under `signal.NotifyContext(SIGINT, SIGTERM)`, following `cmd/worker/main.go`'s shape. Load the Notification DSN and `RABBITMQ_URL` first, before any I/O, and fail fast naming a missing one. Load the delivery configuration and run 4.4a-i's validator here too — a reclaim bound below twice the attempt budget is a startup failure naming both values, not a warning. Open the pool, `Migrate`, ping.
- [ ] 5.2 The handler: decode by event type, build the domain `TerminalEvent` (translating the message's `user_id` into the context's own `UserID` here, which is the sanctioned crossing), call the use case, map its result to a disposition. An undecodable body and an unrecognized event type `Reject`; any pre-attempt repository failure — `FindDeliverable` or the claim — and a claim held by another consumer `Requeue`; everything else, including a claim refused as already resolved and an unrecordable outcome, `Ack`.
- [ ] 5.3 Shutdown: stop consuming, join the consumer so the in-flight delivery reaches a disposition under a bounded drain, then close the pool. The handler runs on `context.WithoutCancel`, so a signal never aborts an outbound request or prevents an outcome being recorded.
- [ ] 5.4 `Dockerfile`: build `/app/notifier` in the `builder` stage and copy it into `runtime` alongside the other two. No new port, no new package.
- [ ] 5.5 `docker-compose.yml`: a `notifier` service on the same image with `command: ["/app/notifier"]`, carrying `NOTIFICATION_POSTGRES_DSN`, `RABBITMQ_URL`, and the destination-policy relaxation set for local development. `depends_on` postgres and rabbitmq, and neither minio nor redis — it uses neither. Comment why the relaxation is set here and must not be set in production.
- [ ] 5.6 `cmd/notifier/main_test.go`: the composition root's own tests, following `cmd/worker`'s — a missing variable is fatal, the disposition mapping is exhaustive over the handler's inputs, and shutdown joins before closing.

## 6. `cmd/api`: the write-time half of the destination policy

- [ ] 6.1 `setupNotification` loads the policy from the environment and passes it into `SetPreference`, so the route refuses a destination the notifier could never dial. The variable name and default are the notifier's — one policy, two readers.
- [ ] 6.2 `SetPreference` applies the policy after `NewDestination` and surfaces a refusal as the same `400` any other validation failure produces. The response says the destination was refused; it does not enumerate which rule caught it.
- [ ] 6.3 `cmd/api/notification_test.go` grows: an `http` destination and a private-address destination are both `400` under the default policy and both accepted with the relaxation set, and a preference stored before the policy existed is neither migrated nor deleted.
- [ ] 6.4 `docker-compose.yml`'s `app` and `app-test` services carry the same relaxation the `notifier` service does — without it the existing tests that register an `http` destination would start failing for a reason unrelated to what they test.
