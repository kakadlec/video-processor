## Why

`cmd/worker`'s handler has **no retry disposition at all**. `internal/video/infrastructure/messaging.Disposition` has exactly two values, `Ack` and `Reject` (`consumer.go:53-67`), and `handle`'s doc comment states the rule deliberately: *"Requeueing is never right — the job's row is past `queued` in most of these cases, so a redelivery could only lose the claim and loop"* (`cmd/worker/main.go:368-376`). For the conditions that comment was written for — an undecodable body, a message naming no source object, an unknown job, a lost claim, a terminal write refused by the fence — it is right. Each names a condition a redelivery cannot improve.

**"In most of these cases" is the whole finding.** The `case err != nil` default branch (`cmd/worker/main.go:424-433`) catches every *other* error the pipeline can produce, and a dependency that is merely down is one of them. Three modes, each verified in the tree rather than assumed, and only one of them ends with nothing able to recover the job:

- **PostgreSQL unreachable *before* the claim.** `StartProcessing` propagates `FindByID`'s and `ClaimForProcessing`'s errors unchanged (`internal/video/application/start_processing.go:44-47`, `:73-76`) — a transport failure is neither `ErrJobClaimLost` nor `ErrVideoJobNotFound`, so it falls to the default branch and is dead-lettered while the row is still `queued`. The sweeper scans `processing` rows alone (`internal/video/infrastructure/postgres/repository.go:679-690`, `WHERE status = $1`; `cmd/worker/sweeper.go:91-97`), and `videojob-lease-recovery` states as a scenario that *"Jobs stranded in queued are not the sweeper's concern"*. **Nothing recovers it.** The row, its `content_hash` and its source object all survive and `GET /api/video-jobs/:id` keeps answering `queued` forever; what is destroyed is the only thing that would have advanced it.
- **PostgreSQL unreachable *after* the claim**, including a `failWith` whose own terminal write cannot commit (`internal/video/application/process_video_job.go:374-379`). Same branch, same dead-letter, but the row is left `processing` and the sweeper recovers it unaided — two missing-lease confirmations, a requeue at a fresh epoch, `failed` at `maxRequeues`. The handler's own comment already says so (`cmd/worker/main.go:425-429`). The cost is dead-letter churn, a delay bounded by the sweep, and one of three requeues spent. **Not a defect.**
- **MinIO unreachable, PostgreSQL up.** No message is dead-lettered at all. `sources.Get` and `results.Put` failures reach `failWith` (`process_video_job.go:287`, `:293`, `:325`), which commits the job `failed` and returns an *unsuccessful result* rather than an error, so the handler takes the `!result.Success` branch (`cmd/worker/main.go:439-452`), runs its one-shot cleanup and **acks**. The outcome is recorded. There is a real defect here and it is a different one — see the non-goal below.

**And the system already disagrees with itself about this.** `cmd/notifier`, built one change later against the same broker, reacts to the identical class of failure in the opposite way: a pre-attempt repository failure — `FindDeliverable`'s included — becomes `DeliveryDeferred` (`internal/notification/application/deliver_notification.go:99-106`) and the consumer `Requeue`s it (`cmd/notifier/main.go:399-414`), accepting head-of-line blocking and losing nothing. Its rule is *whether this handler has attempted anything yet*. Neither `CLAUDE.md` nor `docs/` records that the two consumers hold different rules, let alone why.

And dead-lettering is not archiving. The dead-letter queue is bounded at `deadLetterMaxLength = 10000` with `x-overflow: drop-head` and carries `deadLetterTTL = 24h` (`internal/video/infrastructure/messaging/topology.go:57-59`, `internal/platform/rabbitmq/topology.go:98-103`), and it is shared, unversioned, by both topologies and every generation. A stranded job's only remaining record therefore **expires or is dropped**. On a long enough outage, or a noisy enough queue, "stranded and recoverable by hand" becomes "lost".

## What Changes

- **One new disposition, on exactly one positively-identified condition.** `videomessaging.Disposition` gains a third value, `Requeue` — the same three-valued shape `cmd/notifier` already has, so the two consumers stop disagreeing. It applies to one condition and no other: **the claim step could not reach the database**, so this worker did not decide the claim and has mutated nothing.
- **The discriminator is the claim, not the error's type.** Not "transport versus logical", which would mean classifying driver error values; not "any error", which would requeue post-claim failures the sweeper already owns. The claim is a single atomic, observable boundary. Before it the row is `queued`, no lease exists, no source object has been read and no `ffmpeg` has run — so a redelivery is exactly as safe as the original delivery, because as far as the system is concerned it *is* the original delivery. After it, the existing "never requeue" rule is right and is kept verbatim.
- **The condition is carried by a sentinel, raised at one site.** `internal/video/infrastructure/postgres.Repository` wraps *driver-level* failures — the database could not be reached, the statement did not return — in a new `domain.ErrRepositoryUnavailable`, distinct from a row it *did* read and could not interpret (`scanJobRow`'s `RestoreVideoJob` and value-object parse failures) and distinct from `ErrVideoJobNotFound`, which `sql.ErrNoRows` is mapped to *before* any wrapping. `ProcessVideoJob.Execute` then converts that one error, at the one place it propagates the claim step's error, into a second sentinel meaning *the claim was not decided* — so the handler branches on a fact about control flow rather than on an error's text.
- **The requeue is paced, on the consumer's cancellable context.** `Nack(requeue=true)` on a classic queue returns the message toward the front of the queue and it is offered again immediately; without a pause the worker spins. The consumer pauses before taking the next delivery, exactly as `notificationmessaging.Consumer` does (`consumer.go:297-315`), for a pause passed in by the composition root and defaulting to the notifier's own five seconds.
- **Unbounded rather than counted.** Classic queues carry no delivery count, and the only bound RabbitMQ offers — `x-delivery-limit` — is a quorum-queue feature that would require changing the queue's type, which RabbitMQ refuses on redeclare and which would therefore mean a `.v3` generation bump. What that bound would buy is dead-lettering the message again, which is the outcome being fixed. The pacing is the bound that matters, and its arithmetic across three replicas is stated rather than left to be derived.
- **The four existing sentinels are untouched.** An undecodable body, a missing source key, an unknown job, a lost claim and a fenced terminal write keep dead-lettering, unchanged and for their existing reasons.

## Capabilities

### Modified Capabilities

- `videojob-worker`: the requirement *"A Message the Worker Cannot Act On Is Dead-Lettered, Never Requeued and Never Acked Away"* keeps its header and its rule, narrowed to the conditions under which the worker genuinely *cannot act* — which is what its own text already enumerates — with the previously-implicit "and everything else" made explicit and moved out. A new sibling requirement states the retry disposition: when it applies, the single fact that licenses it, the pacing and its arithmetic across replicas, and what it costs.
- `videojob-execution`: `ProcessVideoJob` propagates a claim the persistence layer could not decide as its own sentinel, alongside the lost claim it already propagates unchanged — without calling `FailJob`, downloading the source, or touching anything. The two are distinct on purpose: a lost claim means another actor owns the job, an undecided claim means nobody does.
- `videojob-persistence`: a new requirement. The repository distinguishes *the database could not be reached* from *a row was read and could not be interpreted*, and the cache decorator passes the distinction through rather than masking it. Only one caller currently branches on it; the contract is stated for the whole repository so a reader can tell which errors carry it.
- `videojob-lease-recovery`: two clarifying narrowings inside *"A Sweeper Returns Abandoned Jobs to the Queue"*. Its *"Recovery SHALL NOT be built on broker redelivery"* clause stays true and gains the distinction a reviewer will otherwise read it as contradicting — a redelivery of a dispatch that was *never acted on* is not recovery of an abandoned job. And its *"Jobs stranded in queued are not the sweeper's concern"* scenario stays, with its "or was dead-lettered" clause narrowed to the cases that still produce one.

## Impact

- **Changed**: `internal/video/domain` (two sentinels), `internal/video/infrastructure/postgres/repository.go` (wrap driver failures), `internal/video/infrastructure/cache/repository.go` (verify pass-through; likely no change), `internal/video/application/process_video_job.go` (one conversion at the claim-step propagation), `internal/video/infrastructure/messaging/consumer.go` (a third `Disposition`, a `requeuePause` constructor parameter, the nack-and-pause branch), `cmd/worker/main.go` (one new case in `handle`, the doc comment that states the rule, the constructor call). Tests in each.
- **One constructor signature changes.** `videomessaging.NewConsumer` gains a `requeuePause time.Duration` parameter, matching `notificationmessaging.NewConsumer`'s shape and for its stated reason: a pause read from inside could only ever be exercised at its production value.
- **No route, response, database statement, published message, topology, or shutdown sequence changes.** No new dependency; `go.mod` and `go.sum` stay byte-identical.
- **Accepted cost — head-of-line blocking, unbounded in duration, at prefetch 1 across three replicas.** This is the notifier's accepted cost without the notifier's bound, and what makes it acceptable here is not the notifier's reason: it is that the requeue path is entered *only* when the dependency every message on that queue needs is unavailable. There is no work the worker could be doing instead, so head and tail are blocked equally and blocking the head costs nothing. Making that true is precisely what the narrow discriminator buys — a broader rule would let one permanently-unreadable row block all three replicas forever.
- **A second accepted cost — the retry is unbounded in count.** A PostgreSQL outage lasting a week keeps the dispatch on the queue for a week, paced. The work queue is bounded at `jobsMaxLength = 10000` with `reject-publish`, so a sufficiently long outage surfaces as the relay's publishes being nacked and the backlog waiting in `video_job_outbox` — where it is durable and correct, and where an outage of the same database has already stopped new jobs being created at all.
- **A third — a redelivery costs one failed `FindByID` per pass.** Against an unreachable database that is a connection failure rather than a round trip, and it is paced; against a database that is up, the path is not entered at all.
- **A non-goal that is structurally unfixable here, stated so it is not mistaken for an oversight.** A *transient* MinIO outage permanently failing every job that touches it is real and cannot be fixed at the disposition layer at any price: by the time `handle` sees `!result.Success` the row is already committed `failed`, so a requeue could only be redelivered into `ErrJobClaimLost` and dead-lettered. Fixing it means a storage failure must not commit a terminal state — a `videojob-lifecycle` change introducing a worker-driven `processing → queued` edge that today only the sweeper may write, interacting with the fence, the lease and the `Applied` cleanup gate. That is its own change. The existing mitigation is real and was verified: a committed failure clears the job's idempotency key (`cmd/worker/main.go:445-451`), so the user's re-upload is not deduplicated onto the failed job. A backlog row is proposed at finalization.
- **Also not in scope**: extending the sweeper to `queued` rows, a delayed-retry queue, a quorum-queue migration, a documented dead-letter replay procedure as the *fix*, and any change to what the existing sentinels do. `design.md` rejects each with reasons.
- **Dependencies**: `migrate-upload-to-async-processing` (archived) — the disposition table this corrects.
