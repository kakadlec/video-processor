## Why

Phase 8 has one change left and this is it (`docs/roadmap.md`). `add-structured-logging` made every event legible and `add-health-and-readiness-endpoints` made every HTTP process answerable. Neither made anything **countable**, and the gap between those is where this system currently has no answers at all.

**Nothing aggregates the records.** They are JSON on standard output (`internal/platform/logging/logging.go:34`) and the compose stack holds no collector — `postgres`, `redis`, `minio`, `rabbitmq`, `gateway`, three APIs, three workers, a notifier, a mail catcher, `app-test`, and nothing else. So "what fraction of uploads were rejected in the last hour", "is the rate limiter currently enforcing anything", "how long does an extraction take" are all *derivable in principle* from records that exist and *unanswerable in practice*, by anyone, today.

**Three features are specified to fail open, and failing open is the state that most needs counting.** The rate limiter allows the request and logs a warning (`cmd/video-api/ratelimit.go:52-55`); `Reserve` proceeds without a reservation and logs a warning (`cmd/video-api/video.go:670-676`); the status cache degrades to PostgreSQL. Each emits one record per occurrence, which is the wrong shape for the question: a per-request warning at load is a flood nobody reads, and "abuse control has been off for forty minutes" is a *total*, not an event. `rate-limiting`'s own specification calls the degradation a loss of enforcement rather than of efficiency. Nothing reports that it is happening.

**And the two processes that do the work emit nothing when idle.** This is not inferred — `docs/operations.md:751` says it, as the accepted cost of the change archived beside this one: "an idle-but-wedged worker is indistinguishable from an idle-and-healthy one", and the same for the notifier. What an operator has instead is "indirect and lagging", and the same paragraph names where the gap gets closed: "Metrics are where that gap is closed if it is closed, and closing it is not a reason to give either process a port."

That sentence is this change's hardest constraint and its most useful one. It rules out the obvious answer and leaves a better question: *what can be counted about the worker by a process that is allowed to serve?*

## What Changes

- **`GET /metrics` on the three HTTP services, and on nothing else.** Prometheus text exposition, unauthenticated, registered on the engine beside `/`, `/health` and `/ready` — outside `requireBearerAuth()` and outside `rateLimitMiddleware`, for the three reasons `service-health-probes` already gives for the probes. **No new environment variable**: it is always served, at one format nothing selects, following `structured-logging`'s rule rather than inventing a toggle.
- **`cmd/worker` and `cmd/notifier` acquire no listener, and this is settled rather than decided here.** `service-health-probes` (`openspec/specs/service-health-probes/spec.md:17`) already requires that they "SHALL acquire no HTTP surface **for this or any other observability purpose**" — wording chosen to reach exactly this change — and `container-image` (`:55`) requires each to expose no port at all, pinned further by an in-package source test in each. A **Pushgateway** was the alternative and is rejected on this deployment's own shape, not on taste: `docker-compose.yml` runs three worker replicas and `instance` is `<hostname>-<pid>-<counter>` resolved per construction, so every restart of every replica would leave a metric group behind on the gateway forever; it is also a single point of failure and it destroys the up/down signal that is the only thing a scrape gives for free.
- **The worker's and the notifier's blind spot is narrowed from the outside, by the service that is allowed to serve, out of the database that service already holds.** `video_job_outbox` is one table shared by both relays, filtered on `event_type` (`internal/video/infrastructure/postgres/schema.sql:76-94`), so **`cmd/video-api` can see the backlog of the terminal relay that lives inside `cmd/worker`**. And a wedged worker shows as jobs that are `queued` and ageing. Four gauges, collected on scrape:

  | Gauge | Answers |
  |---|---|
  | `fiapx_video_jobs_in_state{state}` (`queued`, `processing`) | how much work is in flight |
  | `fiapx_video_jobs_oldest_in_state_age_seconds{state}` | **whether anything is moving** — the one number that says "uploads are being accepted and nothing is consuming them" |
  | `fiapx_video_job_outbox_unpublished{event_type}` | how much is committed and unannounced, per relay |
  | `fiapx_video_job_outbox_oldest_unpublished_age_seconds{event_type}` | whether a relay has stopped, including the one in the worker |

  The two outbox queries are served by an index that already exists. **Neither `video_jobs` query is, and that is the schema change this takes: two partial indexes, `(created_at) WHERE status = 'queued'` and `(created_at) WHERE status = 'processing'`**, each shaped exactly like the `WHERE status = 'processing'` one beside them and justified by the same sentence that one carries. An earlier draft of this proposal claimed the `processing` half was free because an index for that predicate already exists. It is free for a *filter* and not for this: `video_jobs_processing_id_idx` is keyed by `id`, to match the recovery sweep's keyset cursor, so it can find the processing rows and cannot order them by `created_at` — the oldest-age lookup over it reads every one of them. Two questions, two key orders, and no single index answers both.
- **Four counters and one histogram, at sites the exposing process runs itself.** `fiapx_http_requests_total{method,route,status_class}` and `fiapx_http_request_duration_seconds{method,route}` in each root's access-log middleware, which already computes every input; `fiapx_rate_limit_decisions_total{decision}` — `allowed`/`denied`/**`failed_open`** — in the two roots that mount a limiter (`cmd/video-api` and `cmd/notification-api`; `cmd/identity-api` mounts none and has no `ratelimit.go` to instrument); `fiapx_upload_idempotency_reservations_total{outcome}` — `reserved`/`duplicate`/`conflict`/**`failed_open`**, four outcomes because the handler distinguishes four, the third being the `409` a request receives when a reservation it did not win never resolves within its bounded wait; `fiapx_job_status_cache_lookups_total{outcome}` — `hit`/`miss`/`error`. Plus the Go and process collectors, which are the only cheap way to see a goroutine leak or file-descriptor exhaustion.
- **No metric is added for something already answered.** A `login_attempts_total{outcome}` was considered and dropped: `POST /api/auth/login` with a `4xx` status class already is that number, and a second counter for one event is how two numbers that must agree stop agreeing.
- **Label cardinality gets a source-level rule, and it is stricter than logging's, on one axis, for a stated reason.** Three AST rules in `internal/platform/metrics/disclosure_test.go`, the file `structured-logging` established as where a rule of this kind belongs (placement is a separate question and takes the separate per-package `dependency_test.go` the platform convention requires — the disclosure walk judges call sites, not imports): every label **value** at a call site is a string literal or the result of one of two named total constructors, **with rejection as the default for any argument form the walk cannot resolve to one of those two** — a spread slice, a converted `prometheus.Labels` map and a computed key in a `Labels` literal are each a one-line bypass of a walk that enumerates the forms it knows instead; every metric **name**, help string and label-name list is a string literal; and `promauto`, `prometheus.DefaultRegisterer`/`DefaultGatherer` and the package-level `Register`/`MustRegister` are never named anywhere. The stricter axis is identifiers: `structured-logging` permits `job_id`, `user_id` and `delivery_id` **in a record**, and this capability forbids every one of them **in a label**, because a record is a line that ages out and a label value is a permanent series.
- **The two unavoidable variable labels — the HTTP route and its method — are bounded by the router itself.** `metrics.Route()`/`metrics.Method()` resolve against the route table each root reads from its own router at startup and collapse anything else to `<unmatched>`/`UNRECOGNIZED`. The table crosses into the shared package as **a route and a method per entry in a representation of ours**, not as the HTTP framework's own type: nothing under `internal/` imports that framework today and the platform namespace's dependency test says so in terms, so translating it in the root is what keeps the shared package free of it. The ceiling is then `(routes+1) × (methods+1)`, a number the build fixes. The access record truncates an unmatched path to 256 bytes; a metric **must not**, and the difference is the whole point: truncation bounds length, not cardinality, and 256 bytes of caller-supplied text arriving before authentication is still an unbounded series count.
- **The gateway refuses `/metrics`**, a third exact-match `location = /metrics { return 404; }` beside the two the probes already have, for the same reason and with the same requirement — status-code equivalence and non-arrival, not a byte-identical body.
- **`/metrics` is access-logged like any other route.** No `structured-logging` delta: the probe exemption's justification was volume from a prober arriving at a fixed interval forever, and **no scraper exists in this repository**, so arguing the same volume here would be arguing from a consumer that does not exist. If a scraper is added later, the change that adds it is the one that should revisit the exemption, with a real interval to put in the arithmetic.
- **One new dependency, and it is the first in several changes.** `add-structured-logging` cost nothing in `go.mod`; this costs one direct module and five new indirect ones. Measured, not asserted — see Impact.
- **Not in scope**: a Prometheus server in the compose stack (see below — this is the one decision flagged for the user), alerting rules, dashboards, tracing, exemplars, native histograms, any metric recorded by `cmd/worker` or `cmd/notifier` at a site only those processes run, and any change to what startup verifies, to a route's behaviour, or to a probe's verdict.

## Capabilities

### New Capabilities
- `service-metrics`: which processes expose a metrics endpoint and which are answered with *none*, deriving the second from `service-health-probes`'s existing prohibition rather than restating it as a preference; that the endpoint is unauthenticated, gateway-refused, and configured by nothing; the label rule and why it is stricter than the logging rule it is modelled on — no identifier in a label, ever, and two bounded variable labels — the matched route and the request method — whose common domain is the router's own route table, handed to the shared package in a representation of ours rather than the HTTP framework's; that a metric family is declared where it is recorded and registered in one process-wide registry, never in the client library's default one; which families exist and what each one is for, with the standing rule that a metric nobody would act on is not added; that a collected gauge queries on scrape, never reports a cached value, reports a failed collection to the scraper as an error rather than as a number, and — the same rule read the other way — always reports a successful empty collection as a zero rather than as an absence; and what an unauthenticated `/metrics` still discloses once every label is bounded, stated rather than glossed.

### Modified Capabilities
- `videojob-persistence`: one **added** requirement rather than a modification — the repository gains bounded, index-served aggregates of in-flight work (a saturating count and an unsaturating oldest-age, per state and per unpublished `event_type`, each reported for every member of its closed label set so that an empty state is a zero rather than a silence) and the two partial indexes that serve the `video_jobs` half. It belongs here rather than in `service-metrics` because it is a statement about a query and an index, and `service-metrics` should not specify SQL. The requirement carries the reason the count saturates and the age does not.

## Impact

- **Changed**: `cmd/identity-api`, `cmd/video-api`, `cmd/notification-api` — one new file each (`metrics.go`: the families, the middleware hook and the handler), plus `setupRouter`, `main`, and the access-log middleware in each. `cmd/video-api/video.go` (one counter on the four reservation paths) and `ratelimit.go` in the **two** roots that have one — `cmd/video-api` and `cmd/notification-api` — on three branches each. `internal/video/infrastructure/cache` (one counter). `internal/video/infrastructure/postgres` (two aggregate queries as methods on the concrete `Repository` rather than on the domain port, **two** new partial indexes in `schema.sql`, and one `prometheus.Collector` over that repository undecorated). New: `internal/platform/metrics` (registry, handler, the two label constructors, the framework-neutral route-table binding, the three-rule AST walk, and its own per-package dependency test — the walk is the disclosure rule and does not enforce placement). `docker/nginx/nginx.conf` (one refusal block).
- **The dependency, measured rather than asserted.** Resolving `github.com/prometheus/client_golang` (v1.24.1) against a bare `go 1.27.0` module yields **one direct module and seven indirect**, of which **two are already in this repository's `go.mod`** — `github.com/cespare/xxhash/v2 v2.3.0` and `golang.org/x/sys v0.47.0` — and one, `google.golang.org/protobuf`, is present at `v1.36.10` and would move to `v1.36.11`. The genuinely new modules are five: `beorn7/perks`, `munnerz/goautoneg`, `prometheus/client_model`, `prometheus/common`, `prometheus/procfs`. `govulncheck` on that resolution reports no vulnerabilities today, which is a statement about today and not about the surface: five more modules is five more things a future advisory can name, and `Vulnerability Scan (govulncheck)` is a required check.
- **Binary size, honestly bounded rather than quoted.** A trivial `net/http` program grew from 5.73 MB to 13.83 MB when `prometheus` and `promhttp` were linked into it — but that number **overstates the real delta**, because this repository's binaries already link protobuf, xxhash and `x/sys`. The real figure is measured during implementation. The cost that does not shrink: the image carries **five statically linked binaries** (`container-image`), so whatever the per-binary increase is, it lands five times in one image — including in `cmd/worker` and `cmd/notifier`, which link the instrumented shared packages and serve no endpoint.
- **A query per scrape against the video database.** Four gauges, read per in-flight state and per relayed event type with the state written as a literal so the partial index is matched at all, every predicate index-served, every read bounded by a context timeout, and each count saturating at **10,000** — three orders of magnitude above any healthy value, since three workers at prefetch 1 make a healthy `processing` count three. Named because caching the values is the obvious mitigation and this capability refuses it for the reason `storage.Ping` already gave: an answer computed at a different moment from the one the caller asked about.
- **A gauge over shared state is reported per replica.** `docker-compose.yml` runs one `video-api`, so today there is one series per gauge. With more than one, Prometheus separates them by `instance` and the same fact appears N times — an operator must aggregate with `max by (state)` and not `sum`. Stated because it is invisible until the day someone scales that service and their queued-job count triples.
- **An unauthenticated endpoint that discloses more than a probe does, and there is only one control instead of two.** `/ready` had a gateway refusal *and* a body naming no dependency; `/metrics` has the refusal and a body that is, by construction, an inventory: every route template, every dependency's error rate, the Go toolchain version via `go_info`. That is accepted, not overlooked, and the reason is the one the readiness transition record already uses — the reader is inside the deployment. What is *not* accepted, and what the label rule makes structural, is any individual fact: no user, job, delivery, destination, storage key or content hash appears in any label, so nothing about one person or one job is derivable from the endpoint at all.
- **No behaviour changes on any existing route**, no status code, no response body, no database statement other than the two new read-only aggregates, no broker message, no shutdown sequence, no change to startup's fail-fast posture, and no new environment variable.
- **Already in this pull request, as documentation rather than an OpenSpec artifact**: one new `not-started` Change Backlog row in `docs/roadmap.md`, `expose-worker-and-notifier-metrics`, recording exactly what a later change would have to unpick to instrument the two non-HTTP processes directly — a `container-image` delta to "expose no port at all", a `service-health-probes` delta to "SHALL acquire no HTTP surface for this or any other observability purpose", and the two in-package source tests those pin. The row exists so the deferral is visible and costed rather than implied by this proposal's silence, and it is added **here** rather than deferred to the implementation pull request for exactly that reason: a gap recorded only in a proposal that is never implemented is not recorded at all, which would contradict the sentence justifying it. The precedent is one change old — `add-health-and-readiness-endpoints` added `fix-worker-dependency-outage-disposition` in its own propose pull request, not in the one that implemented it.
- **One decision is flagged for the user rather than taken.** Whether the local stack gains a **Prometheus server**. This proposal's default is **no**, following `/health`'s precedent — that change shipped an endpoint whose consumer in this repository is nothing at all, and defended it — and because adding one is not free in specification terms: `container-image:55` says a development-only support service publishing its own loopback port is permitted and that the mail catcher "is the only one", so a second such service needs a delta to that sentence. If the user wants the stack to scrape itself, it is a small second change (`add-local-metrics-scraper`) with that delta, a `prometheus.yml` naming five targets — of which two would have nothing to scrape — and a loopback-bound port. It is not folded in here, because the argument for it is about the local stack and not about what the application exposes.
- **Dependencies**: `add-structured-logging` (archived) for sequencing and for the AST-walk idiom this reuses; `add-health-and-readiness-endpoints` (archived) for the endpoint placement, the gateway refusal idiom, and the prohibition this change is bound by rather than free to revisit.
