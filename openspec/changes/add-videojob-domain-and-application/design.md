## Context

`internal/identity/{domain,application,infrastructure}` (Phase 2) is the only precedent for this repository's package shape: domain packages hold aggregates, value objects, and port interfaces; application packages hold use cases that depend only on those ports; infrastructure implements the ports; `internal/<context>/dependency_rules_test.go` statically enforces the import boundaries via `go/parser`. This change follows that shape exactly for a second bounded context, `video`.

`openspec/specs/ddd-architecture/spec.md` (Phase 1, canonical) already specifies `VideoJob`'s target shape — aggregate invariants, the five-state machine, and the package dependency rules — and `openspec/specs/video-processing-access/spec.md` (Phase 2) already requires the existing (pre-DDD) Video Processing HTTP surface to consume only an opaque `UserID`, without importing Identity's domain or application packages. Both predate this change but constrain it.

## Goals / Non-Goals

**Goals:**
- `internal/video/domain`: `VideoJob` aggregate root; value objects `VideoJobID`, `OriginalFilename`, `StorageKey`, `FrameCount`, `ErrorReason`; `JobStatus` enum (all five states) with a pure transition-validation function; a context-local `UserID` value object.
- `internal/video/domain`: `VideoJobRepository` port (`Create`, `FindByID`, `FindByUserID` with offset/limit pagination).
- `internal/video/application`: `CreateVideoJob`, `GetJobStatus`, `ListUserJobs` use cases, each unit-testable against an in-memory fake repository (mirroring `internal/identity/application`'s `fakeUserRepository`).
- `internal/video/dependency_rules_test.go`, mirroring `internal/identity/dependency_rules_test.go`.
- A `MODIFIED` delta to `ddd-architecture`'s "No direct cross-context domain imports" scenario, replacing its `pkg/`-shared-kernel wording with the context-local-`UserID`-plus-translation model this change actually implements.

**Non-Goals:**
- PostgreSQL adapter, `video_jobs`/`outbox` schema or migration — `add-videojob-infrastructure`.
- Any HTTP route, `cmd/api`, or change to `main.go` — `extract-cmd-api-entrypoint` and `wire-videojob-http-endpoints`.
- `EnqueueVideoJob`, `StartProcessing`, `CompleteJob`, `FailJob` — no use case in this change triggers a state transition, so none of these are implemented as domain methods or use cases yet. All four are added together by `migrate-ffmpeg-execution-to-videojob-application` (still Phase 3), which calls them synchronously in-process; `docs/roadmap.md` documents why they can't be split (`completed`/`failed` require `processing`, itself reachable only via `queued`, so a synchronous path needs all four, not just the last two).
- Domain events (`VideoJobCreated`, `VideoJobCompleted`, etc.) — no consumer exists yet. Mirrors Identity's Phase 2 precedent (`RegisterUser`/`AuthenticateUser` emit nothing either, per `docs/domain-model.md`); `ddd-architecture`'s "Domain Events as Cross-Context Integration Contracts" requirement only binds `VideoJobCompleted`/`VideoJobFailed`, both unreachable from this change's use cases.
- A shared `pkg/` package of any kind — see Decisions.

## Decisions

- **Context-local `UserID`, no shared `pkg/` kernel.** `internal/video/domain` defines its own `UserID` value object — distinct Go type from `internal/identity/domain.UserID` — with a validating constructor (non-empty) but no generator, since Video Processing never mints a `UserID`, only receives one already verified by the Identity context's bearer-auth middleware. Translation between the two contexts' `UserID` types happens at the composition root (today: `main.go`'s auth middleware boundary; later: `cmd/api`), the one place already responsible for knowing about both contexts.
  *Alternative considered:* a shared `pkg/userid` (or similar) package, as `ddd-architecture`'s current text and `docs/domain-model.md`'s "Cross-Context Contracts" note both anticipated. Rejected: a shared kernel is, by definition, compile-time coupling between two contexts whose independence is the architecture's stated reason for existing — Vernon (*IDDD*) treats it as an exception reserved for contexts under tight, coordinated ownership, not a default. It was also never implemented (`pkg/` does not exist in the repo today), and the already-shipped `video-processing-access` spec already commits to the opposite: "Video Processing SHALL consume an authenticated opaque `UserID`... and SHALL NOT import Identity domain or application packages." A shared type either violates that scenario's spirit or requires `UserID` to live outside both contexts' `domain` packages in a way neither existing spec actually describes. Local types with edge translation cost roughly 15 lines and keep both specs consistent with each other.

- **`JobStatus`: enum plus a pure transition-validator, no mutator methods yet.** `JobStatus` covers all five states (`pending`, `queued`, `processing`, `completed`, `failed`) and a `func (s JobStatus) CanTransitionTo(next JobStatus) bool` (or equivalent) encodes the valid-transitions table from `ddd-architecture`'s "Valid State Machine Transitions Only" requirement, independently testable. `VideoJob` itself only exposes creation (always `pending`) in this change — no `Enqueue()`/`StartProcessing()`/`Complete()`/`Fail()` methods, since nothing in `CreateVideoJob`, `GetJobStatus`, or `ListUserJobs` would call them.
  *Alternative considered:* implement the full set of transition methods now so Phase 6 (and `migrate-ffmpeg-execution-to-videojob-application`) can "just call them." Rejected as speculative: those methods would ship untested by any real caller and violate this project's explicit convention against building for hypothetical future requirements. The transition-validity table is cheap to add now (it's what the aggregate's invariants require regardless of which methods call it) and de-risks the later change that does add the mutator methods, since the transition rules will already be specified and tested.

- **`VideoJobID` mirrors `UserID`'s generator/parser port split; this context's local `UserID` deliberately does not.** A `VideoJobIDGenerator` port mints new IDs (used by `CreateVideoJob`, exactly like `UserIDGenerator` in `RegisterUser`). A `VideoJobIDParser` port validates/parses an externally-supplied ID string into a `VideoJobID` (used by `GetJobStatus`, which receives a raw ID string from its caller) — same reasoning as `identity/domain.UserIDParser`: the domain enforces only its own non-empty invariant, and infrastructure supplies the concrete scheme (UUID v4, via `github.com/google/uuid`, already a dependency), which will eventually need to reject malformed input before it reaches a `uuid`-typed PostgreSQL column. This context's own `UserID` gets neither port: it always arrives pre-verified from the Identity context's bearer-auth middleware (never minted here, never parsed from untrusted input here), so a plain validating constructor is sufficient — the asymmetry reflects where each ID actually originates, not an inconsistency.

- **Ownership mismatch and "not found" are the same error.** `GetJobStatus` fetches by `VideoJobID` and then compares the job's `UserID` against the caller's; on mismatch it returns the same `ErrVideoJobNotFound` used for a genuinely missing ID, never a distinct "forbidden" error. This mirrors the existing convention in `main.go`'s `requireArtifactOwnership` (returns `404` for both a missing artifact and one owned by someone else, to avoid confirming another user's artifact exists) and keeps the new use case consistent with the access-control posture `video-processing-access` already establishes for the legacy HTTP surface.

- **`ListUserJobs` pagination: offset/limit.** `VideoJobRepository.FindByUserID(ctx, userID, offset, limit int)`. Cursor-based pagination would give consistency guarantees under concurrent writes, but is unnecessary complexity for this project's scale (a hackathon deliverable) and not required by `docs/domain-model.md`'s "returns paginated list" wording, which does not mandate a specific pagination style.

## Risks / Trade-offs

- [The `ddd-architecture` spec correction (removing `pkg/`) is a change to already-canonical (Phase 1, "Done") text, not just this change's own scope] → the delta is narrow (one scenario's `GIVEN`/wording), and is required for the domain model this change actually ships to be spec-compliant; leaving the stale `pkg/` wording in place would make the canonical spec describe an architecture nobody is building.
- [Deferring all four transition use cases here means `migrate-ffmpeg-execution-to-videojob-application` must add all of them at once, coupling that change's scope to a decision made here] → already reflected in `docs/roadmap.md`'s Phase 3 Change Backlog (updated separately, PR #112), including the correction that they can't be split 2-and-2 with Phase 6, so the dependency is explicit and won't surprise whoever proposes that change.
- [A second, independent `UserID` type could drift from Identity's if either context's validation rules change] → both are intentionally minimal (non-empty string wrapper); any richer validation belongs to the ID *scheme* (UUID v4), which both contexts get from the same `github.com/google/uuid` library independently, not from sharing a type.

## Migration Plan

Single, additive PR: new `internal/video/domain` and `internal/video/application` packages, new `internal/video/dependency_rules_test.go`, plus the `ddd-architecture` spec delta. No existing file is modified outside `openspec/`. No data migration (no persistence yet). Rollback is a normal `git revert` — nothing runtime-visible depends on this code existing.
