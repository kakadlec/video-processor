## Why

`migrate-result-storage-to-minio` moved processed results into the bucket and deleted the `.owner` sidecar mechanism for them — but only for them. Uploaded source videos still land in `uploads/` on the container's local filesystem, and the entire sidecar apparatus (`recordArtifactOwner`, `artifactOwner`, `removeArtifactOwner`, `rejectOwnerSidecarRequests`, `requireArtifactOwnership`, `artifactOwnerSuffix`) survives to serve that one directory and the `/uploads` static mount in front of it. `videojob-result-storage`'s spec says so explicitly: "The sidecar helpers themselves SHALL remain in the codebase for the `uploads/` directory, which still uses them."

The stronger reason is not where the bytes rest, it is the seam. `ProcessVideoJob.Execute(ctx, jobID, videoPath)` takes a **local filesystem path written by the HTTP handler that called it**. Phase 6 runs extraction in `cmd/worker`, a separate process that does not share a filesystem with `cmd/api`; that signature cannot survive it. Replacing the path with a storage key is the change that makes the use case addressable from anywhere, and it is testable now, synchronously, before a queue exists to complicate it.

This change also closes a gap the specs have carried since Phase 1. `video-frame-extraction`'s "Uploaded File Retained On Processing Failure" requirement documents that a failed run leaks its upload forever, and describes itself as waiting for "the planned refactor". This is that refactor.

## What Changes

- Add a `SourceStorage` port to `internal/video/domain` (`Put`/`Get`/`Delete`) and its MinIO-backed adapter to `internal/video/infrastructure/storage`, alongside the existing `ResultStorage`. Both share one bucket and one client; sources take an `uploads/` key prefix, results keep their flat `frames_<jobID>.zip` keys.
- `POST /upload` streams the multipart part straight into the bucket under `uploads/<uploadID>_<original-filename>`, hashing it with SHA-256 on the same pass exactly as it does today. Nothing is written to the local filesystem before the object exists.
- `ProcessVideoJob.Execute` takes a **source storage key** instead of a local video path. It downloads the object to a transient local copy under `temp/`, hands that path to `FrameExtractor`, and owns the copy's lifetime — the `ffmpeg` adapter continues to know nothing about object storage, mirroring the split this project established for the result zip.
- The source object is **fully transient**: `ProcessVideoJob` deletes it on success *and* on failure, so a failed run leaves nothing behind in the bucket. This removes `video-frame-extraction`'s "Uploaded File Retained On Processing Failure" requirement rather than porting the leak into durable storage, where it would be worse: local disk at least gets reclaimed when a container is replaced.
- The duplicate-upload path keeps its shape but changes cost. The content hash is only known once the whole part has been read, so a duplicate's object is already written by the time `Reserve` reports the conflict; `cleanupRedundantUpload` becomes a `Delete` against the bucket instead of an `os.Remove`. This is a real regression on that path — one object write plus one delete where there used to be a local write plus unlink — and it is accepted rather than hidden: avoiding it would mean buffering the upload somewhere to hash before storing, which is the local file this change exists to remove.
- Pin an explicit `PartSize` on the upload. A `multipart.Part` does not report its length, so `PutObject` is called with size `-1`, which routes into `putObjectMultipartStreamNoLength` → `OptimalPartInfo(-1, 0)` → `buf := make([]byte, partSize)`. Verified against the pinned `minio-go v7.3.0` source, whose own comment reads: *"When object size is unknown (-1), default to 5TiB to limit memory usage. This results in ~537MiB part sizes."* With a synchronous, unbounded-concurrency pipeline, N simultaneous uploads would allocate N × ~537 MiB. An explicit part size bounds that per-upload buffer and still permits objects far larger than this service will ever accept.
- Retire `uploads/` entirely: `createDirs` creates only `temp/`, the `Dockerfile` stops pre-creating the directory, and the `app` service drops its `./uploads` bind mount.
- Delete the `.owner` sidecar mechanism in full — all six symbols, their middleware registrations, and their tests. Nothing in the codebase uses ownership sidecars after this change.
- **BREAKING**: the `/uploads` static mount is removed. An authenticated owner can no longer retrieve their own source video over HTTP; the route returns `404` because it no longer exists. `cmd/api/web/app.js` never referenced it (it calls only `/upload`, `/download/`, and `/api/status`), so the bundled frontend is unaffected — but any external client that fetched a source video back loses that capability with no replacement, and `rate-limiting`'s enumeration of limited routes stops naming it.

## Capabilities

### New Capabilities

- `videojob-source-storage`: the `SourceStorage` domain port and its MinIO adapter — source key derivation under the `uploads/` prefix, the streamed upload with its bounded part size, retrieval into a transient local copy for `ffmpeg`, deletion, and the transient-lifetime contract that guarantees no source object outlives its request.

### Modified Capabilities

- `video-frame-extraction`: the uploaded video's storage location changes from `uploads/` to the bucket, and its cleanup rule changes from "deleted on success only" to "deleted on success and failure". The "Uploaded File Retained On Processing Failure" requirement is **removed**, not amended — the behavior it documents ceases to exist.
- `videojob-execution`: `ProcessVideoJob.Execute`'s second parameter changes from a local video file path to a source `StorageKey`, and the use case gains the download step and ownership of the downloaded copy's lifetime. `FrameExtractor`'s own contract is untouched — it still takes a local path and knows nothing about storage.
- `upload-idempotency`: its key-derivation requirement specifies hashing "while it is streamed to `uploads/`", which stops being true; and its redundant-upload scenario describes the original request's artifacts as a file under `uploads/`.
- `rate-limiting`: its route enumeration names "the `/uploads` static mount", which this change removes.
- `container-image`: the runtime stage pre-creates `uploads/` and `temp/`; only `temp/` remains.
- `videojob-result-storage`: its "The outputs Directory And Its Ownership Sidecars Are Retired" requirement states that the sidecar helpers remain in the codebase for `uploads/`, carries a scenario asserting upload sidecars still work, and has a `createDirs` scenario asserting `uploads/` is created — all three stop being true. The requirement is amended rather than removed: its claims about the *result* artifact are unaffected.
Four capabilities were checked and deliberately **not** modified:

- `identity-authentication` — its "Users cannot access another user's artifacts" scenario is already written against "status or download" and never mentions the `/uploads` route, so removing that route leaves it true as written. Its requirement that ownership derive from the authenticated `UserID` rather than caller-controlled fields is likewise location-independent.

- `upload-file-validation` — its "A valid upload is unaffected" scenario says the file is "saved and hashed exactly as before" without naming a location, and its normative requirement constrains only what the handler may do *before* the extension is known valid. The fast-reject contract is preserved exactly: the extension check still runs against the part's filename before a single byte of payload is read, hashed, or stored.
- `ddd-architecture` — a second domain port implemented by a second adapter in the same infrastructure package is precisely the layering this capability already prescribes; no dependency rule changes.
- `videojob-persistence` — every other spec's use of `StorageKey` was checked and each is explicitly the *result* key: `ddd-architecture` writes "`StorageKey` for the result", and `videojob-persistence` and `videojob-lifecycle` reference it only through `CompleteJob`/`GetJobStatus`/`FindByID`, which deal in the completed job's result. Introducing a second key space into the `domain.StorageKey` type therefore falsifies nothing. Beyond that, the source key is a `ProcessVideoJob` parameter, not a field on the aggregate. Persisting it would only matter if a failed job's bytes had to be replayed, and this change makes source objects transient, so there is nothing to replay from. Phase 6's queue message is where a worker will receive the key, and that is where the question genuinely belongs.

## Impact

**Code.** `internal/video/domain` (new `SourceStorage` port, new source key derivation on `StorageKey`), `internal/video/application/process_video_job.go` (parameter change, download step, local-copy lifetime), `internal/video/infrastructure/storage` (new adapter), `cmd/api/video.go` (`handleVideoUpload` streams to the bucket instead of `os.Create`, `cleanupRedundantUpload` deletes an object, `setupVideo` wires the new port), `cmd/api/main.go` (`createDirs`, the `/uploads` route group, and all six sidecar symbols deleted).

**Tests.** `cmd/api/main_test.go` carries three tests built directly on the mechanisms being removed: `TestProcessing_Failure_LeavesUploadedFileBehind` asserts the leak this change fixes and must be **inverted**, not deleted; `TestProcessing_Failure_CleansTempDir` cleans up leftovers that will no longer exist; and `TestStaticUploads_NeverServesOwnerSidecarFiles` covers a route that ceases to exist. Bucket state replaces filesystem globs as the assertion surface for the upload path, and the new adapter needs its own suite against a real MinIO, following `result_storage_test.go`'s per-test-bucket pattern.

**Operations.** `docker-compose.yml`'s `app` service drops the `./uploads:/app/uploads` bind mount; `Dockerfile`'s `mkdir -p uploads temp` becomes `mkdir -p temp`. No new environment variable: the source objects share `VIDEO_MINIO_BUCKET` with results, so the four required `VIDEO_MINIO_*` variables and the fail-closed startup posture are unchanged. Operators lose the ability to inspect a failed upload on the host filesystem — by design, since failures no longer retain the source anywhere.

**Documentation.** `docs/operations.md` describes `uploads/` in its directory listing and lifecycle table and carries a "Known gap" callout for the retention leak this change closes; `docs/architecture.md` has `uploads/` in its request-flow diagram, its state table, its sidecar row, and its route table; `docs/flows.md`'s upload sequence saves to `uploads/` and its preamble names `/uploads/*` among authenticated routes; `README.md`'s limitations list still says uploaded videos live on local disk; `docs/development.md` says the server creates `uploads/` and `temp/`; `CLAUDE.md` describes the save target, the two startup directories, and the sidecar behavior. All are enumerated in the finalization tasks.

**Not in scope.** Presigned download URLs are `add-presigned-download-urls`. No queue, worker, or async execution — `POST /upload` stays synchronous and in-request, and the extra bucket round trip this change introduces (up, then back down) is the honest cost of that being temporary. The frontend is untouched: `app.js` keeps posting to `/upload` and reading `zip_path`.
