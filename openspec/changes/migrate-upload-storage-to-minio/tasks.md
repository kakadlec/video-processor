## 1. Domain: the source port and its key derivation

- [ ] 1.1 `internal/video/domain/source_storage.go`: define the `SourceStorage` port with `Put(ctx, key StorageKey, r io.Reader) error`, `Get(ctx, key StorageKey, localPath string) error`, and `Delete(ctx, key StorageKey) error`, plus `ErrSourceNotFound` and `ErrSourceStoreFailed`. Document on `Put` why it takes a reader while `ResultStorage.Put` takes a path (design.md decision 4): the source has no local existence at upload time, and requiring one would reintroduce the file this change removes. Document on `Delete` that an absent key is **not** an error — the handler's deferred cleanup runs on paths where the object may already be gone.
- [ ] 1.2 `internal/video/domain/storage_key.go`: add `SourceStorageKey(uploadID, originalFilename string) StorageKey` producing `uploads/<uploadID>_<base filename>`. Carry a comment recording the asymmetry with `ResultStorageKey` and *why the prefix is safe only here*: a result key becomes `GET /download/:filename`'s single path segment, so a `/` breaks the route match, while a source key never reaches a URL because this change deletes the `/uploads` route. The two facts are load-bearing together — a future change that re-exposes source objects over HTTP has to drop the prefix in the same commit.
- [ ] 1.2a Fix `StorageKey`'s **type-level** contract, which this change falsifies. `internal/video/domain/storage_key.go:12-13` reads "identifies where a VideoJob's result artifact is stored. It is only set once a job reaches completed; unset (zero value) otherwise" — false the moment source keys exist, since a source key is minted before the `VideoJob` and is never stored on the aggregate. Keep one type (both are opaque bucket keys, and a second type would ripple through both ports and the adapter for no invariant that is actually enforced at the type level), but move the completion invariant to where it belongs: the type doc says it identifies an object in the bucket, named by `ResultStorageKey` or `SourceStorageKey`; the "set only on completion" rule moves onto the `VideoJob`'s own `StorageKey` field, which is the thing that invariant was ever about.
- [ ] 1.3 `ErrSourceStoreFailed` exists for the same reason `ErrResultStoreFailed` does: the client's own error text names the endpoint and bucket, and that text must not reach a user-facing message or a persisted `ErrorReason`. Follow the established pattern rather than reinventing it.

## 2. Storage adapter

- [ ] 2.1 `internal/video/infrastructure/storage/source_storage.go`: `SourceStorage` struct over the existing `*minio.Client` and bucket name, a `New…` constructor, and `var _ domain.SourceStorage = (*SourceStorage)(nil)`. Same bucket as results — the key prefix is what separates the two spaces, and a second bucket would mean a fifth required env var for no behavioral gain (design.md decision 3).
- [ ] 2.2 `Put`: `client.PutObject(ctx, bucket, key.String(), r, -1, opts)` with an **explicit `PartSize`** in `opts`. Size is `-1` because a `multipart.Part` does not report its length; without a configured part size that routes into `putObjectMultipartStreamNoLength` → `OptimalPartInfo(-1, 0)` and allocates a single ~537 MiB buffer per upload (verified in the pinned `minio-go v7.3.0` source, whose own comment states it). Use 16 MiB — the library's `minPartSize`, well above the 5 MiB floor `OptimalPartInfo` enforces — which caps the object at `partSize × 10000` = 160 GiB and bounds the per-upload buffer. Put the reasoning in a comment; the number is otherwise unexplainable.
- [ ] 2.2a Already verified in the pinned source, so do not re-litigate it during implementation: an upload **smaller than the configured part size** is handled correctly. The no-length loop reads with `readFull` and explicitly tolerates a short read (`if rerr != nil && rerr != io.ErrUnexpectedEOF && rerr != io.EOF { return }`), uploading the partial buffer and breaking on the next iteration's `io.EOF`. This matters because every test video in this repo is far under 16 MiB, so that is the path the entire existing suite takes. The one real consequence is that a small object still goes through initiate/upload-part/complete rather than a single `PUT` — more round trips, no correctness impact. Task 6.2's larger-than-part-size case is what covers the genuinely multi-part path.
- [ ] 2.3 `Get`: `client.FGetObject` into the caller's path. Map a `NoSuchKey` response code to `ErrSourceNotFound`, wrap everything else — reuse the existing `wrap()`-style helper in this package rather than writing a second error mapper.
- [ ] 2.4 `Delete`: `client.RemoveObject`. Verify against the pinned stack whether removing an absent key returns an error; if it does, swallow that specific case so the contract in 1.1 holds. Record the observed behavior in a comment rather than asserting it from documentation — this is the same class of check that `GetObject`'s laziness turned out to need.

## 3. Application: ProcessVideoJob takes a key

- [ ] 3.1 `internal/video/application/process_video_job.go`: add a `domain.SourceStorage` dependency; change `Execute`'s second parameter from `videoPath string` to `sourceKey domain.StorageKey`.
- [ ] 3.2 After `StartProcessing` succeeds, build the local path as `temp/<jobID>_source` — beside the extractor's per-job frame directory, never inside it, so that directory's `defer os.RemoveAll` cannot delete a file it does not own. **No file extension**: `ffmpeg` probes content, and dropping the extension means no part of the path derives from a user-supplied filename (design.md decision 2). ## 4. Composition root: upload handler, router, and the sidecar removal

- [ ] 4.1 `cmd/api/video.go` `setupVideo`: construct the `SourceStorage` adapter from the client already opened for results, and extend `videoModule` and `newVideoModule` to carry it. No new configuration, no second `EnsureBucket`.
- [ ] 4.2 `handleVideoUpload`: replace `os.Create` + `io.Copy` with `SourceStorage.Put(ctx, sourceKey, io.TeeReader(part, hasher))`. Keep the hash on the same single pass. **The extension check stays strictly before any read of the payload** — `upload-file-validation`'s fast-reject is the behavior most easily broken by restructuring this handler, and it is asserted by a test that must keep passing.
- [ ] 4.3 On a `Put` failure, respond with the existing pt-BR save-error message shape. Do not surface the adapter's error text.
- [ ] 4.3a Log a cleanup failure with the source key and do **not** fail the request because of it — the response reflects the job's outcome, not housekeeping. The log line is what makes the residual leak enumerable; without it a failed delete is invisible (design.md decision 6a).
- [ ] 4.4 Register **one** `defer` immediately after a successful `Put` that deletes the source object on a detached `NewFinalizationContext`. That single construct covers every later exit — idempotency conflict, `CreateVideoJob` error, `ProcessVideoJob` error, processing failure, success, and panic. Do not scatter per-path delete calls; split cleanup ownership is how the leak this change closes was written in the first place (design.md decision 6). The detached context matters: a canceled request context can itself be why processing failed, and the cleanup must still run.
- [ ] 4.5 `cleanupRedundantUpload`: delete the object rather than the file, and drop its sidecar call. Its comment should record that the duplicate's write-then-delete is unavoidable — the content hash is only known after the full read (design.md decision 8).
- [ ] 4.6 Remove the success-path `os.Remove(videoPath)` and both `removeArtifactOwner("uploads", …)` calls; 4.4's defer subsumes them.
- [ ] 4.7 `cmd/api/main.go`: delete the `/uploads` route group and its two middlewares, and drop `"uploads"` from `createDirs` so only `temp/` remains.
- [ ] 4.8 `cmd/api/main.go`: delete `artifactOwnerSuffix`, `recordArtifactOwner`, `artifactOwner`, `removeArtifactOwner`, `rejectOwnerSidecarRequests`, and `requireArtifactOwnership` outright. Run that grep as the completion check for this task.
