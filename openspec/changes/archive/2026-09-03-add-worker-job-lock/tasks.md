## 1. Domain and ports

- [x] 1.1 `internal/video/domain/job_status.go`: add `JobStatusProcessing → JobStatusQueued` to `validTransitions`. Rewrite the table's comment: it currently reads "No backwards transitions", which becomes false. State the one exception, why it exists (a job whose worker died is otherwise unreachable — the claim predicate refuses a `processing` row and the broker's redelivery arrives before any lease can lapse), and that `completed`/`failed` stay terminal.
- [x] 1.2 `internal/video/domain/video_job.go`: add a `Requeue()` transition method for that edge. It rejects an empty source key with the same sentinel `Enqueue` uses — a re-dispatch with no source is a message no worker can act on. It also **advances the aggregate's in-memory epoch by one**, matching the `lease_epoch = lease_epoch + 1` the conditional statement applies, so the decorator has the advanced value to cache without a second read. Do **not** route it through `Enqueue`: the two differ in origin status and in who may perform them.
- [x] 1.3 `internal/video/domain/video_job.go`: add a `leaseEpoch` field with an accessor, carried by `NewVideoJob` (zero) and `RestoreVideoJob`. No cross-field validation pairing it with status — every status is reachable at every epoch, and the column ships with a default that must keep pre-existing rows loadable, exactly as `sourceKey` and `contentHash` do.
- [x] 1.4 `internal/video/domain/repository.go`: `ClaimForProcessing` returns the claimed row's epoch alongside the bool. Add `Requeue(ctx, job, observedEpoch) (requeued bool, err error)` and `FindProcessing(ctx, after VideoJobID, limit int) ([]*VideoJob, error)` — the cursor parameter is not optional, since task 2.8's keyset rotation cannot be implemented without it. **The zero `VideoJobID` means "start of scan"**, which the first cycle and every wrap pass: it serializes to the empty string while `video_jobs.id` is a PostgreSQL `uuid`, so binding it into `id > $1` would error before a single row was examined. Say so at the parameter. `Update` takes the caller's epoch **and returns an outcome, not just an error** — `Update(ctx, job, epoch) (applied bool, err error)` or a small result type. An error-only signature cannot express task 4.2c's applied-versus-already-present distinction, and without it the sweeper's single-cleanup guarantee has no implementable form. Update the port's doc comments — `ClaimForProcessing`'s currently ends "It is deliberately not a recovery primitive: a job whose consumer died mid-run stays processing, and nothing here reclaims it", which this change makes false; replace it with why the predicate still names `queued` alone.
- [x] 1.5 New exported sentinel `ErrJobFenced` in `internal/video/domain`, distinct from `ErrJobClaimLost` and `ErrVideoJobNotFound`. Document the distinction at the declaration: a lost claim means another consumer took the job *before* this one started, a fenced write means another consumer took it away *while* this one was working. Callers separate them with `errors.Is`, which only works if they are disjoint.
- [x] 1.6 `internal/video/domain/job_lease.go` (new): the `JobLeaseStore` port — acquire, renew, release, and a query for whether a job is leased **at a given epoch** (`Held(ctx, jobID, epoch)`, not `Held(ctx, jobID)`). Every method carries the fence epoch; renew and release are conditional on the stored value still naming it, and the query answers about the epoch the caller observed rather than about the key's mere existence. Without the epoch on the query, a stale lease masks a live abandonment: if the current holder never managed to acquire (its acquire failed open) and a superseded claimant's late acquire found the key absent, the store would hold an *older* epoch, and a job-ID-only query would report the job as held while the actual holder is fenced and the row is unrecoverable. Document why the epoch is a sufficient holder identity: only a requeue changes it, and only a requeue can produce a second holder.

## 2. Persistence

- [x] 2.1 `internal/video/infrastructure/postgres/schema.sql`: `lease_epoch BIGINT NOT NULL DEFAULT 0` inline in `CREATE TABLE` and via `ALTER TABLE … ADD COLUMN IF NOT EXISTS`, in the file's existing idempotent-DDL style, with the same two-paths comment `source_key` and `content_hash` carry. The comment must say why `0` is the *correct* value rather than a placeholder: the epoch counts abandonments, and a pre-existing row has been abandoned zero times.
- [x] 2.2 `schema.sql`: a partial index supporting the sweeper's scan and its cursor (`video_jobs (id) WHERE status = 'processing'`, or on whatever column task 2.8's ordering settles on). Comment it against the outbox index's precedent — the sweeper runs on a timer for the life of the deployment, so a scan whose cost grows with total job history is the failure mode this exists to avoid.
- [x] 2.3 `repository.go`: round-trip `lease_epoch` through `Create`, `FindByID`, `FindByUserID`, and `FindCompletedByUserID`, and through `scanJobRow`. A pre-migration row loads at zero, not an error. Keep the SELECT list, the `Scan`, and the `RestoreVideoJob` call in step — the existing comment there already warns about this.
- [x] 2.4 `repository.go`: `ClaimForProcessing` gains `RETURNING lease_epoch` on the claiming statement itself. Not a second query before or after: a value read before can be stale by the time the claim lands (a sweep can requeue in between) and the winner would then hold an epoch that fences its own terminal write; a value read after is a statement another writer can interleave with. Do **not** advance the epoch here.
- [x] 2.5 `repository.go`: **split `updateJobStatement` first.** It is shared verbatim by `Update` and `Enqueue`, so adding the predicate to it in place would make every `pending → queued` enqueue affect zero rows while still inserting and committing its outbox row — a job left `pending` with a live dispatch naming it. Give `Enqueue` its own statement, keeping its `WHERE id = $5` (its transition is guarded by the aggregate and by the transaction, and the outbox insert is what must commit with it), and give `Update` a terminal-only statement whose predicate gains `AND lease_epoch = $6 AND status = 'processing'`. The shared statement's comment explains the sharing and must be rewritten rather than left describing a statement that no longer exists. Zero rows affected on the `Update` statement is classified by the follow-up lookup of task 2.6, not returned as `ErrJobFenced` unconditionally: a strictly greater epoch, or a same-epoch terminal row whose recorded outcome differs from the one being written, returns `ErrJobFenced`; a same-epoch terminal row carrying exactly that outcome returns `applied = false, err = nil`. Both conjuncts are required and neither is redundant: the epoch rejects a superseded worker, the status makes the write exclusive between two actors legitimately holding the *same* epoch (a leaseless worker still running and the sweeper abandoning it). It is safe because `Update` writes only `processing → completed|failed` — `Enqueue`, `ClaimForProcessing`, and `Requeue` own the other three edges. Rewrite the statement's comment block, which currently explains why `Update` is unconditional — that reasoning is superseded, and the replacement must say what changed (recovery now exists), what each conjunct buys, and why the aggregate's own transition check does not substitute for the status one.
- [x] 2.6 Classify the zero-row cases with a follow-up lookup, the way `ClaimForProcessing` already does. Three readings: a strictly greater epoch is a takeover (`ErrJobFenced`); a same-epoch terminal row with a *differing* outcome is another actor at this epoch having finished first (also `ErrJobFenced`; the application may log the shared sentinel as a generic takeover); a same-epoch terminal row carrying *exactly* the outcome being written is this caller's own earlier commit, reported as not-applied success. Compare the outcome on status, storage key, frame count, and error reason — all four, since the sweeper's abandonment and a genuine failure differ only in the reason.
- [x] 2.7 `repository.go`: `Requeue` — one transaction: the conditional `UPDATE … SET status = 'queued', lease_epoch = lease_epoch + 1 WHERE id = $1 AND status = 'processing' AND lease_epoch = $2`, plus the outbox insert, using the **same** `videoJobQueuedEventType` constant and the same payload struct `Enqueue` uses. Zero rows affected rolls the transaction back and reports "not requeued" rather than an error. Factor the payload/insert with `Enqueue` rather than copying it — a drifted second payload is a message the consumer decodes to zero values.
- [x] 2.8 `repository.go`: `FindProcessing(ctx, after, limit)` — status filter in the query, deterministic order, explicit limit, and a **keyset cursor** the sweeper carries between cycles, wrapping to the start when a scan returns short. A zero cursor omits the keyset predicate entirely rather than binding an empty string against a `uuid` column; two statements, or one built conditionally, but never `id > ''`. Not owner-scoped, and not reachable from any route. A fixed `ORDER BY … LIMIT n` with no cursor starves recovery: if one batch's worth of healthy long-running extractions sorts first, an abandoned job behind them is never examined until they finish.
- [x] 2.9 `internal/video/infrastructure/cache/repository.go`: add `LeaseEpoch` to `cachedJobRecord`, `newCachedJobRecord`, and `toVideoJob`, with `omitempty` decoding a previous release's record to zero. Same non-optional plumbing argument as `SourceKey`/`ContentHash`.
- [x] 2.10 `cache/repository.go`: implement `Requeue` write-through **only when a row was affected**, propagate `Update`'s `applied` outcome unchanged, and pass `FindProcessing` straight through uncached. Write through only when the write was *applied* — a fenced `Update` returns the sentinel, and an already-present one applied nothing, so in both cases writing the caller's in-memory job would publish a state it does not own.

## 3. The lease adapter

- [x] 3.1 `internal/video/infrastructure/lease/redis_store.go` (new): `JobLeaseStore` over `*redis.Client`, keys `videojob:lease:<jobID>`, value the epoch, TTL a package constant. Acquire is a Lua compare-and-set with expiry: write when the key is absent or holds an **older or equal** epoch, refuse when it holds a **newer** one, and report that refusal as an ordinary outcome rather than an error. `SET NX` is still wrong for the reason it always was — it would also refuse an older key, leaving a legitimate new holder leaseless and invisible to the sweeper for that key's remaining TTL — but a plain unconditional `SET` is wrong too: a claimant that stalls between winning the claim and setting the lease can be swept and superseded, and its late write would replace the rightful holder's lease with a stale epoch, stop that holder's renewals, and get a live job requeued a second time. Not-newer is the predicate that keeps both properties.
- [x] 3.2 Renew and release are conditional on the stored value, as Lua scripts in the shape of `idempotency.RedisStore`'s `clearScript`. A refused renew is ambiguous between a missing key and a different epoch, so the heartbeat follows it with conditional acquire: equal/absent restores the lease and continues, while a newer epoch proves takeover and stops renewal.
- [x] 3.3 The held-query takes the epoch and reports held only when the stored value names it; a stored value naming a different epoch is "not held". It also distinguishes "not held" from "could not tell". Do not collapse a Redis error into `false`: the sweeper's whole failure posture depends on being able to tell them apart, and a collapsed error would turn an outage into a licence to requeue every running job.
- [x] 3.4 Constants, not configuration: TTL, renewal period, sweep interval, batch size, and the requeue bound are package constants, on the same reasoning as the status cache's fixed 5-minute TTL. No new environment variable at either binary.

## 4. Application layer

- [x] 4.1 `start_processing.go`: `TransitionResult` (or a dedicated result) carries the epoch `ClaimForProcessing` returned. Everything else about this use case stays — in particular the pending-vs-lost-claim discrimination, which survives untouched precisely because the claim predicate was not widened. Note that in the doc comment so a later reader does not "simplify" it after seeing the new backwards edge in the transition table.
- [x] 4.2 `complete_job.go` and `fail_job.go`: their inputs gain the epoch, passed to `Update`. They must **not** read it off the job they loaded — by then the row may carry a successor's, and the fence would pass in exactly the case it exists to reject. Say so at the field, not only in the design doc.
- [x] 4.2b `start_processing.go`, `complete_job.go`, and `fail_job.go`: take a **reader** and a **writer** rather than one repository — the undecorated PostgreSQL repository for the load, the cached decorator for the write — and wire them that way in `cmd/worker`'s `setupWorker` (and anywhere `cmd/api`'s tests construct them). The rule is that a decision about who owns a job does not read a cache, and each of the three makes one; `EnqueueVideoJob` keeps its cached read because a submitter transitioning a job it just created does not. For the terminal writes, without this the equal-epoch `queued` case below has no executable path: the aggregate refuses the transition before any statement runs, so a stale cached record leaves the rightful holder unable to commit at all. For the claim the stake is higher — a failed requeue cache write and failed fallback invalidation can leave `processing` cached against a `queued` row, so `job.StartProcessing()` refuses `processing → processing` and `handle` dead-letters the `ErrInvalidStatusTransition`; since the sweeper only scans `processing`, a recovery that already succeeded would be lost for good. Same judgement as `GET /download/:filename`'s entitlement lookup and the sweeper's scan.
- [x] 4.2a `complete_job.go` and `fail_job.go`: map a refused aggregate transition to `ErrJobFenced` when the loaded row's epoch is strictly greater than the caller's held epoch, or when it is equal on a terminal row whose recorded outcome differs from the one being written. Two cases are deliberately **not** fences: an equal epoch on a `queued` row (impossible for a real requeue, which always advances the epoch — it means a stale cache entry, which task 4.2b's authoritative read prevents from ever reaching this branch), and an equal epoch on a terminal row carrying exactly this call's own status, storage key, frame count, and reason — report success so a lost-response retry acks and cleans up.
- [x] 4.2c That success must carry **applied versus already-present**, which means `CompleteJob`/`FailJob` return it and `ProcessVideoJob` carries it through in its result. Matching fields do not prove this caller wrote them: two sweepers at the bound write the identical epoch, `failed`, and fixed reason. `handle`'s `completeWithRetry` may clean up on already-present because it is retrying its own attempt; the sweeper, which attempts once, must clean up only on *applied*. Both use cases load and transition *before* they write, so a job already requeued (`queued`) or already finished by a successor (terminal) never reaches the fenced statement and would otherwise surface as `ErrInvalidStatusTransition` — which `cmd/worker`'s disposition table does not branch on. A `pending` job is exempt and keeps reporting the raw error, mirroring `start_processing.go`'s pending-versus-lost-claim discrimination; write the exemption as deliberately as that one.
- [x] 4.3 `process_video_job.go`: carry the epoch from `StartProcessing` into every `failWith` call and into `ProcessVideoJobResult`. A `FailJob` refused by the fence is returned as the sentinel — not retried unfenced, not re-loaded, not reported as a failed job. The local-copy cleanup still runs on that path. `ProcessVideoJobResult` also carries `FailJob`'s **applied-versus-already-present** outcome (task 4.2c): `handle` reads `CompleteJob`'s from its own return value, but the failure write happens in here, and its `!result.Success` branch deletes the source and clears the idempotency key on the strength of it.
- [x] 4.4 `process_video_job.go`: take the `JobLeaseStore` port. Acquire the lease the moment `StartProcessing` reports a won claim, renew it from a goroutine for the duration of the extraction, and stop renewing before returning. Acquire and renew failures are logged and extraction continues — the conditional PostgreSQL claim and terminal fence protect correctness. If renewal is refused, conditionally reacquire: a missing/equal lease resumes the heartbeat, while a newer epoch stops it because the terminal write will be fenced. Do **not** release here; the worker does that after the terminal write (task 5.2).

- [x] 4.5 A use case (or a method on an existing one) for the sweeper's terminal abandonment: fail the job with the fixed reason at the fenced epoch. Reuse `FailJob` rather than adding a second path to `failed`; the reason string is an English constant beside `storeFailureReason`/`fetchFailureReason`, naming no endpoint, bucket, broker, or Redis.

## 5. `cmd/worker`: the lease and the fenced disposition

- [x] 5.1 `setupWorker`: construct the lease store from the Redis client already wired for the idempotency store and the cache decorator. No new configuration surface.
- [x] 5.2 `handle`: release the lease once the outcome is committed — after `completeWithRetry` succeeds, and on the terminal-failure path after `ProcessVideoJob` reports a committed `failed`. Acquisition and renewal are `ProcessVideoJob`'s (task 4.4), because only it knows the moment the claim was won; release is conditional on the epoch, so performing it here is safe and puts it where the outcome is decided.
- [x] 5.3 Do not release the lease on the fenced path or on any path that committed nothing. A fenced worker's epoch no longer matches, so a conditional release is already a no-op — but attempting one and logging its result muddies the log with a failure that is the expected outcome.
- [x] 5.4 `handle`: add the fenced case to the disposition table. `ErrJobFenced` from `completeWithRetry` or from `ProcessVideoJob` → reject without requeue, **keep the source object**, do not clear the idempotency key, and log the job, the epoch held, and any result key stored. Distinguish it in the log from a lost claim; they mean different things and only one of them implies work was thrown away.
- [x] 5.5 `completeWithRetry`: `ErrJobFenced` is **not** retryable. Break out of the retry loop on it — retrying a fenced write burns the full backoff to fail identically four times.
- [x] 5.6 Review every existing comment in `cmd/worker/main.go` that asserts a stranded job is permanent. `drainTimeout`'s comment ("stranded until an operator or a later recovery mechanism intervenes") and the `err != nil` branch's are the two to correct — the recovery mechanism now exists and is in this same file.

## 6. `cmd/worker`: the sweeper

- [x] 6.1 A `sweeper` type (or a `run`-level goroutine, matching how `cmd/api` runs its relay) that ticks on an interval, calls `FindProcessing` on the **undecorated** PostgreSQL repository with the batch limit and the cursor it carries from the previous cycle, and for each job asks the lease store whether it is held **at the epoch that scan reported** — a lease naming any other epoch is not this generation's and does not protect the row. The scan bypasses the cache because a takeover is a correctness decision (the `GET /download/:filename` precedent); the **requeue and the abandonment write go through the cached decorator**, carrying the epoch that authoritative scan reported — a requeue written past the decorator would leave a `processing` entry in the cache for its TTL and `GET /api/video-jobs/:id` would keep reporting `processing` for a job already re-dispatched. Advance the cursor past the last row examined and wrap on a short read, so a batch of healthy leased jobs cannot pin the scan to the same prefix forever.
- [x] 6.1a Confirmation before action: carry an in-memory `map[VideoJobID]epoch` of jobs seen unleased, and act on a job only when the current cycle confirms a mark at the *same* epoch. Drop the mark whenever a cycle finds the job leased, not `processing`, at a different epoch, or cannot query the lease store for that job; marks outside a failing keyset batch are not globally invalidated. This is not belt-and-braces — a claim commits in PostgreSQL and its lease is set in Redis, so every healthy run is briefly unleased, and at the requeue bound acting on that single observation fails a live job and deletes its source. Keep the map worker-local: sharing or persisting it would add a coordination problem the conditional writes already solve.
- [x] 6.2 Held → skip. Not held **and** the epoch is below the bound **and** the job has a source key → `Requeue` with the observed epoch; log the job and the new epoch. Not held and the bound is reached → abandon it (task 6.2a).
- [x] 6.2a Abandonment: fail the job through the fenced terminal write, and only if that write is reported as **applied by this call** (task 4.2c) — not merely as a terminal row matching what it intended — delete the source object and clear the idempotency key, reusing `deleteSource` and `clearIdempotencyKey`. Exclusivity here comes from task 2.5's `status = 'processing'` conjunct, not from reasoning about which error the loser gets: two sweepers, or a sweeper and a leaseless worker still running, can hold the same epoch, so whoever writes first leaves the row terminal and every other write affects no row. Do not gate the cleanup on the job merely *being* terminal — that is the same invariant `handle` already enforces on its own paths.
- [x] 6.2b A `processing` job whose `source_key` is empty is failed rather than requeued once the same two-observation abandonment check succeeds, through the same abandonment path. These are the pre-`source_key`-column rows the first sweep is meant to recover, and requeueing one is a loop with no exit: `VideoJob.Requeue` rejects an empty source key, so the epoch never advances, the bound is never reached, and the sweeper logs the same error every cycle forever. Filtering them out of `FindProcessing` instead would leave them stranded, which is what this change exists to end.
- [x] 6.3 Could not tell → skip, and log once per cycle rather than once per job. This is the fail-closed half of the posture and needs its own comment: "cannot reach Redis" is not evidence of expiry, and treating it as such would take over every live job at once.
- [x] 6.4 A requeue that reports no row affected is a normal outcome, not an error — another sweeper won, or the job finished between the scan and the write. Log one ordinary line with the job and observed epoch (the project logger has no debug level); do not retry it.
- [x] 6.5 `run`: start the sweeper alongside the consumer, cancel it on the shutdown signal, and **join** it before `closeDB`/`redis.Close`. Same reasoning as `cmd/api`'s relay join, and the comment should point at it: the sweeper holds a transaction while it runs, so closing the pool first would abort a claim instead of resolving it.
- [x] 6.6 The sweeper's own context: it must not run on `context.WithoutCancel` the way the handler does. The handler is detached because killing a running `ffmpeg` is worse than waiting; a sweep has no such investment and should stop promptly.
