## 2. Package: `internal/platform/rabbitmq` (context-free plumbing)

- [x] 2.1 `config.go`: `Config` with a single `URL` field, `LoadConfigFromEnv` reading `RABBITMQ_URL`, and an exported `ErrURLRequired` returned when the variable is unset or empty. One field, not a decomposed host/port/user/vhost set — the URI is AMQP's own addressing form and carries the TLS scheme, the credentials, and the vhost that a bare address cannot express. Mirror `internal/platform/redis/config.go`'s shape and error style.
- [x] 2.2 `client.go`: `Open(cfg Config) (*amqp091.Connection, error)` calling `amqp091.Dial`. Unlike `redis.Open` and `storage.Open` this genuinely connects (design.md decision 2) — record that in a doc comment with the reason, so a later consistency pass does not "fix" it into a deferred-connect shim. The wrapped error must not echo `cfg.URL`: an AMQP URI carries **both** the username and the password in its userinfo component, and this error reaches logs.
- [x] 2.3 `client.go`: `Ping(conn *amqp091.Connection) error` that opens a channel and closes it. Do **not** use `conn.IsClosed()` — it reports only what this process has already observed, which is stale for exactly the unreachable-broker case a health check exists to catch (design.md decision 3, and the same trap `minio-infrastructure` documents for `minio-go`'s cached `IsOnline`). Note in a comment why the cheap predicate was rejected.
- [x] 2.4 `client.go`: `Close(conn *amqp091.Connection) error`. Unlike the MinIO adapter, which has no teardown because `*minio.Client` exposes none, an AMQP connection owns a socket and must be released.
- [x] 2.5 `topology.go`: an exported `Topology` descriptor with fields for the five names (exchange, routing key, work queue, dead-letter exchange, dead-letter queue) and the three bound values (work max length, dead TTL, dead max length). **No default value and no name literal in this package** — `ddd-architecture` confines `internal/platform/` to connection/lifecycle plumbing, never a specific context's use case, and `video.jobs` is Video Processing's (design.md decision 4). The two overflow policies and the dead-letter queue's lack of its own DLX are likewise **not** fields: they are the invariants that make the topology bounded, and a caller able to vary them could declare an unbounded chain through this API.
- [x] 2.6 `topology.go`: `DeclareTopology(conn *amqp091.Connection, topo Topology) error` opening **its own** channel and closing it before returning, so a failed declaration cannot leave a caller's long-lived channel closed — AMQP gives no way to reopen the same channel. Declaration order is fixed and load-bearing: dead-letter exchange, dead-letter queue, and its binding **first**, then the work exchange, the work queue, and its binding. RabbitMQ does not validate that a queue's `x-dead-letter-exchange` exists at declare time and silently drops dead-lettered messages when it does not, so declaring the sink first makes a partial failure leave an incomplete topology rather than a complete-looking lossy one (design.md decision 6).
- [x] 2.7 `topology.go`: declare every exchange and queue `durable: true`, `autoDelete: false`, `exclusive: false`, `noWait: false`. All four, not just durability: the flags are independent, and an exclusive queue is visible only to its declaring connection, an auto-delete queue vanishes with its last consumer, and `noWait: true` returns before the broker answers so a rejected declaration surfaces later as a channel exception rather than as this function's error.
- [x] 2.8 `topology.go`: declare the work queue with the descriptor's max length, `x-overflow: reject-publish`, the descriptor's dead-letter exchange — and **no** `x-message-ttl`. The omission is the decision: expiring a live work message dead-letters it without touching the database row describing the same work, and `internal/video/domain/job_status.go`'s table has no edge out of `queued` except to `processing`, so the job would report `queued` forever with nothing able to advance it (design.md decision 7). `reject-publish` rather than `drop-head` so a full queue is back-pressure a publisher can retry out of instead of silently losing the oldest item; `reject-publish` rather than `reject-publish-dlx` so a retrying publisher does not deposit one dead-lettered duplicate per attempt.
- [x] 2.9 `topology.go`: declare the dead-letter queue with the descriptor's TTL and max length, `x-overflow: drop-head`, and **no** `x-dead-letter-exchange`. This is what terminates the chain — a bound on the work queue alone relocates growth into an unbounded sink rather than capping it. A TTL is safe here in a way it is not on the work queue: a message only arrives after a consumer rejected it or a bound shed it, so it is already something no consumer will act on.

## 3. Package: `internal/video/infrastructure/messaging` (the context's own names)

- [x] 3.1 `topology.go`: `JobDispatchTopology() rabbitmq.Topology` returning exchange `video.jobs.v1` (direct), routing key `video_job.queued`, work queue `video.jobs.queued.v1`, dead-letter exchange `video.jobs.dlx` (fanout), dead-letter queue `video.jobs.dead`, max length 10 000, dead TTL 24 h, dead max length 10 000. The routing key matches the outbox `event_type` string `add-videojob-source-key-and-outbox-relay` will persist, following the existing `video_job.created` constant.
- [x] 3.2 `topology.go`: document in a comment that the **exchange** carries the generation suffix and the queue name merely follows it, with the reason — a `direct` exchange delivers each publish to every queue bound with the matching routing key, so versioning only the queue would let a not-yet-redeployed replica's messages reach the cutover's new consumer, which is the double-processing window the separate queue was supposed to close. The dead-letter exchange and queue stay unversioned deliberately: a fanout sink shared by both generations is one place to look instead of two (design.md decision 5).

## 5. Local dev & CI infrastructure

- [x] 5.1 `docker-compose.yml`: add a `rabbitmq` service pinned to `rabbitmq:4-alpine`, matching the major-version pinning `postgres:16-alpine` and `redis:7-alpine` already use and the tag CI will use. Healthcheck `rabbitmq-diagnostics -q ping`; ports published on `127.0.0.1` only, following the `redis` and `minio` services' comment style. Set `RABBITMQ_DEFAULT_USER: video` and `RABBITMQ_DEFAULT_PASS: video` — fixed, non-secret, local-only credentials in the same posture as `minioadmin` and `identity`. This is not decoration: RabbitMQ confines the built-in `guest` account to loopback **as the broker sees it**, and every connection in both environments arrives over a Docker network from another address, so a `guest` URI fails with `ACCESS_REFUSED` in compose and CI alike. Record that in the comment so nobody simplifies it back to `guest`. Update the file's header comment, which currently says later phases extend it "with RabbitMQ" — that is now this change.
- [x] 5.2 `docker-compose.yml`: add a named `rabbitmq_data` volume mounted at `/var/lib/rabbitmq`, declare it under top-level `volumes:`, **and pin `hostname: rabbitmq` on the service**. The hostname is not cosmetic and the volume does not work without it: RabbitMQ stores its Mnesia database under `mnesia/rabbit@<hostname>`, and Compose gives a recreated container a fresh generated hostname, so a persisted volume would be reopened by a node with a different name — starting empty beside the old directory rather than resuming it. Carry that reason in the comment, and contrast it explicitly with the `redis` service's deliberate no-volume comment so the difference reads as a decision: Redis holds explicitly non-authoritative data, whereas once the relay has a broker acknowledgement and stamps `published_at`, the message is the only record that the job is still waiting — the same dangling state `minio_data` exists to prevent. Note that clearing the relay change's residue therefore needs `docker compose down -v`, not a plain `down`.
- [x] 5.3 `docker-compose.yml`: add `RABBITMQ_TEST_URL: amqp://video:video@rabbitmq:5672/` to the `app-test` service's environment and add `rabbitmq` to `app-test`'s `depends_on` with `condition: service_healthy` — `docker compose run` starts only a service's declared dependencies, so without this the tests in section 4 connect to nothing. Do **not** add a non-test `RABBITMQ_URL` to the `app` service: nothing in `cmd/api` reads it, and adding it would imply a startup requirement this change explicitly does not create.
- [x] 5.4 `.github/workflows/ci.yml`: add `rabbitmq` to the `test` job's `services:` block — a service container, unlike MinIO. The comment on the MinIO step warns against converting it back to a service container; that warning is specific to an image whose `CMD` lacks its own server arguments. `rabbitmq`'s default command is `rabbitmq-server`, which is exactly what is wanted. Health options mirroring the compose healthcheck (`--health-cmd "rabbitmq-diagnostics -q ping"`), port `5672:5672`, and `RABBITMQ_DEFAULT_USER`/`RABBITMQ_DEFAULT_PASS` in the service's `env:`.
- [x] 5.5 `.github/workflows/ci.yml`: add `RABBITMQ_TEST_URL: amqp://video:video@localhost:5672/` to the `Test` step's env. `localhost:5672` is the runner's published port, but the broker sees the connection arriving from the Docker bridge rather than from its own loopback, so the built-in `guest` account is refused here too — the same reason as task 5.1, and what makes this a dedicated account rather than a stylistic choice.
