## Why

Phase 6 turns `POST /upload` into a non-blocking endpoint served by a separate `cmd/worker`, and every step of that depends on a durable broker this repository has never connected to. `openspec/specs/ddd-architecture/spec.md` already names RabbitMQ as the durable job queue Redis must not replace, and `video_job_outbox` has been sitting in the schema since Phase 3 waiting for a relay to publish from — but nothing in the codebase can open an AMQP connection, so none of Phase 6's three remaining changes has anything to build against.

This mirrors `add-redis-infrastructure` and `add-minio-infrastructure`: the connection adapter lands first, alone, consumed only by its own tests, and the feature changes that need it follow. `docs/roadmap.md`'s Phase 6 section carries the full decomposition and the three dependents.

## What Changes

- New `internal/platform/rabbitmq/`: `Config`/`LoadConfigFromEnv` (reads `RABBITMQ_URL`), `Open`, `Ping`, `Close`, a generic `Topology` descriptor, and `DeclareTopology(conn, topo)`. Bare connection and lifecycle plumbing — no publisher, no consumer, no relay, and no name belonging to any bounded context.
- New `internal/video/infrastructure/messaging/`: `JobDispatchTopology()`, the Video Processing context's own descriptor. The split follows the line `ddd-architecture` already draws — `internal/platform/` holds "only connection/lifecycle plumbing, never domain or application logic for a specific context's use case" — and an exchange named `video.jobs` carrying a routing key named after a `VideoJob` event is that context's use case however generic the surrounding code is. Keeping the names in `internal/platform/` would have needed a MODIFIED delta relaxing that scenario: a real architectural change made incidentally, to avoid moving one function.
- The adapter still belongs in `internal/platform/` rather than the video context, unlike MinIO: Phase 7's Notification context subscribes to the same broker through the same `Open`/`DeclareTopology`, with a topology of its own. MinIO sits in the video context for the complementary reason — every one of its consumers is Video Processing.
- `Open` connects, unlike `redis.Open`. There is no lazy AMQP client: the protocol requires a handshake before anything is usable, so `Open` returns a live connection or an error. Forced by the protocol, not chosen — and it is why `Ping` cannot mirror Redis's either (see `design.md`).
- The declared topology is bounded **by length**, on both the job queue and the dead-letter queue, and a full job queue **refuses** the publish rather than dropping its oldest message. The job queue deliberately carries no message TTL: expiring a live job message moves it to the dead-letter queue without touching the `video_jobs` row, and the state machine has no edge out of `queued` except to `processing`, so the job would report `queued` forever with nothing able to advance it. Length plus `reject-publish` bounds the queue and turns a full one into back-pressure a publisher can retry out of.
- The topology's generation lives in the **exchange** name (`video.jobs.v1`), not the queue name. `docs/roadmap.md`'s cutover row commits to a separately named queue, and a separately named queue does not do the job: a `direct` exchange delivers each publish to every queue bound with the matching routing key, so a `.v2` queue on the same exchange would still receive a not-yet-redeployed replica's messages. Versioning the exchange gives the generations separate paths while leaving the routing key equal to the outbox `event_type` string.
- New dependency: `github.com/rabbitmq/amqp091-go` (the RabbitMQ-maintained successor to `streadway/amqp`).
- `docker-compose.yml` gains a `rabbitmq` service with a named volume, a pinned hostname, and a dedicated account, and `.github/workflows/ci.yml`'s `test` job gains a matching service. Both are consumed only by these packages' own tests through `RABBITMQ_TEST_URL`. The volume follows `postgres`/`minio` rather than `redis` — once the relay has a broker acknowledgement and stamps `published_at`, the message is the only record that the job is still waiting. The hostname is what makes the volume work: RabbitMQ keys its Mnesia directory by hostname, and Compose regenerates one per container. The account is what makes any of it reachable: RabbitMQ confines the built-in `guest` to loopback as the broker sees it, and every connection here arrives over a Docker network.
- No `cmd/api` or `cmd/worker` wiring, no new required startup configuration, and no behavior change to any existing endpoint.

## Capabilities

### New Capabilities
- `rabbitmq-infrastructure`: the shared, context-free AMQP adapter (`internal/platform/rabbitmq`) — configuration, connection lifecycle, health check, and generic idempotent topology declaration. Names nothing.
- `videojob-messaging`: the Video Processing context's job-dispatch topology (`internal/video/infrastructure/messaging`) — the pinned names and bounds, the generation scheme the cutover extends, and the obligation on any publisher to publish persistently.

### Modified Capabilities

None — and the package split above is what makes that true rather than a claim to check at promotion time. Every existing RabbitMQ mention in `openspec/specs/` is forward-looking (`ddd-architecture`'s "Redis… SHALL NOT replace RabbitMQ as the durable job queue", the deferred worker lock, and the documentation-accuracy requirement), and all stay true because this change puts no queue in the running application's path. The one canonical requirement this change could have collided with — `internal/platform/` holding only connection/lifecycle plumbing — is satisfied by construction. The first canonical statement that has to move is `videojob-execution`'s, and that belongs to the change that actually publishes.

## Impact

- New files only, under `internal/platform/rabbitmq/` and `internal/video/infrastructure/messaging/`, plus `docker-compose.yml` and `.github/workflows/ci.yml` service and environment additions. No existing Go source is modified.
- New third-party dependency `github.com/rabbitmq/amqp091-go` in `go.mod`/`go.sum`. Not yet an application runtime dependency: `cmd/api` never opens an AMQP connection in this change, so nothing in the running application depends on RabbitMQ being reachable. A broker (compose locally, a service container in CI) is a dependency of these packages' own test suites only.
- `go test ./...` gains a fourth infrastructure prerequisite **for full coverage**, not for a passing run: these tests skip with a clear message when `RABBITMQ_TEST_URL` is unset, matching both sibling adapters, so a local suite without a broker still passes while exercising none of the new code. CI always provides it, and `docker compose run --build --rm app-test go test ./... -v` supplies all four services locally. `docs/development.md` is updated in this change's finalization PR, per the repository's PR-separation rule.
- One finding this change inherits to `migrate-upload-to-async-processing` rather than fixing here: that row's "separately named queue" is necessary but not sufficient, and its own proposal has to version the exchange. Correcting that row's text belongs to the change that owns it.
