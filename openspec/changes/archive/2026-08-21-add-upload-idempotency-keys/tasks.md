## 2. Infrastructure

- [x] 2.1 `internal/video/infrastructure/idempotency/redis_store.go`: `RedisStore` implementing `domain.IdempotencyStore` against `*redis.Client` (from `internal/platform/redis`). `Reserve` generates a token (`uuid.NewString()`) and issues `SET key "reserved:{token}" NX EX <sentinel-ttl>` (sentinel TTL: a few minutes, comfortably longer than `CreateVideoJob`'s own latency — 5 minutes); returns the token and whether the reservation succeeded. `Finalize`/`Clear` each run a Lua script via `client.Eval`/`Script.Run` that checks the key's current value against the caller's token before writing — `SET key "final:{token}:{jobID}" EX 86400` for `Finalize` (the token is embedded in the finalized value too, not just the reservation, so a later `Clear` can still verify ownership after finalization), `DEL key` for `Clear` — returning whether the write actually happened. `Lookup` uses `GET key`, returning `found=false` on a miss and treating any value without the `"final:"` prefix (i.e. still `"reserved:..."`) as `found=false` too (an in-flight reservation is not yet a real job to return), otherwise parsing the job ID out of the `"final:{token}:{jobID}"` value. (As-delivered detail differs from the original task text above, which described a bare `SET key <jobID>` for `Finalize` — the token-embedding refinement was needed for `Clear`'s post-finalization ownership check.)
- [x] 2.2 Integration tests against `REDIS_TEST_ADDR` (skip with a clear message if unset, matching `internal/platform/redis`'s own test pattern): reserve-then-finalize round-trip, reserve-fails-when-already-reserved, lookup-miss, lookup-sentinel-treated-as-miss, clear-then-lookup-miss, sentinel TTL is set on `Reserve` (assert via `TTL` command or equivalent — not just the finalized key's TTL), finalized-key TTL is 24h, a `Finalize`/`Clear` call with a stale/mismatched token is a no-op that leaves the current owner's value untouched and returns `finalized=false`/`cleared=false`.

- [x] 3.5 `handleVideoUpload`: on `reserved=false`, enter a bounded retry loop calling `idempotency.Lookup` (e.g. every 100ms, up to a 2-second bound — both values named constants, not magic numbers). If `Lookup` resolves to a real `VideoJobID` within the bound: delete the just-saved file/sidecar, fetch that job's current status via `getJobStatus`, translate it into `ProcessingResult` per the mapping in design.md Decision 8 (completed/failed/still-processing), and return it — no `409` in this path. If the bound elapses without resolving: delete the just-saved file/sidecar and respond `409 Conflict` with an English-language `ProcessingResult{Success: false, Message: "..."}` (per `CLAUDE.md`'s language policy — this string is Go code, not `index.html`/`app.js` visible copy, so it's new and English, not Portuguese).
- [x] 3.6 `handleVideoUpload`: on `CreateVideoJob` failure, call `idempotency.Clear` with this request's token (log if `cleared=false`, but don't change the error response) before returning the existing 500 error response. On `CreateVideoJob` success, call `idempotency.Finalize` with the new `VideoJobID` and this request's token; if `finalized=false` or `Finalize` returns an error, log it and proceed to `ProcessVideoJob` anyway (per design.md Decision 7 — a Finalize failure is not fatal to an otherwise-valid job).
- [x] 3.7 `handleVideoUpload`: on the `FailJob` path(s) — both `ProcessVideoJob`'s own extraction failure and the existing post-processing `FailJob` call (ownership recording failure) — call `idempotency.Clear` with this request's token for this request's key (log, don't fail the response, if `cleared=false`).
