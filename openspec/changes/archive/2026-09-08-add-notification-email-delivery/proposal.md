## Why

`email` is the last rejected value in the system. `add-notification-domain-and-preferences` closed the `Channel` set at `webhook` and said why — a preference the system stores and never honours is indistinguishable to its owner from one that works — and named this change as the one that would open it. `add-notification-webhook-delivery` then built everything a second channel needs: a consumer that drains the terminal queue, a `Deliverer` port, a claim that deduplicates before any attempt is made, a bounded budget, and a recorded outcome. All of it is channel-agnostic already; `FindDeliverable` orders by channel and would return an e-mail preference today if one could be stored.

So this change is small in the place it looks large and large in the place it looks small. The trigger, the retry policy, the deduplication and the fencing are **not** rebuilt — an SMTP adapter behind the existing port and a channel-to-`Deliverer` routing decision in the composition root are the whole delivery story. What is not small is that three of the Notification context's own invariants were written when `webhook` was the only channel and quietly assume it, and each has to become conditional on the channel before an e-mail preference can be written and read back.

It also closes Phase 7 without the change that used to precede it. `add-identity-user-registered-event` was removed from the backlog on 2026-09-07: the address an e-mail is delivered to is the preference's own `Destination`, the same user-supplied column the webhook channel stores a URL in, so no Identity outbox, relay, or local projection has to exist. The accepted cost — the address is self-declared rather than the verified one Identity holds — is recorded here rather than left to be rediscovered.

## What Changes

- **The `Channel` set opens to `email`.** It stays closed, at two elements. `ParseChannel` accepts the second value, and the scenario in `notification-preferences` that currently requires `400` for `email` inverts.

- **Destination construction becomes channel-dependent, and that is the change's one genuinely new domain concept.** `Destination` today means "an absolute `http` or `https` URL with a host", and one constructor enforces it for every channel. It becomes a per-channel rule: `webhook` keeps that rule unchanged, `email` requires a syntactically valid address. Four call sites build a `Destination` — three reconstructions in `internal/notification/infrastructure/postgres/repository.go` and one in `SetPreference` — and every one of them already holds the channel, so the change is mechanical rather than structural. One `destination` column still stores both, because both are exactly one string and nothing queries inside it.

- **The destination policy applies to the `webhook` branch only, and this is a narrowing of scope, not a relaxation of the rule.** `DestinationPolicy` exists to judge a connection target the user supplied: `CheckDestination` at write time and `CheckAddr` against the resolved address in the dialer. The e-mail channel dials **this deployment's own configured SMTP relay**, never the address the user registered, so there is no user-supplied connection target for it to judge and no SSRF surface for it to guard. The policy's "zero value is the restrictive posture" property is preserved because the branch is taken on the closed `Channel` set — a channel outside the set never reaches either branch, because `ParseChannel` refused it first.

- **The "a stored preference always carries a signing secret" invariant becomes conditional on the channel, in four places rather than one.** An e-mail preference has no secret: HMAC signing is the webhook channel's mechanism and an SMTP message is not signed with one. Each is load-bearing on its own:
  - the `notification_preferences_secret_not_empty` CHECK becomes `channel <> 'webhook' OR secret <> ''`;
  - the create path gains a third statement that **names** `secret` in its inserted tuple and writes the empty string — the column is `NOT NULL` with deliberately no default, so a statement omitting it would insert NULL rather than the empty string the new CHECK permits — while **omitting** `secret` from its conflict clause, so a later write that submits none preserves a secret already stored;
  - the delivery read's projection yields a secret only for a row whose channel signs, decided in the statement rather than after the value has been scanned — an `email` row may carry a secret, since a write submitting one stores it whatever the channel;
  - `NotificationPreference`'s own invariant — enforced by `RestoreNotificationPreference` and reached for **every row `FindDeliverable` returns**, which parses the column through `NewSecret` before restoring — has to admit a preference carrying none. Without this one, an e-mail row could be written and then never loaded, which is the failure mode a schema-only reading of this change would ship.

  `ErrSecretRequired` survives unchanged for `webhook`, and `NewPreferenceIntent` is not touched: it deliberately does not enforce the secret rule, leaving it to the adapter's row count, which is exactly what lets that rule become channel-conditional in the adapter alone.

- **An SMTP adapter behind the existing `Deliverer` port.** `internal/notification/infrastructure/smtp` implements the same one-attempt-at-one-delivery contract the webhook client implements, reports every failure as the existing `*DeliveryError` — built from our own classification, never from a transport error's text — and carries the Notification context's own payload rendered as a message rather than the Video Processing wire payload forwarded. It reads the preference's `Secret` not at all.

- **A channel-to-`Deliverer` routing decision in `cmd/notifier`, and no change to `DeliverNotification`.** The use case holds one `Deliverer` and calls it per preference. Rather than teaching it about channels, the composition root composes a `Deliverer` that dispatches on the preference's channel to one of two implementations. The use case, its budget, its claim, its fence and its disposition table are untouched.

- **A mail service in `docker-compose.yml` for local development**, from an image this repository does not produce — the arrangement the gateway already uses — so a contributor can see a delivered message without configuring an external relay or sending real mail.

No change to `POST /upload`, to `cmd/worker`, to either topology, to any `VideoJob` state, or to the terminal-event contract. A delivery that fails still never touches a job. This is **not** breaking: a channel value that is refused today becomes accepted, and every stored `webhook` preference keeps its meaning, its destination rule, its policy and its secret requirement unchanged.

## Capabilities

### New Capabilities
- `notification-email-delivery`: what a delivered e-mail is — the address the preference carries and how it is validated, the message built from the Notification context's own payload, the relay it is sent through and the configuration that names it, why the destination policy does not apply to it, and the fact that it is not signed. It shares the enrolment boundary, the claim, the budget and the recorded outcome with `notification-webhook-delivery` rather than restating them, and says so.

### Modified Capabilities
- `notification-preferences`: the accepted channel set gains `email`; the destination rule becomes per-channel rather than one rule for every channel; and "a preference carries a signing secret" narrows to the `webhook` channel, so creating an e-mail preference without one succeeds rather than being refused with `ErrSecretRequired`. The requirement currently titled for a webhook preference is what changes; the secret's non-disclosure, the omit-preserves rule, the owner scoping, the upsert semantics and the enrolment boundary are all unchanged.
- `notification-persistence`: the stored form admits a preference with an empty secret when its channel is not `webhook` — the CHECK becomes conditional and the create path gains the third atomic statement — and the single named read path that loads the secret must restore an aggregate that has none.
- `notification-event-consumer`: `cmd/notifier` gains the SMTP configuration in the set of variables it requires at startup, and composes two `Deliverer` implementations rather than one. Its disposition table, its shutdown **ordering** and the rule that produces them are unchanged, and the change says so explicitly so that "a second channel" is not read as licence to revisit them. The drain's **length** does change: a message can now resolve to one preference per channel and they are handled one after another, so the bound is sized from the channel count rather than from a single claim hold — otherwise it would expire during work that is within budget.
- `notification-webhook-delivery`: the destination-policy requirement is scoped to the channel whose destination is a **connection target**, rather than stated over destinations generally, and its justification no longer cites the refusal of `email` as an example. This is not a behaviour change for a webhook preference; it is the existing text made accurate now that a second channel exists. The bounded-attempt requirement is **not** modified — that the budget governs every channel with no channel-specific term is stated in the new capability instead, so the webhook capability keeps describing webhook attempts.
- `development-workflow`: the stack the documented single command starts gains a mail service, and the contributor can observe a delivered notification without an external relay.
- `container-image` (**added at finalization, not foreseen in this proposal**): its "exactly one host port" rule was written about the application's surface and read as a rule about the stack, so the mail catcher's inspection port contradicted it. The rule is now scoped to the application and a development-only support service may publish a loopback-bound port of its own. Recorded here rather than quietly promoted, because the paragraph below claiming this capability was untouched was wrong.

## Impact

- **Code**: new `internal/notification/infrastructure/smtp` (the adapter, its configuration, and the message it renders); `internal/notification/domain` gains the per-channel destination rule and loses the unconditional secret invariant in `RestoreNotificationPreference`; `internal/notification/infrastructure/postgres` gains the third upsert statement and channel-aware reconstruction in the three places that rebuild a `Destination` and the one that rebuilds a `Secret`; `cmd/notifier` gains the routing `Deliverer` and the SMTP configuration. `cmd/notification-api` changes only in that `SetPreference` now branches. Nothing under `internal/video`, `internal/identity`, `internal/platform`, `internal/contracts`, `cmd/video-api`, `cmd/identity-api` or `cmd/worker` changes, and no new binary is added — `container-image` changes only in the one sentence that scoped host ports to the whole stack rather than to the application, which the mail catcher's inspection port would otherwise contradict.
- **Data**: no new table and no new column. One constraint is replaced by a conditional one in the Notification database, through the context's existing advisory-locked `Migrate`, as an `ALTER TABLE` that is safe to re-execute on every startup — the pattern `internal/video`'s schema already uses for a statement that has to reach a database whose table exists. No backfill: every stored row is a `webhook` row carrying a secret and satisfies the new constraint unchanged.
- **Configuration**: `cmd/notifier` gains the SMTP relay's address, the envelope sender, and whatever credentials the relay needs, required at startup for the same reason the delivery budget is validated there — a notifier that cannot send is a notifier whose e-mail preferences are stored and silently never honoured. `cmd/notification-api` gains nothing: it validates an address, it does not send. `docker-compose.yml` gains the mail service and points the notifier at it.
- **Security**: the first outbound path that carries a user-supplied string into a message envelope, so address validation is a contract rather than an implementation detail. Two properties are stated rather than assumed: the SMTP adapter reads no `Secret`, and a recorded reason or log line on this path is built from our own classification exactly as the webhook path's is — an address may not appear in either. The self-declared-address exposure is recorded in `docs/operations.md`; what bounds it is that a delivery is only ever triggered by a job the same user owns.
- **Docs**: `docs/architecture.md` gains the second delivery channel, `docs/domain-model.md` the per-channel destination and the narrowed secret invariant, `docs/operations.md` the new service, its variables and the self-declared-address consideration, `docs/development.md` the mail service in the local stack, `docs/roadmap.md` the row's status, and `CLAUDE.md` the second channel and the three conditional invariants.
