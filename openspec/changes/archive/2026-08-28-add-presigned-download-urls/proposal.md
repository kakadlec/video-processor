## Why

Phase 5 moved every artifact into the bucket, but `cmd/api` still stands in the middle of the one operation that is pure I/O. `handleDownload` opens the stored object and copies it byte-for-byte into the response, so a 200 MB result is read out of MinIO and written back out through the API process, holding a goroutine and a connection for the whole transfer. The bytes already live in a system built to serve them directly; proxying them buys nothing but a bottleneck.

The timing matters. Phase 6 makes `POST /upload` non-blocking and moves extraction into `cmd/worker`, on the premise that `cmd/api` becomes a thin, quick-to-respond control plane that can be replicated freely. Leaving the download path as a proxy would contradict that in the one place where transfer sizes are largest — an API replica's memory and connection budget would still be sized by result size rather than by request rate.

This is the last of Phase 5's four changes. `add-minio-infrastructure` supplied the connection plumbing, `migrate-result-storage-to-minio` and `migrate-upload-storage-to-minio` moved the two artifact classes into the bucket; this one stops the API from carrying result bytes.

## What Changes

- **Add a presigning operation to the `ResultStorage` port** and its MinIO adapter: given a `StorageKey`, a TTL, and the filename to present to the browser, return a time-bounded URL that grants unauthenticated read access to that one object, plus the instant it stops being accepted.
- **`GET /download/:filename` stops streaming bytes and becomes the issuer of that URL.** It keeps its route, its bearer gate, and its entitlement logic exactly; only its response body changes, from the zip to `{"url": ..., "expires_at": ...}`. **BREAKING**: any client that today reads the zip from this endpoint gets JSON instead.
- **Entitlement is enforced at issuance, and only there.** The requested key must parse to a `VideoJobID`, that job must exist, belong to the caller, be `completed`, and record that exact key — the same five conditions, in the same order, that guard the streaming handler today. A presigned URL carries no identity once issued, so this is the only point at which ownership can be checked.
- **The handler `Stat`s the object before issuing.** Presigning is offline signing: it succeeds for a key that holds no object, and the failure would surface only when the browser follows the URL and gets a `404` from MinIO instead of the byte-identical `404` this endpoint promises. One `Stat` — the call `GET /api/status` already makes per entry — preserves "an object missing from the bucket is indistinguishable from every other rejection" without weakening the requirement.
- **`ResultStorage.Open` is removed.** `handleDownload` was its only consumer; after this change nothing in the codebase reads a result artifact's bytes through the API. Keeping an unused method on a domain port would invite a future caller back into the data path this change exists to leave.
- **New optional configuration for the browser-facing host**: `VIDEO_MINIO_PUBLIC_ENDPOINT` and `VIDEO_MINIO_PUBLIC_USE_SSL`, each defaulting to its internal counterpart when unset. This is not a convenience. SigV4 signs the `Host` header, so a minted URL's host cannot be rewritten afterwards without invalidating the signature — and the internal endpoint is routinely a name only the server can resolve (`docker-compose.yml` sets `VIDEO_MINIO_ENDPOINT: minio:9000`, which no browser on the host can reach). The presigning client must therefore be constructed against the public host from the start.
- **The bucket's region is discovered once at startup** and passed to that presigning client. Verified against `minio-go v7.3.0`: `PresignedGetObject` on a client with no configured region issues a `GetBucketLocation` round trip before it can sign — which is fatal for a client pointed at a host the server cannot reach. With the region set, signing is local arithmetic (measured at ~150 µs against an endpoint that does not resolve). `cmd/api` already pings and ensures the bucket at startup; discovering the region there costs one more round trip on a path that is already fail-closed, and avoids inventing a `VIDEO_MINIO_REGION` variable that operators would have to keep correct.
- **The attachment filename travels inside the signature.** `response-content-disposition` is passed as a signed query parameter, so the browser still receives `Content-Disposition: attachment; filename="frames_<jobID>.zip"` from MinIO. Verified against the pinned stack: the parameter is honored, and tampering with it after signing yields `403`. This matters beyond cosmetics — the HTML `download` attribute is ignored for cross-origin URLs, so the header is the only thing that makes the response a download rather than a navigation.
- **The TTL is a fixed constant, not configuration**, following the status cache's fixed 5-minute TTL. Issuance happens on click, not on listing, so the interval a URL must survive is the sub-second gap between the JSON response and the browser's navigation — not the minutes a listing may sit on screen.
- **`cmd/api/web/app.js`'s `downloadFile()` changes shape**: it fetches JSON with the bearer token, then navigates to the returned URL, instead of fetching a blob and building an object URL. This removes the whole-result-in-browser-memory step the current implementation requires. New user-facing copy stays pt-BR, per the language policy.
- **The issuance response carries `Cache-Control: no-store`**, on success and rejection alike. Its body is a credential, and an authenticated `200` is otherwise ordinarily cacheable — a retained copy would outlive the request that asked for it and undo the short lifetime. Applying it to every response also keeps the byte-identical rejections identical down to headers.
- **`expires_at` is read off the issued URL's signature**, not computed as `now + TTL`. The signing library stamps the signature's start at whole-second precision and truncates the lifetime to whole seconds, so the naive value overstates the real admission window — measured at 561 ms in one issuance, and a requested `5m0.5s` signed as exactly `300` seconds. Overstating it is the harmful direction: a client that trusts the field retries after the service has stopped accepting.
- **A `429` still cannot be reached by the transfer.** Issuance sits on `videoRoutes` and is rate limited exactly as before; the subsequent `GET` goes to MinIO and is not. Stated as an accepted change of posture rather than left for a reader to discover — see Impact.

## Capabilities

### New Capabilities

None. The download endpoint's contract already belongs to `videojob-result-storage`, whose Purpose names "the two HTTP endpoints that read results back"; splitting one endpoint's behavior across two specs would leave neither readable on its own.

### Modified Capabilities

- `videojob-result-storage`: the port's operation list changes (presigning added, opening removed), and with it the requirement that opening resolves existence and size before returning. "Result Download Is Authorized From The `VideoJob` Row" keeps all five entitlement conditions but its success scenario stops asserting a `200` with the object's bytes. "Every Download Rejection Is Byte-Identical" keeps its full rejection list — including the missing-object case, which the pre-issuance `Stat` preserves — and gains presigning failure as a further rejection that must look identical. The adapter-testing requirement enumerates "storing, opening, and stating" and asserts the result is "retrievable through `GET /download/:filename`"; both stop being true, so it is amended rather than left to become false at promotion time.
- `video-frame-extraction`: it owns the outward description of the same two endpoints — its "Processed File Download" requirement says the system streams the stored object, its zip-packaging scenario says the `zip_path` is downloaded through that route, and its listing requirement describes a download URL. The endpoint stops streaming, so all three are amended; the listing requirement additionally gains the rule that `download_url` addresses this API and never carries a credential.
- `minio-infrastructure`: `Config`/`LoadConfigFromEnv` gain two optional variables and the defaulting rule that ties each to its internal counterpart, and the package gains region discovery plus construction of a second, presign-only client. The four required variables and `VIDEO_MINIO_USE_SSL`'s existing optional contract are untouched.
- `video-processing-access`: gains a requirement for the property this change introduces — that a credential granting artifact access can outlive the request that authorized it, that its scope is one object for a bounded interval, and that it is not revocable. That boundary is exactly what this capability exists to define, and it has never before had to describe access that carries no `UserID`.
- `rate-limiting`: its route enumeration describes the group as containing "JSON and streaming handlers"; after this change every handler in it is JSON. More substantially, the requirement's claim that a rejected request retrieves no object from storage stays true, but the limiter's reach no longer extends to the bytes themselves, and the spec should say so rather than let "every authenticated route is rate limited" be read as "every byte served is rate limited".

Three capabilities were checked and deliberately **not** modified:

- `identity-authentication` — its "Users cannot access another user's artifacts" scenario is written as "user B requests its status or download using a valid token → the server denies access and does not disclose the artifact". That stays exactly true: B's *issuance* request is denied by the unchanged entitlement check, and no URL is minted. The requirement constrains who may obtain access, not the transport by which granted access is exercised.
- `videojob-result-storage`'s key-shape requirement — the flat `frames_<jobID>.zip` convention is justified there by the key being "used verbatim as the `:filename` path segment of `GET /download/:filename`". Because the route survives unchanged, that justification survives with it; the key never becomes free to re-shape. Worth stating explicitly, since the obvious reading of "the frontend no longer downloads through the API" is that the constraint has lapsed. It has not, and re-keying results would orphan every object already stored.
- `upload-idempotency`, `videojob-lifecycle`, `videojob-persistence`, `videojob-execution` — nothing in the write path changes. The job aggregate, its `StorageKey` invariant, and the pipeline that produces the artifact are untouched; only how a stored artifact is handed back moves.

## Impact

**Code.** `internal/video/domain/result_storage.go` (presigning added to the port, `Open` and its doc removed; a sentinel for presigning failure), `internal/video/infrastructure/storage` (the adapter's presigning implementation; config gains the two public variables; client construction gains region discovery and the presign-only client), `cmd/api/video.go` (`handleDownload` becomes an issuer, `setupVideo` wires the presigning client), `cmd/api/web/app.js` (`downloadFile`).

**Tests.** The adapter needs a test that **fetches the issued URL against the real test MinIO with no `Authorization` header and compares bytes** — structural assertions on the query string will pass while producing a URL that `403`s, so they cannot stand alone. Alongside it: that the signature covers `response-content-disposition`, that an expired URL is refused, and that a client configured against an unresolvable public endpoint still signs. `cmd/api`'s download tests move from asserting zip bytes to asserting the issued URL's shape and then following it. The existing byte-identical-`404` suite keeps every case and gains the presign-failure case.

**Operations.** `docker-compose.yml`'s `app` service gains `VIDEO_MINIO_PUBLIC_ENDPOINT: 127.0.0.1:9000` — the host-mapped port, so a browser on the developer's machine can actually follow the URL. Deployments where one endpoint is reachable from both server and client need no new variables at all. Operators gain a new failure mode worth documenting: a correct internal endpoint with a wrong or unset public endpoint produces URLs that authenticate correctly and are unreachable, and the API cannot detect this, because it never follows them.

**Security posture.** Three properties change, and all three are accepted rather than mitigated:

1. **An issued URL cannot be revoked.** Deleting the job, or changing who owns it, does not invalidate a URL already handed out; the TTL is the entire revocation story. This is inherent to presigning and is why the TTL is short.
2. **Result bytes are no longer rate limited.** The limiter guards issuance; the transfer is between the browser and MinIO. A caller limited to 60 issuances per minute can still start 60 transfers.
3. **The URL is a credential.** It must never be logged, echoed into an error, or included in a failure report. Existing code logs the *key* on failure, which stays correct and is what the new paths will do too.

**Documentation.** `docs/architecture.md` (route table, request-flow description of the download path), `docs/flows.md` (the download sequence), `docs/operations.md` (configuration table, the new misconfiguration failure mode), `README.md` (the download step of the usage walkthrough), `docs/development.md` (environment variables for local runs), `CLAUDE.md` (`handleDownload`'s description, the "every authenticated route is rate limited" bullet, the flat-key gotcha's justification), `docs/roadmap.md` (Phase 5 becomes Done, and this row's status). All enumerated in the finalization tasks.

**Not in scope.** No queue, worker, or async upload — that is Phase 6, and `POST /upload` stays synchronous here. No presigned *upload* URLs: `POST /upload` must read the bytes anyway to hash them for idempotency and to validate the extension before the transfer starts, so handing the browser a direct-to-bucket URL would move both checks somewhere they cannot run. No re-keying of result objects, for the reason given above. No pagination on `GET /api/status`, which remains a frontend-coupled follow-up.
