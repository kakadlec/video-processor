## Why

Phase 8 has two changes left and this is one of them (`docs/roadmap.md`). Every dependency the three HTTP services hold is verified exactly once — at startup, fatally. `setupIdentity` opens, migrates and pings PostgreSQL and exits on failure (`cmd/identity-api/identity.go:68-81`); `setupVideo` does the same for PostgreSQL and then pings MinIO, ensures the bucket, discovers its region and builds the presign client, all fatal (`cmd/video-api/video.go:150-211`); `setupNotification` does the same for its own pool (`cmd/notification-api/notification.go:76-87`). **After that moment nothing ever asks again.** A process whose database went away an hour after it started keeps accepting connections, keeps answering `GET /`, `/styles.css` and `/app.js` out of `go:embed`, and answers `500` on every route that matters — and the only way to find out is to make a real request and read the failure. Fail-fast covers `t=0`; nothing covers `t>0`.

There is also nothing for a container runtime to ask. `docker-compose.yml` gives PostgreSQL, Redis, MinIO, RabbitMQ and the gateway a healthcheck each (`:36`, `:52`, `:80`, `:122`, `:148`); **the five application services have none**, so `docker compose ps` reports the one thing the runtime can see unaided — that the process has not exited.

## What Changes

- **Two endpoints on each of the three HTTP services: `GET /health` and `GET /ready`.** Unauthenticated, registered on the engine rather than on the bearer group, alongside `/`, `/styles.css` and `/app.js`. The names are the ones `docs/roadmap.md` and `docs/operations.md:677` already promise; `/livez`/`/readyz` is a Kubernetes idiom and there is no Kubernetes here.
- **`/health` consults nothing and always answers `200` while the process serves.** That is not a weaker `/ready` — it is the only correct liveness rule. A liveness probe that touches a dependency turns a database blip into a restart loop, and a restart is the one remedy that cannot fix a dependency outage.
- **`/ready` answers `200` or `503`, after checking only the dependencies whose absence stops that process honouring its own contract.** The criterion is not invented here; it is this repository's own, stated on the gateway's healthcheck (`docker-compose.yml:149-152`): *"the gateway is healthy when it can serve, and tying its health to a backend's would make an unrelated service's restart look like an ingress failure."* Generalised: **a dependency the system is designed to survive is not a readiness dependency.**

  | | PostgreSQL | MinIO | Redis | RabbitMQ |
  |---|---|---|---|---|
  | `identity-api` | yes | — | — | — |
  | `video-api` | yes | yes — **bucket present**, not merely reachable | **no** | **no** |
  | `notification-api` | yes | — | **no** | — |

  The MinIO cell says *bucket present* because the distinction is the whole of it: every route that touches object storage names an object inside one configured bucket, so a reachable server whose bucket has been deleted fails all of them while a reachability check still passes. Redis is excluded because every feature over it fails open by specification — `upload-idempotency`'s `Reserve` (`cmd/video-api/video.go:658-661`), `rate-limiting`'s counter, `videojob-status-cache`'s writes — so a process with Redis down is a slower correct system, not an unserviceable one. RabbitMQ is excluded on a stronger footing than preference: `POST /upload` commits the `pending → queued` transition and its outbox row in one PostgreSQL transaction and answers `202` with the broker unreachable (`internal/video/infrastructure/postgres/repository.go:479-509`), and `platformrabbitmq.Ping` **requires a live `*amqp.Connection` that no HTTP process holds** — the relay stores a `Config` and dials inside its own loop (`internal/video/infrastructure/messaging/relay.go:63-68`) — **and takes no context**, so it could not be bounded even if one did.
- **Exactly one new check is written.** `/ready` calls `db.PingContext`, the same call startup already makes. It does **not** call `storage.Ping`, which cannot answer the object-storage question: `Ping` issues a real `BucketExists` round trip and then **discards the boolean** (`internal/video/infrastructure/storage/client.go:32-36`), so a reachable server whose bucket has been deleted returns nil. Startup survives that only because it calls `EnsureBucket` on the next line; a readiness endpoint has no next line and must never create the bucket, so as proposed it would hold `/ready` at `200` while upload, status and download could not honour their contracts. Object storage therefore gets a **bounded, read-only bucket-presence check** of its own — `EnsureBucket`'s first half without its second: `BucketExists`, the boolean actually read, no `MakeBucket`. Changing `Ping` to assert presence was rejected rather than overlooked: startup pings *before* it ensures, so a presence-asserting `Ping` would make every fresh deployment fail to boot on a bucket `EnsureBucket` was about to create. `platformredis.Ping` and `platformrabbitmq.Ping` keep their present count of production callers, which is zero.
- **Every check is bounded, and the bound is part of the specification rather than a tuning constant.** An unbounded ping against a hung dependency holds the probe open past the prober's own timeout, at which point every verdict reads as failure regardless of the dependency — the signal inverts.
- **`cmd/worker` and `cmd/notifier` acquire no HTTP surface.** This answers the first of the row's two open questions rather than leaving it open, and the answer is *no*, with its cost stated below.
- **The two probe routes are excluded from the access record, and `/ready` logs verdict *transitions* instead.** One record when the verdict turns not-ready, naming which dependency failed; one when it recovers. `O(transitions)`, not `O(probes)` — and strictly more informative than an access record, because the record may name the failing dependency where the response body must not.
- **`docker-compose.yml` gives the three services a healthcheck against `/ready`**, and **nothing gains `depends_on: condition: service_healthy` against them.** The verdict's consumer is `docker compose ps` and an operator; there is no orchestrator, and this change does not pretend one into existence.
- **The gateway stops exposing a probe.** `/health` on `video-api` is reachable from outside today for free, because it falls into `location /` (`docker/nginx/nginx.conf:107`), while the same path on the other two services is not — an asymmetry nobody chose. Two exact-match `location` blocks returning `404` make the probes internal-only across all three, and the requirement is **status-code equivalence with a path the application does not serve, not a byte-identical body** — byte-identity would take `proxy_intercept_errors on`, which would rewrite the body of every *upstream* `404` in the system, including the one `GET /download/:filename` makes byte-identical on purpose. That is the gateway change this takes; three new upstream blocks, each with its own `set $backend`, is the change it does *not* take.
- **Not in scope**: `/metrics`, Prometheus, an admin listener on a second port, a dependency check of any kind for the two non-HTTP processes, and any change to what startup verifies or how fatally.

## Capabilities

### New Capabilities
- `service-health-probes`: what a liveness answer and a readiness answer mean in this system and why they are two endpoints rather than one; that liveness consults nothing and what that consequently fails to detect; the rule that decides a readiness dependency — the dependency whose absence stops the process honouring its own contract, and no other — applied per service and derived from the gateway's own already-stated rule; that every check is bounded and how that bound relates to the prober's; that neither probe is authenticated, and what a probe response must therefore never disclose; that the verdict is legible to an operator through the local stack while no orchestrator consumes it; and that the worker and the notifier are answered by this capability with *no surface at all*, which `container-image` already requires of them.

### Modified Capabilities
- `structured-logging`: the "HTTP Request and Panic Records Are Records Like Any Other" requirement currently obliges **every** request to yield one access record, with no exclusion mechanism of any kind — it is pinned by spec (`openspec/specs/structured-logging/spec.md:125`, `:144`) and by a test in each of the three roots (`logging_test.go`, held there deliberately by commit `390e4ce`). The delta adds a **closed, named exception for exactly the two probe route templates**, and states the volume argument that justifies it and the transition record that replaces what is lost. A general exclusion mechanism is explicitly refused: it would let any future route leave the access log without spec review.

## Impact

- **Changed**: `cmd/identity-api`, `cmd/video-api`, `cmd/notification-api` — one new file each (the probe handlers and the readiness checker), plus `setupRouter` and `main`. `docker/nginx/nginx.conf` (two refusal blocks). `docker-compose.yml` (three healthchecks). The access-log middleware and its pinned test in each of the three roots.
- **One signature changes.** `setupVideo` returns `(*videoModule, *sql.DB, *redis.Client, *videomessaging.Relay, error)`, and neither object-storage handle is among them: not the MinIO client it pinged, and not the bucket name, which lives only in the local `minioConfig` inside the function. The readiness check needs both, so `setupVideo` gains one return value — **a purpose-built object-storage readiness check that has already captured the client and the bucket**, rather than the two raw values leaked into the composition root. `setupIdentity` and `setupNotification` already return their `*sql.DB`. This is the only structural change the endpoints force.
- **No behaviour changes on any existing route**, no database statement, no broker message, no shutdown sequence, no new dependency, no change to startup's fail-fast posture. `go.mod` and `go.sum` stay byte-identical.
- **Accepted cost, named rather than discovered — the worker and the notifier get no liveness signal, and today nothing else gives them one either.** `cmd/worker`'s sweeper runs every 60s but every record in that file is conditional on finding something; the relay logs lifecycle only; both consumers log only on failure, so a healthy connected consumer is silent. **No record fires on an idle stack for either process**, which means an idle-but-wedged worker is indistinguishable from an idle-and-healthy one. That gap is real and this change declines to close it. What makes declining defensible rather than convenient: `container-image` already requires that the worker and the notifier "SHALL each expose no port at all" (`openspec/specs/container-image/spec.md:55`, scenarios at `:83` and `:88`), so giving either one a listener is not a free decision available to this change — it needs a `container-image` delta, and the argument for it would have to be made against an orchestrator that does not exist. A command-based compose healthcheck remains available without any of that: `sh`, `wget` and `nc` are in the runtime image (`curl` is not), and both `CMD` and `CMD-SHELL` are already used in this file.
- **A second accepted cost — the readiness verdict is consumed by a human.** No orchestrator exists: `docs/operations.md:5` says "There is no orchestration", `:17` says the project has no deployment target, and `.github/workflows/` holds `ci.yml` and `release-please.yml` and no deploy job. Compose marks a container unhealthy and acts on that only through `depends_on: condition: service_healthy`, which this change deliberately points at nothing. So `/ready` buys observability now and a wiring point later, and this proposal claims no more.
- **A third — `/ready` puts a real round trip on each dependency at the probe interval**, which is the price of not caching a verdict. Caching is what `storage.Ping`'s own doc comment refuses for exactly this reason, so a cache here would reintroduce the staleness that decision removed.
- **Also in this change's pull request, as documentation rather than OpenSpec artifacts**: two factual corrections to `docs/roadmap.md`'s own row for this change — it refers to "the notifier's relay", and `cmd/notifier` has no relay (the two are `cmd/video-api`'s dispatch relay and `cmd/worker`'s terminal relay), and it claims per-process dependencies are "already enumerated in `docs/operations.md`'s environment matrix", which enumerates **variables read**, not **connections opened**, and diverges in three places. Both follow the file's `**Revised <date> — …**` precedent. And one new `not-started` Change Backlog row, `fix-worker-dependency-outage-disposition`, recording a worker disposition defect this change's exploration surfaced and deliberately does not fix: `cmd/worker` has no retry disposition, so a runtime dependency outage dead-letters the dispatch instead of retrying it, and when the outage precedes the claim that strands the job at `queued` where the sweeper — which scans `processing` alone — cannot reach it. The row is deliberately **not** written as data loss: the job row, its content hash and its source object all survive, the sweeper recovers the post-claim case unaided, and a MinIO outage is acked with a committed `failed` rather than dead-lettered at all.
- **Dependencies**: `add-structured-logging`, archived. Sequencing, and now also substance — this change modifies its capability.
