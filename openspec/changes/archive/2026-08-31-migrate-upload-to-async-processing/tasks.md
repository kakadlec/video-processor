## 2. Persistence

- [x] 2.1 `internal/video/infrastructure/postgres/schema.sql`: `ALTER TABLE video_jobs ADD COLUMN IF NOT EXISTS content_hash TEXT NOT NULL DEFAULT ''`, in the file's existing idempotent-DDL style. Additive, no backfill — the digest could in principle be recomputed from the stored object, but pre-existing jobs' source objects are already deleted.
- [x] 2.2 `repository.go`: `videoJobQueuedEventType` becomes `"video_job.queued.v2"`, matching the new routing key — the two are one vocabulary and `videojob-messaging` pins them equal. This is the change that actually isolates the generations, so comment it there and not only in the topology file: the old relay's claim is a literal it can never match, which is the only property that works against an already-deployed relay.
- [x] 2.3 `schema.sql`: the cutoff migration — `UPDATE video_job_outbox SET published_at = now() WHERE event_type = 'video_job.queued' AND published_at IS NULL`, scoped to the **previous** generation's literal. Comment what it is and is not: it records a boundary the event-type scoping already enforces, so a version written against "any unpublished dispatch row" would stamp live work as published and drop it silently. Guard it so it runs once and cannot match rows written afterwards.
- [x] 2.4 `repository.go`: round-trip `content_hash` through `Create`, `FindByID`, `FindByUserID`, and `FindCompletedByUserID`. A pre-migration row must load with an empty value, not error.
- [x] 2.5 `repository.go`: `ClaimForProcessing` — one statement, `UPDATE video_jobs SET status = 'processing' WHERE id = $1 AND status = 'queued'`, returning rows-affected. Not a transaction, not a `SELECT` then an `UPDATE`, and no row lock held past the statement: the caller runs a multi-minute extraction next. Distinguish "no row matched because the status differs" from "no row matched because the id does not exist" — a second lookup on zero rows affected is the straightforward way, and the comment should say why the distinction matters (dead-letter classification).
- [x] 2.6 `internal/video/infrastructure/cache/repository.go`: add `ContentHash` to `cachedJobRecord`, `newCachedJobRecord`, and `toVideoJob`. Same non-optional plumbing argument as `SourceKey`: the record mirrors the column set exactly, and a dropped content hash leaves a failed job's idempotency key unclearable.
- [x] 2.7 `cache/repository.go`: implement `ClaimForProcessing`. Write through **only when a row was affected**. A lost claim changed nothing in PostgreSQL, and writing the caller's in-memory `processing` job would overwrite the winner's entry on behalf of the loser. Do not pass it through uncached.
- [x] 2.8 `internal/video/infrastructure/idempotency/redis_store.go`: implement `ClearByJob` as a Lua script comparing the stored value's job-ID suffix (`final:<token>:<jobID>`) and deleting only on a match, matching the existing `clearScript`'s shape. An unfinalized `reserved:` value must never match. An absent key reports `false`, not an error.

## 3. Application layer

- [x] 3.1 `start_processing.go`: persist via `ClaimForProcessing` instead of `Update`. **Two paths reach the lost claim and both must return the sentinel.** The common one happens before any write: the use case loads the job first, and `job.StartProcessing()` rejects a `processing`/`completed`/`failed` job with an invalid-transition error that knows nothing about claims — map that to the sentinel. The rare one is the race after the read, where `ClaimForProcessing` reports no row affected. A `pending` job is **not** a lost claim: it was never dispatched, so it stays an ordinary error, and collapsing the two would hide the anomaly behind the routine case. Do not retry, do not call `FailJob`, do not mutate the job on either path.
- [x] 3.2 `process_video_job.go`: propagate the lost-claim sentinel unchanged from its `StartProcessing` call. It already returns early on a `StartProcessing` error; the task is to make sure that path stays free of `FailJob` and of the source download, and to say so in the doc comment — the "uniform error handling" refactor that turns this into a failure is exactly what the spec forbids.
- [x] 3.3 `create_video_job.go`: `CreateVideoJobInput` gains `ContentHash`, passed through to `NewVideoJob`. Empty stays valid — `POST /api/video-jobs` has no content.
- [x] 3.4 New use case or store call for clearing a failed job's key by job reference, wherever it composes most cleanly for the worker to invoke after a `failed` outcome. Derive the key with the **same** function `handleVideoUpload` uses (`domain.NewIdempotencyKey`), not a re-implementation.

## 4. Messaging: generation and consumer

- [x] 4.1 `internal/video/infrastructure/messaging/topology.go`: `ExchangeJobs` becomes `video.jobs.v2`, `QueueJobs` `video.jobs.queued.v2`, and `RoutingKeyJobQueued` `video_job.queued.v2` — the routing key moves too, and task 2.2's outbox constant moves with it. Dead-letter names unchanged. Rewrite the comment block on both counts: the reason for a generation is the rolling-deploy window in which an old inline replica's cleanup would delete the source out from under a new worker's extraction (not stale residue, which the conditional claim already neutralizes), and the reason the *event type* carries the generation is that every replica's relay claims from one outbox table by that string — the exchange alone isolates nothing, because the crossing happens before anything is published. Both reasons are absent from `docs/roadmap.md`, so the code is where they have to live until finalization corrects it.
- [x] 4.2 `internal/video/infrastructure/messaging/consumer.go` (new): a `Consumer` over an `internal/platform/rabbitmq` connection — declares the topology, sets `Qos(prefetch: 1)`, consumes with manual ack, and hands each delivery to a callback that returns an ack/reject decision. Keep it free of use-case knowledge, mirroring how `Publisher` is free of outbox knowledge; the decision table lives in `cmd/worker`.
- [x] 4.3 If `internal/platform/rabbitmq` needs a helper for consuming (QoS, `Consume`, or a channel-lifecycle wrapper), add it there — and check it against that package's two enforcement tests: no import outside `internal/platform/`, and no context name (`video.jobs`, `video_job.`) in non-test source.

## 5. `cmd/worker`

- [x] 5.1 `cmd/worker/main.go`: composition root wiring the Video Processing PostgreSQL pool (+ migrations), MinIO source and result storage, Redis (idempotency store and the status-cache decorator), and the broker. **No identity, no router, no rate limiter, no outbox relay.** Fail fast and exit non-zero on unreachable PostgreSQL or MinIO; dial the broker with retry rather than treating it as a startup gate.
- [x] 5.2 The per-message decision table from `design.md` Decision 8, one place, explicit: processed to terminal → ack; unparseable payload, unknown job, lost claim, or infra error mid-run → reject **without requeue**. No path acks a message it did not process.
- [x] 5.3 On a terminal outcome for a job it claimed: `CompleteJob` on success only (never `FailJob` — `ProcessVideoJob` already did it), then delete the source object, then — if the job ended `failed` — clear its idempotency key.
- [x] 5.3a Retry the terminal write a bounded number of times with backoff, on a detached context. `CompleteJob` returns its repository error and leaves the job in `processing`, so a transient database blip at that moment produces a durable result no listing shows — and one more attempt costs nothing next to a re-extraction. If it still will not commit: reject without requeue, log the job ID and the result `StorageKey`, keep the source, and do not ack.
- [x] 5.3b **Gate the source deletion on a committed terminal state, not on having won the claim.** A `defer` registered at claim time looks like the careful version and is the dangerous one: a panic, a terminal write that never commits, or an expired shutdown deadline each leave the job in `processing`, and those bytes are the only thing a later fenced takeover could finish it from. Deleting them turns a recoverable job into one that can only be failed. Leaking is the better outcome — the lifecycle rule reclaims a leaked object, nothing reclaims a deleted one. A lost claim likewise deletes nothing.
- [x] 5.4 Graceful shutdown on `SIGINT`/`SIGTERM`: cancel the consumer so no new delivery is taken, wait for the in-flight job to reach terminal and be acked, then close the broker, PostgreSQL, and Redis handles. Bound the wait; on expiry, log the in-flight job ID and exit anyway. Note in a comment why abandoning is worse than waiting — the redelivery cannot re-claim a `processing` row, so an abrupt exit strands the job.
- [x] 5.5 Redial and redeclare the topology on every successful dial, the same posture as the relay: nothing else declares it, so a recreated broker would otherwise leave the consumer bound to nothing.

- [x] 9.7 The generation bump is asserted, not assumed: `JobDispatchTopology()` returns the `.v2` names, and a message published to a `.v1`-shaped exchange is not delivered to the `.v2` queue.

- [x] 9.9 Generation isolation at the claim, which is where it actually lives: with unpublished rows under both the old and the new dispatch event type in one table, a relay configured for the new generation claims only the new ones. - [x] 9.10 Worker lifecycle, which nothing else covers: graceful shutdown finishes the in-flight job and acks it before exiting; no further job is claimed after the signal; the shutdown deadline expires cleanly and logs the in-flight job ID; and a reconnect after the broker is restarted redeclares the topology and resumes consuming. These paths decide whether a restart strands a claimed job, so they are not optional coverage.
- [x] 9.11 The terminal-write failure path: with the repository failing only the `CompleteJob` write, the job stays `processing`, the source object survives, the message is dead-lettered rather than acked, and the job ID and result key are logged.
