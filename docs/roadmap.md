# Roadmap

FIAP X evolves from the current synchronous monolith (`main.go`) into a fully structured DDD system across exactly **8 phases**. Each phase decomposes into one or more focused OpenSpec changes — see [Change Backlog](#change-backlog) below for the concrete, right-sized units and their order. A phase is a grouping for human understanding, not a promise that it ships as a single change.

> **Canonical source:** The authoritative roadmap — including full scope descriptions, ADRs, dependency rules, and the complete domain model — lives in [`openspec/specs/ddd-architecture/spec.md`](../openspec/specs/ddd-architecture/spec.md). Phase 2's own scope is likewise authoritative in [`openspec/specs/identity-authentication/spec.md`](../openspec/specs/identity-authentication/spec.md).
>
> This file is a summary for human readers. If the Phase Summary or any architecture/target-state description below conflicts with the canonical source, the canonical source takes precedence.
>
> The **Change Backlog** section below is different: it's a planning/sequencing artifact with no counterpart in `openspec/specs/` — canonical specs describe target system behavior, not the order in which OpenSpec changes get proposed. It can't "conflict" with the canonical source in the same sense; it's authoritative for change sequencing in its own right. See [`openspec/specs/development-workflow/spec.md`](../openspec/specs/development-workflow/spec.md) for how it's maintained.

## Current State (Phases 1–4 done)

Phase 1 established the architectural foundation — bounded contexts, aggregate design, ADRs, dependency rules, and this documentation — without touching any application code.

Phase 2 added the first executable bounded context: `internal/identity/{domain,application,infrastructure}`, PostgreSQL-backed user registration and login, JWT bearer authentication, and per-artifact ownership enforcement for uploads/downloads/status. Identity configuration (`IDENTITY_POSTGRES_DSN`/`IDENTITY_JWT_SIGNING_KEY`) is mandatory at startup — the server fails to start rather than falling back to unauthenticated video processing (see `enforce-mandatory-identity-config` in the Change Backlog above, correcting the opt-in behavior Phase 2 originally shipped with). The composition root is now `cmd/api` (Phase 3's `extract-cmd-api-entrypoint`, see the Change Backlog above), not the repo-root `main.go` Phase 2 originally wired into. See [docs/architecture.md](architecture.md) for the current request flow and [docs/operations.md](operations.md) for the identity configuration.

Phase 3 is done. `internal/video/domain` and `application` are fully built: `CreateVideoJob`/`GetJobStatus`/`ListUserJobs` plus the state-transition use cases `EnqueueVideoJob`/`StartProcessing`/`CompleteJob`/`FailJob` and a `ProcessVideoJob` orchestration use case, all wired into `cmd/api` (`VIDEO_POSTGRES_DSN` is mandatory at startup, alongside the `IDENTITY_*` variables). Two HTTP-reachable paths use this layer: `POST /api/video-jobs`/`GET /api/video-jobs/:id`/`GET /api/video-jobs` (a preview job-lifecycle API, wired by `wire-videojob-http-endpoints`) and the legacy `POST /upload` (its `ffmpeg` call migrated into this application layer by `migrate-ffmpeg-execution-to-videojob-application`, still fully synchronous — no queue/worker until Phase 6). `POST /api/video-jobs` still gives a created job no processing trigger — `migrate-ffmpeg-execution-to-videojob-application` drives `EnqueueVideoJob`/`StartProcessing`/`CompleteJob`/`FailJob` from `/upload`, not from that endpoint — so a job created directly via `POST /api/video-jobs` still stays `pending` forever; giving it its own trigger would need a separate, not-yet-proposed future change. Because `/upload` and `/api/video-jobs` share the same `VideoJob` repository, `GET /api/video-jobs`/`GET /api/video-jobs/:id` do show real `completed`/`failed` jobs for a user who has used `/upload`. The frontend keeps using `POST /upload` exclusively; it does not consume `/api/video-jobs`.

Phase 4 is done: `internal/platform/redis` (`add-redis-infrastructure`) provides connection plumbing, and all three of its planned features are wired in — idempotency keys on `POST /upload` (`add-upload-idempotency-keys`), per-user rate limiting on every authenticated route (`add-rate-limiting-middleware`), and a cache-aside/write-through status cache for `VideoJob` lookups (`add-videojob-status-cache`), decorating the PostgreSQL repository ahead of `GetJobStatus`'s repeated `GET /api/video-jobs/:id` polling reads. PostgreSQL remains authoritative on any cache miss. A design correction to the idempotency feature (`fail-open-upload-idempotency`, see Change Backlog) has also shipped: a `Reserve` error now fails open, logging the error and proceeding without dedup protection, matching rate limiting's and the status cache's posture — none of Phase 4's Redis-backed features can block the critical path (video processing) on a Redis outage anymore, though what each one degrades to differs: idempotency and the status cache lose an optimization (bounded extra `ffmpeg`/PostgreSQL cost, no correctness impact), while rate limiting loses its abuse-control enforcement entirely for the outage's duration (requests that should have been rejected are allowed through), not just efficiency.

Phase 5 is complete, and object storage is now load-bearing for every artifact. `add-minio-infrastructure` provided the connection adapter; `migrate-result-storage-to-minio` wired it into `cmd/api` for results; `migrate-upload-storage-to-minio` did the same for uploaded source videos; and `add-presigned-download-urls` took the API out of the result-byte path entirely — `GET /download/:filename` authorizes and issues a five-minute signed URL, and the client fetches the ZIP from MinIO directly. Both `outputs/` and `uploads/` are gone, along with the `.owner` sidecar mechanism in its entirety — artifact ownership comes from the `VideoJob` row, and source objects are never served at all. `temp/` is the only local directory left, holding per-request scratch that is always cleaned up. The four required `VIDEO_MINIO_*` variables are a fail-closed startup precondition: the server refuses to start rather than accepting an upload it cannot store; `VIDEO_MINIO_PUBLIC_ENDPOINT`/`VIDEO_MINIO_PUBLIC_USE_SSL` joined them as optional variables naming the address clients reach the bucket at, which matters because SigV4 signs `Host` and a signed URL's host cannot be corrected after issuance. `ProcessVideoJob` now takes a source storage key rather than a local filesystem path, which is the seam Phase 6's `cmd/worker` depends on — it will not share a filesystem with `cmd/api`. Two consequences of presigned delivery are accepted rather than mitigated and are documented in `docs/operations.md`: an issued URL cannot be revoked before it expires, and result bytes are no longer rate limited, since the transfer never passes through the API. Phases 6–8 remain planned. All of them are sequenced by dependency: each phase safely assumes the prior phase's code is merged. The phases do not need to be fully completed to deliver value — even partial implementation (e.g., through Phase 3 or 4) produces a meaningfully more structured and capable system.
