# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A minimal Go web service ("FIAP X - Processador de Vídeos") that accepts a video upload, extracts frames at 1fps via `ffmpeg`, zips them, and serves the zip back for download. It's the code deliverable for a POSTECH/FIAP hackathon (see `docs/project-requirements.pdf` for the assignment brief — a binary PDF, not readable as text).

The HTTP composition root lives in `cmd/api/main.go` (package `main`), alongside `identity.go` and their `_test.go` files; `internal/identity` and `internal/video` hold the DDD bounded contexts introduced in later phases (see `docs/architecture.md`). CI runs on GitHub Actions (`.github/workflows/ci.yml`); there is no linter config beyond `go vet` and `gosec`.

## Development workflow

No development methodology is mandatory. Changes may be implemented directly; OpenSpec is used only when the developer explicitly requests it, invokes an `/opsx:*` command, or continues a named active OpenSpec change. Selecting OpenSpec activates its full lifecycle through the `change-lifecycle` skill; the size or complexity of a direct request does not activate it.

Quality and delivery requirements apply independently of methodology. `main` has no direct pushes, and every PR is gated by `Build & Test`, `SAST (gosec)`, and `Vulnerability Scan (govulncheck)`. The `repo-workflow` skill applies whenever a developer requests a PR action or the agent creates a PR. Full quality-gate, branch-protection, review, merge-authorization, commit, and release rules live in `docs/development.md`.

One rule worth restating: **`go test ./... -v` must pass locally before reporting a change complete whenever the diff includes a Go module input (`.go`/`go.mod`/`go.sum`)** — tests require `ffmpeg` on `PATH` **and** a reachable MinIO configured through `VIDEO_MINIO_*`, or run via `docker compose run --build --rm app-test go test ./... -v`, which supplies both.

## Commands

```bash
go run ./cmd/api        # run the server directly (listens on :8080)
go build -o app ./cmd/api  # build a binary
go mod tidy             # sync go.mod/go.sum after dependency changes
go test ./... -v        # integration suite (requires ffmpeg on PATH and MinIO via VIDEO_MINIO_*; exits 1 with an error if either is absent)
docker compose up --build   # full stack via Docker (app + PostgreSQL, identity enabled)
```

`ffmpeg` must be installed and on `PATH` — the app shells out to it (`exec.Command("ffmpeg", ...)`) and has no fallback or embedded copy. `cmd/api`'s tests additionally require a reachable MinIO: `main_test.go`'s `TestMain` exits 1 when either `ffmpeg` or the `VIDEO_MINIO_*` configuration is missing, deliberately rather than skipping — `POST /upload` stores its result in a bucket, so a skipped suite would report green while covering none of that. If either is unavailable locally, run tests inside Docker instead: `docker compose run --build --rm app-test go test ./... -v` (`app-test` builds from the `Dockerfile`'s `test` stage — the hardened `app` service's image has no Go toolchain to run tests with). `docker-compose.yml` is the sole documented way to build, run, or test the application via Docker **for local development** — there is no separate plain `docker build`/`docker run` workflow documented for that purpose. Container deployment is a separate, intentionally-retained concern documented in `docs/operations.md`.

## Architecture

Request flow, all in `cmd/api/main.go`, `cmd/api/identity.go`, and `cmd/api/video.go`:

1. `setupRouter(identity, video, limiter)` wires a single `gin` router: no static artifact mounts remain (both `/uploads` and `/outputs` are gone), a permissive CORS middleware (allows `*`), and routes `GET /`, `POST /upload`, `GET /download/:filename`, `GET /api/status`, `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/video-jobs`, `GET /api/video-jobs/:id`, `GET /api/video-jobs`. Every route gated by `identity.requireBearerAuth()` (everything except the two `/api/auth/*` routes and static assets) is also gated by a per-user rate-limit middleware (`internal/platform/ratelimit`, see the rate-limiting bullet below). `main()` calls `setupIdentity`/`setupVideo` then constructs the limiter, then `setupRouter(identity, video, limiter)` then `.Run(":8080")` — the split exists so `main_test.go`/`identity_test.go`/`video_test.go` can drive the real handlers via `httptest.NewServer` without binding the real port.
2. `GET /` serves `cmd/api/web/index.html` (with `cmd/api/web/styles.css` and `cmd/api/web/app.js` at `/styles.css` and `/app.js`), embedded into the binary via `go:embed` — an upload form with vanilla JS (fetch calls to `/upload` and `/api/status`). There is no separate frontend build; editing the UI means editing the files under `cmd/api/web/`. The frontend does not consume `/api/video-jobs` — it keeps using the legacy `/upload` flow exclusively.
3. `POST /upload` (`(*videoModule).handleVideoUpload` in `cmd/api/video.go`) validates the file extension, streams the upload into the bucket under `uploads/<uploadID>_<original-filename>` while hashing it (SHA-256) on the same pass — nothing touches local disk on the way in — reserves a Redis-backed idempotency key scoped to `UserID` + content hash (see the idempotency bullet below), creates a `VideoJob` via `CreateVideoJob`, then runs it through `ProcessVideoJob`. A single `defer`, registered the moment the `Put` succeeds, deletes that source object on every exit path.
4. `ProcessVideoJob` (`internal/video/application`) is the core pipeline: `EnqueueVideoJob` → `StartProcessing` → `SourceStorage.Get` → `FrameExtractor.ExtractFrames` → `ResultStorage.Put`, driving the `VideoJob` from `pending` through `queued`/`processing`. **It takes a source `StorageKey`, not a local path** — a path written by the calling handler only means something to a process sharing that handler's filesystem, and Phase 6's `cmd/worker` will not. It still leaves a successful job in `processing` for `handleVideoUpload` to complete, but that split no longer guards a caller failure branch: storing the result is `ProcessVideoJob`'s own step, so a successful return already means the artifact is durable. `ProcessVideoJob` calls `FailJob` itself if the fetch, the extraction, or the storage step fails. It downloads the source to `temp/<jobID>_source` — no file extension, so no part of that path derives from a user-supplied filename; `ffmpeg` detects the container by probing content — and removes that copy on every path via a `defer` registered *before* extraction. The `ffmpeg` exec/zip work lives in `internal/video/infrastructure/ffmpeg`'s `Extractor`: creates a per-job scratch dir under `temp/<jobID>`, runs `ffmpeg -i <video> -vf fps=1 -y temp/<jobID>/frame_%04d.png` via `exec.CommandContext` (so a canceled request context kills the subprocess), globs the PNGs, zips them into `temp/<jobID>.zip` — beside the frame dir, not inside it, so the `defer os.RemoveAll` can't delete the zip — and returns that local path. `ProcessVideoJob` uploads it under the key `frames_<jobID>.zip` and removes the local copy whether the upload succeeded or not. It does **not** delete the source object — the handler does, since it stored it and reaches exit paths this use case never runs on.
5. `GET /download/:filename` and `GET /api/status` (both `*videoModule` methods in `cmd/api/video.go`) read from the bucket. Download parses the `VideoJobID` out of the requested key, loads the job, and serves the object only if the job belongs to the caller, is `completed`, and records that exact key; every rejection returns a byte-identical `404`. Status lists the caller's `completed` jobs and takes each result's `size` and `created_at` from a `StatObject` — so `created_at` keeps meaning "when the artifact was written", as it did when it was a file's `ModTime`.
6. `POST /api/video-jobs`, `GET /api/video-jobs/:id`, and `GET /api/video-jobs` (all bearer-authenticated, owner-scoped) wrap `internal/video/application`'s `CreateVideoJob`/`GetJobStatus`/`ListUserJobs` use cases — a preview job-lifecycle API, separate from the legacy flow above. A job created *through this API* has no processing trigger and stays `pending` forever; do not present this as a working end-to-end path (see `openspec/specs/videojob-http-api/spec.md`). Because `/upload` also calls `CreateVideoJob`, though, `GET /api/video-jobs`/`GET /api/video-jobs/:id` do show real `completed`/`failed` jobs for a user who has used `/upload` — same aggregate, same repository.

One directory is created at startup (`createDirs`) and used only by the `/upload` flow above — `POST /api/video-jobs` accepts a JSON filename and never touches the filesystem: `temp/`, holding the downloaded source copy, the per-job frame directory, and the zip built from it, all always cleaned up. There is no `uploads/` and no `outputs/`: both source videos and results are objects in the MinIO bucket, separated by key prefix. `VideoJob`s (created via either `/upload` or `/api/video-jobs`) are persisted in PostgreSQL (`VIDEO_POSTGRES_DSN`, required at startup like `IDENTITY_POSTGRES_DSN`).

Processing is synchronous and in-request: `handleVideoUpload` blocks on the full `ProcessVideoJob` sequence (including the `ffmpeg` run and zip creation) before responding. There is no job queue, no async/webhook flow, and no per-request concurrency limiting — large videos or concurrent uploads will hold multiple `ffmpeg` processes at once.

## Language policy: English for new code (as of 2026-07-28)

Code, error messages, and comments in **new or changed code** SHALL be written in English, going forward. This is a change from the project's original convention (see below) — it applies prospectively, not retroactively:

- Do not translate the existing Portuguese (pt-BR) strings already in `cmd/api/main.go` and `cmd/api/web/index.html` (the HTML form, existing JSON `Message`/`error` fields, existing `fmt.Printf`/`log.Printf` calls) just because you're touching a nearby line. Leave them as-is unless a change specifically asks for that.
- Any error message, log line, or other string you add or rewrite from now on should be in English, even inside an otherwise-Portuguese function.
- Comments: default to none. Add one only when it explains something genuinely non-obvious (a hidden constraint, a workaround, a subtle invariant) — not to restate what the code already says. When you do add one, write it in English.
- Exception: new **user-facing UI copy** in `cmd/api/web/index.html` (labels, buttons, status messages shown on the page itself) and user-facing strings in `cmd/api/web/app.js` stay in Portuguese, matching the rest of that page — it's written for the same pt-BR hackathon audience as the existing form, and mixing languages within one UI reads as inconsistent to that audience. This exception is scoped to visible page copy only; error messages, log lines, and comments in the surrounding Go code still follow the English rule above.
- **JSON `Message`/`error` values are Go strings, so the English rule covers them** — the `web/` exception does not reach into `cmd/api/*.go`, even though `app.js` renders `ProcessingResult.Message` straight onto that pt-BR page. Existing pt-BR values stay grandfathered; a value you add or rewrite is English. `handleVideoUpload` therefore carries both languages, and that mix is accepted rather than accidental: translating the grandfathered ones would be the retroactive change this policy explicitly rules out. Stated here because the ambiguity produced a review finding on PR #181 and would otherwise be relitigated by every change that touches one of those strings.

## Notable constraints / gotchas

- The Dockerfile is a multi-stage, non-root build (`builder` → `test` → `runtime`) — it is no longer the intentional single-stage/root anti-pattern this project originally shipped with.
- The app's *existing* user-facing strings (error messages, HTML) are in Portuguese (pt-BR) — this was the original convention for this pt-BR hackathon audience. It's superseded for new code by the language policy above; existing pt-BR strings are grandfathered in and not being retroactively translated.
- File type validation (`isValidVideoFile`) is by extension only (`.mp4 .avi .mov .mkv .wmv .flv .webm`), not content sniffing. `POST /upload` reads the "video" multipart part via a streaming `MultipartReader`/`NextPart` (`videoFilePart` in `cmd/api/video.go`), not `c.Request.FormFile` — `FormFile` calls `ParseMultipartForm` internally, which reads the entire request body before the filename is available, so a large invalid-extension upload would otherwise pay the full transfer cost before being rejected. See `openspec/specs/upload-file-validation/spec.md`.
- The `.owner` sidecar mechanism is gone entirely — the helpers, the suffix constant, and both middlewares. No artifact class uses it: results derive ownership from the `VideoJob` row, and source objects are never served at all.
- `handleDownload` no longer touches the filesystem: the requested `:filename` must parse as `frames_<jobID>.zip`, and the job it names must belong to the caller, be `completed`, and record that exact key. `handleStatus` never accepts a caller-supplied name at all. The **result** key deliberately contains no `/` — `cmd/api/web/app.js` uses it verbatim as that route's single path segment, and a `%2F` would break the match, so per-user or per-date prefixes on results are not possible without a frontend change. **Source** keys do carry an `uploads/` prefix, for exactly the complementary reason: no route exposes them. Anything that re-exposes source objects over HTTP has to drop that prefix in the same change.
- Both uploaded source videos and processed results live in the MinIO bucket, not on local disk — `internal/video/domain.SourceStorage` and `ResultStorage`, implemented by the two adapters in `internal/video/infrastructure/storage` over one client and one bucket. Source keys carry an `uploads/` prefix; result keys are flat. **Source objects are transient**: each `POST /upload` deletes its own before the request finishes, on success and failure alike, through one `defer` registered the moment the `Put` succeeds. That deletion is best effort — one call, no retry — so a failure is logged with the key and does not fail the request; `docs/operations.md` documents the recommended `uploads/`-prefix lifecycle rule as the operator-side backstop. See `openspec/specs/videojob-source-storage/spec.md`. `VIDEO_MINIO_ENDPOINT`/`ACCESS_KEY`/`SECRET_KEY`/`BUCKET` are **required at `cmd/api` startup** (`VIDEO_MINIO_USE_SSL` stays optional): `setupVideo` loads, opens, pings, and ensures the bucket, and any failure is fatal. This is **fail-closed**, deliberately unlike every Redis-backed feature below — those degrade to a slower but correct system, whereas a result that cannot be stored cannot be delivered. `GET /download/:filename`'s entitlement lookup deliberately uses the *undecorated* PostgreSQL repository rather than the cached one, so a stale `processing` cache entry can't 404 a result `GET /api/status` is already listing. See `openspec/specs/videojob-result-storage/spec.md`.
- `POST /upload` deduplicates by content: identical bytes uploaded twice by the same authenticated user reuse the first request's `VideoJob` instead of running `ffmpeg` again (`internal/video/domain.IdempotencyStore`, backed by Redis via `internal/video/infrastructure/idempotency.RedisStore`). This requires `REDIS_ADDR` at `cmd/api` startup, alongside the existing `IDENTITY_*`/`VIDEO_POSTGRES_DSN` variables. A `Reserve` error (Redis unreachable/erroring, as opposed to a normal reservation conflict) fails open: the handler logs it and proceeds without a reservation rather than blocking the upload, matching rate limiting's and the status cache's fail-open posture. See `docs/architecture.md`'s Request pipeline section and `openspec/specs/upload-idempotency/spec.md` for the full protocol.
- Every authenticated route is also rate limited per user: a Redis-backed fixed-window counter (`internal/platform/ratelimit`, mounted as `cmd/api/ratelimit.go`'s `rateLimitMiddleware` on the `videoRoutes` group, right after `requireBearerAuth()`) rejects excess requests with `429` + `Retry-After` before any handler runs. Configurable via optional `RATE_LIMIT_MAX_REQUESTS`/`RATE_LIMIT_WINDOW_SECONDS` (defaults 60/60s) — unlike `REDIS_ADDR`, these are not required at startup. A limiter failure (including its own bounded internal timeout) fails open rather than blocking the request. See `openspec/specs/rate-limiting/spec.md` for the full protocol.
- `GetJobStatus`/`ListUserJobs`/the four state-transition use cases all read and write `VideoJob`s through `internal/video/infrastructure/cache.CachedVideoJobRepository`, a decorator wired into `setupVideo` ahead of the PostgreSQL adapter — `FindByID` is cache-aside (Redis `SET NX` on miss-repopulation, never a plain `SET`, so a slow reader can't clobber a fresher concurrent write), `Update` is write-through (unconditional `SET` after the PostgreSQL write succeeds). No new required/optional env var — the cache TTL is a fixed 5-minute constant. See `openspec/specs/videojob-status-cache/spec.md` for the full protocol.
