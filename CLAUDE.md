# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Go service ("FIAP X - Processador de Vídeos") that accepts a video upload, extracts frames at 1fps via `ffmpeg`, zips them, and hands back a presigned URL. Processing is **asynchronous** and the HTTP surface is **split one service per bounded context** behind an nginx gateway: `cmd/identity-api` issues tokens, `cmd/video-api` accepts and reports, `cmd/notification-api` holds delivery preferences, `cmd/worker` extracts, and `cmd/notifier` announces the outcome to whatever webhook the job's owner registered. It's the code deliverable for a POSTECH/FIAP hackathon (see `docs/project-requirements.pdf` for the assignment brief — a binary PDF, not readable as text).

There are **five** composition roots, all package `main`: `cmd/identity-api/{main,identity,logging,probes,readiness}.go`, `cmd/video-api/{main,video,auth,ratelimit,logging,probes,readiness}.go`, `cmd/notification-api/{main,notification,auth,ratelimit,logging,probes,readiness}.go`, `cmd/worker/{main,sweeper,logging}.go`, and `cmd/notifier/{main,deliverer,logging}.go`, each with its own `_test.go` files. **`cmd/api` is gone** — any path naming it is stale. Because `package main` cannot import `package main`, the bearer-auth and rate-limit middlewares are one thin copy per **authenticated** HTTP service over the unchanged shared packages (`internal/identity/infrastructure/jwtauth`, `internal/platform/ratelimit`) — that is `cmd/video-api` and `cmd/notification-api` only; `cmd/identity-api` mounts neither, because its two routes are how a caller obtains a token and gating them would be circular. The duplication is deliberate and bounded at two copies, and each copy carries the tests that can catch it regressing. `probes.go` and `readiness.go` are copied across **three** for the same `package main` reason, and the pair splits in a way worth knowing: `probes.go` is **byte-identical** across the three, while `readiness.go` is deliberately not — it holds each service's readiness matrix, and only `cmd/video-api`'s has two entries. A drift in the first is a defect; a difference in the second is the design. `internal/contracts` holds the cross-context pins, because after the split **no composition root links both Video Processing and Notification** — each HTTP root still imports Identity's verifier port and JWT adapter, which an authenticated route needs by construction, but nothing links the two copies of the terminal contract that the pins compare. `internal/identity`, `internal/video`, and `internal/notification` hold the DDD bounded contexts introduced in later phases, `internal/platform` the cross-cutting plumbing — the connection adapters, and since `add-structured-logging` the shared logger every root installs (see `docs/architecture.md`). CI runs on GitHub Actions (`.github/workflows/ci.yml`); there is no linter config beyond `go vet` and `gosec`.

## Development workflow

No development methodology is mandatory. Changes may be implemented directly; OpenSpec is used only when the developer explicitly requests it, invokes an `/opsx:*` command, or continues a named active OpenSpec change. Selecting OpenSpec activates its full lifecycle through the `change-lifecycle` skill; the size or complexity of a direct request does not activate it.

Quality and delivery requirements apply independently of methodology. `main` has no direct pushes, and every PR is gated by `Build & Test`, `SAST (gosec)`, `Vulnerability Scan (govulncheck)`, and `Container Image Build`. The `repo-workflow` skill applies whenever a developer requests a PR action or the agent creates a PR. Full quality-gate, branch-protection, review, merge-authorization, commit, and release rules live in `docs/development.md`.

One rule worth restating: **`go test ./... -v` must pass locally before reporting a change complete whenever the diff includes a Go module input (`.go`/`go.mod`/`go.sum`)** — tests require `ffmpeg` on `PATH` **and** a reachable MinIO configured through `VIDEO_MINIO_*`, or run via `docker compose run --build --rm app-test go test ./... -v`, which supplies both.

## Commands

```bash
go run ./cmd/identity-api      # tokens: POST /api/auth/register, /api/auth/login (listens on :8080)
go run ./cmd/video-api        # frontend, /upload, /download, /api/status, /api/video-jobs (also :8080)
go run ./cmd/notification-api # GET/PUT /api/notification-preferences (also :8080)
go run ./cmd/worker     # run the worker (no HTTP, no port) — WITHOUT IT NOTHING IS PROCESSED
go run ./cmd/notifier   # run the notifier (no HTTP, no port) — WITHOUT IT NOTHING IS DELIVERED ON EITHER CHANNEL
go build -o identity-api ./cmd/identity-api && go build -o video-api ./cmd/video-api && go build -o notification-api ./cmd/notification-api && go build -o worker ./cmd/worker && go build -o notifier ./cmd/notifier  # build all five binaries
go mod tidy             # sync go.mod/go.sum after dependency changes
go test ./... -v        # integration suite (requires ffmpeg on PATH, MinIO via VIDEO_MINIO_*, and RABBITMQ_URL to be set; cmd/video-api's TestMain exits 1 with an error if any is absent, and it is the only TestMain of the five that gates on anything. RABBITMQ_URL only has to be set, not reachable — cmd/video-api doesn't require a live broker either. A reachable broker via RABBITMQ_TEST_URL is a prerequisite for full coverage only — internal/platform/rabbitmq's and internal/video/infrastructure/messaging's tests skip cleanly without it, so the suite still passes while covering none of those packages. NOTIFICATION_POSTGRES_TEST_DSN is the same kind of coverage-only prerequisite: internal/notification/infrastructure/postgres skips without it, and its "create with no secret is refused" rule is enforced by a row count against a real database, so a skipped run covers none of it. NOTIFICATION_POSTGRES_DSN is deliberately NOT in the TestMain gate and not needed to run tests — no test in any composition root calls setupNotification, setupIdentity, or setupVideo; every one builds its modules by hand. cmd/notifier's tests need nothing at all: they drive setupNotifier's failure paths and run's shutdown branches over injected functions)
docker compose up --build   # full stack via Docker (gateway + the three HTTP services + three workers + notifier + PostgreSQL + Redis + MinIO + RabbitMQ + a Mailpit mail catcher). Two host ports, both loopback: the gateway on 127.0.0.1:8080 for the application, and the mail catcher's inbox on 127.0.0.1:8025 — a development-only support service, so it publishes its own rather than taking a gateway route
```

`ffmpeg` must be installed and on `PATH` — `cmd/worker` shells out to it (`exec.CommandContext("ffmpeg", ...)`) and has no fallback or embedded copy. No HTTP service runs it, but the test suite does. `cmd/video-api`'s tests additionally require a reachable MinIO: `main_test.go`'s `TestMain` exits 1 when either `ffmpeg` or the `VIDEO_MINIO_*` configuration is missing, deliberately rather than skipping — `POST /upload` stores its result in a bucket, so a skipped suite would report green while covering none of that. If either is unavailable locally, run tests inside Docker instead: `docker compose run --build --rm app-test go test ./... -v` (`app-test` builds from the `Dockerfile`'s `test` stage — the hardened `runtime` image every application service uses has no Go toolchain to run tests with). **`--build` is not optional**: the `test` stage copies the source at image-build time, so without it a stale image runs old code and reports green.. `docker-compose.yml` is the sole documented way to build, run, or test the application via Docker **for local development** — there is no separate plain `docker build`/`docker run` workflow documented for that purpose. Container deployment is a separate, intentionally-retained concern documented in `docs/operations.md`.

## Architecture

Request flow across **five** composition roots — `cmd/identity-api`, `cmd/video-api`, `cmd/notification-api`, `cmd/worker/{main,sweeper,logging}.go` and `cmd/notifier/{main,deliverer,logging}.go` — behind one nginx gateway:

0. **The gateway (`docker/nginx/nginx.conf`) is the only *application* process publishing a host port** — the compose stack's mail catcher publishes its own inspection port, a development-only support service that serves no application route and exists in no deployment — and it routes by path prefix: `/api/auth/` → `identity-api`, `/api/notification-preferences` → `notification-api`, `/` (everything else, including the frontend) → `video-api`. A client sees one origin, which is why `app.js` was not modified by the split. Three settings are load-bearing rather than tuning: `client_max_body_size 0` (nginx's 1 MB default would 413 an upload before the extension check ran), `proxy_request_buffering off` (otherwise nginx spools the whole body to its own disk — the local-disk write `POST /upload` exists not to make), and `proxy_http_version 1.1` (an HTTP/1.0 upstream has no chunked encoding, so nginx would silently fall back to buffering). Each `location` holds its upstream in a `set $backend` **variable**, because a literal hostname in `proxy_pass` is resolved once at config load and cached for the worker's life — recreating a backend would then send traffic to a dead address. `set` is per-`location`, so every block declares its own. The trailing slashes differ deliberately: `/api/auth/` has routes beneath it, `/api/notification-preferences` **is** the resource and has none.

1. **Each HTTP service wires its own `gin` router** — `gin.New()`, never `gin.Default()`, with `gin.SetMode(gin.ReleaseMode)` called in `main()` *before* `setupRouter`, since route registration is itself what prints `[GIN-debug]` lines — and all three listen on `:8080` inside their own container. `cmd/identity-api`'s `setupRouter(identity)` mounts `POST /api/auth/register` and `POST /api/auth/login` with **no** bearer group and **no** limiter — they are how a caller obtains a token, so gating them would be circular. `cmd/video-api`'s `setupRouter(auth, video, limiter)` mounts `GET /`, `/styles.css`, `/app.js` outside any group and `POST /upload`, `GET /download/:filename`, `GET /api/status`, `POST /api/video-jobs`, `GET /api/video-jobs/:id`, `GET /api/video-jobs` on a group carrying `auth.requireBearerAuth()` then `rateLimitMiddleware`. `cmd/notification-api`'s `setupRouter(auth, notification, limiter)` mounts the two preference routes on a group carrying that same pair in that same order. **The middleware pair and its order are the invariant, not the group**: the limiter keys on the authenticated subject, so it has nothing to key on ahead of the middleware that establishes one. No static artifact mounts remain anywhere (`/uploads` and `/outputs` are both gone). **`GET /health` and `GET /ready` are mounted on the engine in all three, outside the bearer group and outside the limiter, and that is the invariant being honoured rather than broken**: the limiter keys on the authenticated subject, a probe carries none, and a probe issued at a fixed interval from inside the limiter would eventually be answered `429` — the limiter manufacturing the outage it exists to have no part in. `/health` consults nothing and always answers `200`; `/ready` consults that service's readiness dependencies (PostgreSQL everywhere, plus MinIO's configured bucket on `cmd/video-api`, and **neither Redis nor RabbitMQ anywhere**, because every feature over Redis fails open and `POST /upload` answers `202` with the broker down). Both bodies are fixed per verdict and written with `c.Data`, not `c.JSON`, so nothing acquires a field later; both carry `Cache-Control: no-store`; and neither names the failing dependency — that goes to the log. The criterion is **cited, not invented**: it is the one `docker-compose.yml` already applies to the gateway's own healthcheck — a component is healthy when it can serve, and tying its health to a backend's would make an unrelated service's restart look like an ingress failure. The gateway refuses both paths with exact-match `location = … { return 404; }` blocks that proxy nothing, so a probe is answered on a service's own `:8080` from inside the network and never through the ingress; status-code equivalence with an unserved path is the requirement, not a byte-identical body, because `proxy_intercept_errors on` would rewrite every upstream `404` including `GET /download/:filename`'s deliberate one. Each check is bounded at 2s off the request context and **that bound must stay strictly below the prober's own timeout** (5s in the compose healthchecks): reversed, every verdict becomes a failure whatever the dependency is doing, with nothing in the output saying so. The CORS middleware is **byte-identical** across the three, deliberately — a browser reaches all of them through one origin, so a per-path policy would make the split observable to a client for the first time; it advertises `GET, POST, PUT, OPTIONS`, and `PUT` is there for the preference write and nothing else. Every `main()` installs the process logger first (see the logging paragraph below), then builds its modules, then its router, then serves through an explicit `http.Server` under a `signal.NotifyContext(SIGINT, SIGTERM)` — the split between `main` and `setupRouter` exists so each service's `_test.go` files can drive the real handlers via `httptest.NewServer` without binding the real port. **Shutdown ordering is load-bearing and not alphabetical in exactly one service**: `cmd/video-api` does `server.Shutdown` → cancel the outbox relay → **join** its goroutine → close the video PostgreSQL pool → close Redis, because the relay holds a database transaction while it runs and closing the pool before joining would abort an in-flight claim instead of resolving it. `cmd/identity-api` and `cmd/notification-api` have no such constraint and say so in their own comments: nothing there borrows a connection for a whole operation, so once `Shutdown` returns every statement those processes will ever run has finished. MinIO is deliberately absent from every sequence — that adapter exposes no teardown. **`cmd/worker` has the same shape as the Video API for the same reason**: `run` cancels and joins the recovery sweeper, then cancels and joins its terminal-event relay, before dependencies close, then waits for the consumer goroutine to finish the delivery in hand (bounded by a 5-minute drain), and only then are PostgreSQL and Redis closed — the sweeper, the relay, and the handler each borrow them for a whole operation. The relay is stopped wherever its current cycle stands rather than drained to empty: a committed but unpublished terminal row is picked up by a later cycle, in this worker or another.
2. `GET /` serves `cmd/video-api/web/index.html` (with `cmd/video-api/web/styles.css` and `cmd/video-api/web/app.js` at `/styles.css` and `/app.js`), embedded into the binary via `go:embed` — an upload form with vanilla JS. There is no separate frontend build; editing the UI means editing the files under `cmd/video-api/web/`. It still submits to `/upload`, but a `202` carries no result, so `app.js` now **polls** the `status_url` the response names (`GET /api/video-jobs/:id`, 2s initial interval, ×1.5 backoff, 10s cap) until the job reports `completed` or `failed`, then reads `/api/status` for the artifact. So the frontend does consume the job-lifecycle API for reads — what it never does is *create* a job through `POST /api/video-jobs`.
3. `POST /upload` (`(*videoModule).handleVideoUpload` in `cmd/video-api/video.go`) validates the file extension, streams the upload into the bucket under `uploads/<uploadID>_<original-filename>` while hashing it (SHA-256) on the same pass — nothing touches local disk on the way in — reserves a Redis-backed idempotency key scoped to `UserID` + content hash (see the idempotency bullet below), creates a `VideoJob` via `CreateVideoJob` (carrying that source key **and** the content hash), calls `EnqueueVideoJob` — which commits the `pending → queued` update and a `video_job.queued.v2` outbox row in one transaction — finalizes the reservation, and returns **`202 {job_id, status, status_url}`**. It does **not** call `ProcessVideoJob`, `StartProcessing`, `CompleteJob`, or `FailJob`; no extraction happens in the request, and the body carries no frame count, result key, or download URL because none exists yet. Finalize runs *after* the enqueue, not before — the ordering is specified (`upload-idempotency`), because finalizing first would advertise a job stuck in `pending` for the full 24h window. An `EnqueueVideoJob` failure is handled like a `CreateVideoJob` failure: clear the reservation, `500`, no dispatch. A single `defer`, registered the moment the `Put` succeeds and **guarded on whether the enqueue committed**, deletes that source object only on the paths where the job never reached `queued` — after the enqueue the object is the worker's input and must survive. A duplicate is answered with the same `202` shape naming the existing job, whatever state it is in, so a client needs no duplicate branch.
4. `cmd/worker` consumes `video.jobs.queued.v2` (prefetch **1**) and runs each dispatch to a terminal state. `internal/video/infrastructure/messaging.Consumer` owns only the plumbing — dial, redeclare the topology on every dial, `Ack`/`Reject` a `Handler`'s verdict, requeue on exactly one path (a delivery pulled off the channel after shutdown, before any work). `cmd/worker/main.go`'s `handle` holds the decision table: undecodable body, missing source key, unknown job, lost claim, a run that broke before a terminal commit, and a terminal write refused by the fence all `Reject` to the DLQ, never requeue. The fenced case is distinct: work ran but this actor did not win the terminal outcome (because the epoch advanced or another actor finished first at the same epoch), so the worker keeps the source object and idempotency key, releases no lease, and logs its held epoch plus any result key. A failure this run committed is **acked** after deleting the source, clearing the idempotency key, and releasing its epoch-scoped lease; an identical failure already present is acked without cleanup. A success calls `CompleteJob`, retried 4× with backoff on a context detached from shutdown, then performs the same source/lease cleanup and acks. If completion still will not commit, it rejects and keeps the source. The handler runs on `context.WithoutCancel`, so shutdown never kills a running `ffmpeg` or aborts the terminal write. Alongside the consumer, `cmd/worker/sweeper.go` scans bounded, keyset-paginated batches of `processing` jobs and requeues one only after two successful observations that its lease is absent at the same epoch; a Redis query error for that job clears its confirmation and takes over nothing.
5. `ProcessVideoJob` (`internal/video/application`) is the core pipeline the worker calls: `StartProcessing` → acquire/renew lease → `SourceStorage.Get` → `FrameExtractor.ExtractFrames` → `ResultStorage.Put`. **`StartProcessing` is an atomic conditional claim** — `Repository.ClaimForProcessing` runs `UPDATE video_jobs SET status='processing' WHERE id=$1 AND status='queued' RETURNING lease_epoch`; affecting no row returns `ErrJobClaimLost`, which `ProcessVideoJob` propagates without touching the source or job. The literal `queued` predicate remains the Redis-independent correctness primitive. Recovery is separate: a sweeper moves an unleased `processing` row back to `queued`, increments `lease_epoch`, and records a new outbox dispatch transactionally. `ProcessVideoJob` carries the claimed epoch into its own `FailJob` and its result; `CompleteJob`/`FailJob` write only while the row is still `processing` at that epoch, otherwise returning `ErrJobFenced`; the applied write also commits the job's terminal outbox event in the same transaction (see the outbox bullet below). The lease heartbeat fails open and reacquires a missing equal-epoch lease after Redis recovers, but refuses a newer holder. The use case does **not** enqueue or delete the source object. It downloads the source to `temp/<jobID>_source`, removes it on every path, extracts through `internal/video/infrastructure/ffmpeg`, uploads `frames_<jobID>.zip`, and removes the local zip. A successful job remains `processing` for the worker's fenced terminal write, because that commit licenses the acknowledgement.
6. `GET /download/:filename` and `GET /api/status` (both `*videoModule` methods in `cmd/video-api/video.go`) read from the bucket. **Download does not serve bytes**: it parses the `VideoJobID` out of the requested key, loads the job, and — only if the job belongs to the caller, is `completed`, and records that exact key — `Stat`s the object and returns `200 {"url", "expires_at"}` carrying a 5-minute presigned URL the client redeems against MinIO directly. That `Stat` is load-bearing, not vestigial: signing is offline and succeeds for a key holding no object, so without it a missing object would surface as MinIO's own XML `404` at a different origin. Because an issued URL carries no identity, that entitlement check is the *complete* authorization decision, and the URL cannot be revoked before it expires — treat it as a credential (never logged, echoed, or persisted; log the `StorageKey`). Every rejection returns a byte-identical `404`, and **every** response — success and rejection alike — carries `Cache-Control: no-store`. `expires_at` is read off the URL's own `X-Amz-Date`/`X-Amz-Expires`, never computed as `now + TTL`. Status lists the caller's `completed` jobs and takes each result's `size` and `created_at` from a `StatObject` — so `created_at` keeps meaning "when the artifact was written", as it did when it was a file's `ModTime`.
7. `POST /api/video-jobs`, `GET /api/video-jobs/:id`, and `GET /api/video-jobs` (all bearer-authenticated, owner-scoped) wrap `internal/video/application`'s `CreateVideoJob`/`GetJobStatus`/`ListUserJobs` use cases — a preview job-lifecycle API, separate from the legacy flow above. A job created *through this API* has no processing trigger and stays `pending` forever; do not present this as a working end-to-end path (see `openspec/specs/videojob-http-api/spec.md`). Because `/upload` also calls `CreateVideoJob`, though, `GET /api/video-jobs`/`GET /api/video-jobs/:id` do show real `completed`/`failed` jobs for a user who has used `/upload` — same aggregate, same repository.
8. `GET /api/notification-preferences` and `PUT /api/notification-preferences` (both `*notificationModule` methods in `cmd/notification-api/notification.go`, bearer-authenticated and owner-scoped) wrap `internal/notification/application`'s `ListPreferences`/`SetPreference`. A preference is identified by the triple `(UserID, EventType, Channel)` — the pair lives in the **body**, not the path, because a versioned event type (`video_job.completed.v1`) is a poor path segment. `EventType` and `Channel` are closed sets: the two terminal event types, and `webhook` and `email`. The set stays closed at the channels an adapter delivers through, which is the rule that kept `email` out until one existed; `domain.AllChannels()` exposes it so `cmd/notifier` composes exhaustively over it and refuses to boot when a channel has no implementation. The write is a `PUT` because it is idempotent on that triple; a `user_id` in the body is **ignored, not rejected** — the authenticated subject is the only owner, and rejecting a guessed identifier would report whether it exists. An empty read is `200` with an empty array, never `404`. **These preferences are now consumed** — `add-notification-webhook-delivery` shipped `cmd/notifier`, which resolves each terminal event against them (item 9). Absence of a row means *not subscribed* — there is no implicit default and no backfill. `SetPreference` builds the destination through `NewDestinationFor(channel, raw)` — an absolute URL for `webhook`, a single addr-spec address for `email` — and applies the destination policy on the **webhook branch only** (see the destination-policy bullet below), so a destination the notifier could never dial is a `400` at registration rather than a stored row that silently never fires.

9. `cmd/notifier` consumes `video.jobs.terminal.events.v1` (prefetch **1**) and delivers each outcome to the destinations its owner registered. `internal/notification/infrastructure/messaging.Consumer` owns the plumbing — dial with backoff, redeclare the topology on every dial, and apply the handler's verdict — and its disposition set is **three-valued**, deliberately unlike `cmd/worker`'s: `Ack`, `Reject`, and `Requeue` (which pauses before taking the next delivery). `cmd/notifier/main.go`'s `handle` decodes the message, translates its `user_id` into the Notification context's own `UserID` — the sanctioned crossing, and the only one — and calls `internal/notification/application.DeliverNotification`, which loads deliverable preferences, **drops any whose `CreatedAt` is not before the event's `OccurredAt`**, and for each survivor claims, attempts, and resolves. The rule behind the disposition table is *whether this handler has attempted anything yet*, not which error occurred: an undecodable body or an unrecognized event type rejects to the DLQ; **every** pre-attempt repository failure — `FindDeliverable`'s included — and a claim `ClaimHeldByAnother` requeue; everything else acks, including a `ClaimAlreadyResolved`, an exhausted attempt budget recorded as `failed`, a resolve refused by the fence, and an outcome that could not be recorded at all. `ClaimHeldByAnother` requeueing rather than acking looks wrong and is not: a crashed claimant's redelivery arrives within seconds, far inside the reclaim bound, so acking there would strand a `pending` row nothing else will ever meet. The accepted cost is head-of-line blocking bounded by the reclaim bound. Shutdown stops consuming, joins the consumer under a bounded drain (**one `MaxClaimHold()` per channel** in `domain.AllChannels()`, plus a 30s grace — 90s at the documented budget), and closes the pool **only if that join succeeded** — when the drain expires the handler is still running on its `context.WithoutCancel` and can never be joined, so the bound wins and the close is skipped; process exit releases the connections and the unresolved claim is what a later consumer reclaims. The drain is per channel because the triple allows one preference per channel per event type and the handler works through them sequentially, so a message can legitimately consume the whole budget once for each — a drain sized for a single hold would expire during work that is within budget, making the skipped close the ordinary path. `Validate()`'s floor on the reclaim bound is unaffected: that bound is per claim and each claim is fenced independently. That is why `docker-compose.yml` gives the service `stop_grace_period: 120s`.

  **Which transport a delivery takes is decided in the composition root, not in the use case.** `cmd/notifier` composes a `Deliverer` that dispatches on `preference.Channel()` to `internal/notification/infrastructure/webhook` or `.../smtp`, built exhaustively over the closed channel set at startup so a channel with no implementation fails to boot rather than at its first delivery. `DeliverNotification` holds one outbound port and never names a channel — which is what keeps the file holding the claim and the fence untouched by a second channel, and what makes "the new channel inherits the first one's guarantees" a property of the build.

**Every process logs the same way, and the way is not negotiable per package.** `internal/platform/logging` builds a JSON `slog` handler writing to **stdout** and binds two identity fields — `service`, drawn from a closed set of constants (`identity-api`, `video-api`, `notification-api`, `worker`, `notifier`), and `instance`, `<hostname>-<pid>-<counter>` resolved once at construction, because `docker-compose.yml` runs three workers and a hostname alone does not say which one. `LOG_LEVEL` is the only new variable: optional, absent means info, and a value that will not parse is reported through a bootstrap logger carrying the same two fields and then **exits non-zero** rather than starting at a severity nobody asked for. Each composition root parses it as the first statement of `main()` and installs the logger through `slog.SetDefault` immediately after, before any other configuration is read, which is what makes every *other* startup failure reportable as a record. `internal/` packages then log through `slog.Default()` rather than an injected logger — the one exception, `internal/notification/application`, already accepted one for its own tests and still does, now `*slog.Logger` with nil meaning the default. Do not thread a logger through a constructor that needs one for no other reason: that is how a bounded context acquires an opinion about its process's logging. The cost is named rather than hidden — a test that reads records swaps process-global state and cannot be parallel.

One directory is created at startup (`createDirs`), and it belongs to **`cmd/worker`**, not to any HTTP service — `temp/`, holding the downloaded source copy, the per-job frame directory, and the zip built from it, all always cleaned up. No HTTP service writes anything to disk on any path: `POST /upload` streams straight into the bucket, and `POST /api/video-jobs` accepts a JSON filename and never touches the filesystem. There is no `uploads/` and no `outputs/`: both source videos and results are objects in the MinIO bucket, separated by key prefix. `VideoJob`s (created via either `/upload` or `/api/video-jobs`) are persisted in PostgreSQL (`VIDEO_POSTGRES_DSN`, required at startup like `IDENTITY_POSTGRES_DSN`). `NotificationPreference`s and `notification_deliveries` rows are persisted in a **third** pool under `NOTIFICATION_POSTGRES_DSN`, required and fatal when absent at the startup of **both** `cmd/notification-api` and `cmd/notifier` — one pool **and one database** per bounded context, on whatever single server `docker-compose.yml` happens to point all three at (`identity`, `video`, `notification`, created by `docker/postgres-init/create-context-databases.sql` on the volume's first init — PostgreSQL has no cross-database query without an extension, so the boundary is enforced by the engine rather than by review). Both processes also run the context's `Migrate`, for the same reason both sides of the terminal topology declare it: neither process's startup may depend on the other's having run first. `cmd/worker` reads none of the DSNs but its own and is unaffected by the variable. `cmd/notifier` writes nothing to disk and needs no directory.

Processing is **asynchronous and out-of-request**: `handleVideoUpload` returns `202` as soon as the job is `queued`, and the extraction happens later in `cmd/worker`. No `ffmpeg` process is ever held open by an HTTP request, so upload latency no longer tracks video length. Concurrency is bounded by *worker count*, not by request count: prefetch is 1, so one worker runs one extraction at a time and scaling out means running more worker processes. `docker-compose.yml` starts **three** of them (`worker`'s `deploy.replicas`), so the default local stack processes three videos at once; `--scale worker=<n>` overrides that in either direction. **The queue is the only trigger** — with no worker running, uploads keep succeeding and every job sits at `queued` forever. The same holds one step further out: with no `cmd/notifier` running, jobs still finish and `video.jobs.terminal.events.v1` accumulates, but no webhook is delivered.

Worker crash recovery is implemented. Each claimed run holds a Redis lease scoped to its PostgreSQL `lease_epoch`; the sweeper confirms a missing lease twice, then conditionally performs `processing → queued`, advances the epoch, and writes a new dispatch row. A previous holder's terminal write is fenced by both epoch and `status = 'processing'`, so it cannot overwrite its successor. After three requeues, or for a legacy processing row with no source key, the sweeper commits `failed` and performs cleanup only when its own write was applied. This recovers jobs stranded in `processing`; it does not recover jobs stranded in `queued`, which remain an outbox/broker operations concern.

## Language policy: English for new code (as of 2026-07-28)

Code, error messages, and comments in **new or changed code** SHALL be written in English, going forward. This is a change from the project's original convention (see below) — it applies prospectively, not retroactively:

- Do not translate the existing Portuguese (pt-BR) strings already in `cmd/video-api/{main,video}.go` and `cmd/video-api/web/index.html` (the HTML form and the existing JSON `Message`/`error` fields — the `fmt.Printf`/`log.Printf` calls this clause also used to name are gone, converted to English records by `add-structured-logging`, and no unstructured output path is reachable any more) just because you're touching a nearby line. Leave them as-is unless a change specifically asks for that.
- Any error message, log line, or other string you add or rewrite from now on should be in English, even inside an otherwise-Portuguese function.
- Comments: default to none. Add one only when it explains something genuinely non-obvious (a hidden constraint, a workaround, a subtle invariant) — not to restate what the code already says. When you do add one, write it in English.
- Exception: new **user-facing UI copy** in `cmd/video-api/web/index.html` (labels, buttons, status messages shown on the page itself) and user-facing strings in `cmd/video-api/web/app.js` stay in Portuguese, matching the rest of that page — it's written for the same pt-BR hackathon audience as the existing form, and mixing languages within one UI reads as inconsistent to that audience. This exception is scoped to visible page copy only; error messages, log lines, and comments in the surrounding Go code still follow the English rule above.
- **JSON `Message`/`error` values are Go strings, so the English rule covers them** — the `web/` exception does not reach into `cmd/video-api/*.go`, even though `app.js` renders `ProcessingResult.Message` straight onto that pt-BR page. Stated here because the ambiguity produced a review finding on PR #181 and would otherwise be relitigated by every change that touches one of those strings.

## Notable constraints / gotchas

- **Access tokens are RS256, and only `cmd/identity-api` can mint one.** `internal/identity/infrastructure/jwtauth` splits the capability into an `Issuer` and a `Verifier` with **disjoint method sets**, so using the wrong one is a compile error rather than a convention. `IDENTITY_JWT_PRIVATE_KEY` + `IDENTITY_JWT_KEY_ID` are read by the Identity service alone; `IDENTITY_JWT_PUBLIC_KEYS` is a **set** (JSON `kid` → PEM, so a rotation can hold the outgoing and incoming keys at once) read by every service that verifies. Tokens carry a `kid` header and the verifier looks the key up by id; the algorithm is pinned with `jwt.WithValidMethods`. `NewVerifier` **refuses a private-key PEM**, so a private key handed to the wrong service stops that service at startup rather than quietly upgrading it. The public key is distributed **by configuration, not JWKS**, deliberately: JWKS would put a synchronous call to Identity on every verifier's cold cache and make Identity's availability a dependency of every other service's authorization decision — the exact coupling the split removes. What it buys is that a token issued before Identity went down is still accepted while it is down. `TestOnlyTheIdentityServiceConstructsATokenIssuer` (in `cmd/video-api/auth_test.go`) scans every other composition root's non-test sources for `jwtauth.NewIssuer`/`LoadIssuerFromEnv` and fails if any names one — a claim about source, which no behavioural test can hold. `IDENTITY_JWT_SIGNING_KEY`, the HMAC secret that preceded all this, is **gone**; there is no fallback path.
- The Dockerfile is a multi-stage, non-root build (`builder` → `test` → `runtime`) — it is no longer the intentional single-stage/root anti-pattern this project originally shipped with. One image carries **all five** binaries (`/app/identity-api`, `/app/video-api`, `/app/notification-api`, `/app/worker`, `/app/notifier`); `CMD` names `/app/video-api` — it serves the frontend, so it is the least surprising default — and every other process is the same image run with its own binary as the command. `docker-compose.yml` names a command for all five rather than relying on the default for any. Keeping them in one image is deliberate: they share every internal package, so a split would let the halves of one deploy drift to different builds of the same domain code. The gateway is the one service built from an image this repository does not produce: stock `nginx:1.29-alpine` plus a read-only mounted `docker/nginx/nginx.conf`, carrying no binary, key, or credential of ours.

  That image is **built by a required check and published on release** (`publish-container-image`). `Container Image Build` in `ci.yml` builds both published platforms plus the `test` stage, pushes nothing, and then reads the ELF headers of all five binaries in each image — a build succeeding proves nothing here, because the builder chains five `go build` calls and `GOARCH` reaching four of them yields an image that builds, scans and pushes clean while one process dies at `exec` on one platform only; inspecting the manifest would not catch it, since the manifest reports the platform it *claims* and never opens a layer. The builder is pinned to `--platform=$BUILDPLATFORM` and cross-compiles (`CGO_ENABLED=0` already made that exact), so only the `runtime` stage's `apk` layer is ever emulated — and the `test` stage inherits that pin **deliberately**, because it backs `docker compose run --build --rm app-test` and an emulated Go toolchain would make the documented local test path unusable. Publication goes to `ghcr.io/kakadlec/video-processor` for `linux/amd64` and `linux/arm64`, tagged with the version and, when it is the highest published one, `latest`; a version tag is immutable with **no override input**, and replacing one means deleting it from the registry by hand. The publish job sits in `release-please.yml` rather than its own workflow because a release created with the workflow's own `GITHUB_TOKEN` triggers no further workflow run — a separate `release:`-keyed workflow would never fire. A `workflow_dispatch` publishes a tag that already exists (the bootstrap and recovery path), validating the tag's form and existence first, since `actions/checkout` resolves a branch as happily as a tag. Local development is untouched: Compose still builds from the working tree, and `--build` stays load-bearing.
- **A log call may only build a field from a scalar it extracted itself, and three source-level rules hold that** — one AST walk over every non-test file under `cmd/` and `internal/`, in `internal/platform/logging/disclosure_test.go`, which is also where a new rule belongs. (1) **Typed attributes only**, after the message *and* in every `Logger.With` argument: `slog.String/Int/Int64/Bool/Duration/Time`. `slog.Any`, `slog.Group`, `slog.AnyValue`, `slog.GroupValue` are denied by name and the alternating key/value form is denied outright; `WithGroup(name)` binds no value and is deliberately uncovered. This is stronger than redacting the types known to be sensitive, on purpose: the JSON handler walks a value's exported fields with no chance for the type to intervene, so a domain value carrying a user-supplied connection target — a webhook destination whose query string may legitimately hold a credential — would be written out verbatim, and `domain.Secret`'s own defences (which *do* work, at the cost of the whole attribute and its siblings) are not the general case. Foreclosing the arbitrary-value path covers the types nobody has thought to defend yet. (2) **No import of the standard `log` package at all** — an import ban rather than a list of function names, because a `log.New` plus a method call on the result reintroduces the entire path while every enumeration of `log.Print`/`log.Fatal` stays green — and no `fmt.Print*`/`Fprint*` whose destination **resolves** to a standard stream or a framework default writer. Resolution traces an identifier back to its assignment, because `os.Stdout` is an `*os.File` like any other and a type check cannot tell it from the `strings.Builder` that `internal/notification/infrastructure/smtp` legitimately `Fprintf`s the mail message into. A `log.Fatal*` is therefore an error record plus an explicit `os.Exit(1)`; that skips defers exactly as `log.Fatal` did — what changed is that the skip is legible. (3) **Every message is a string literal** — not `fmt.Sprintf`, not concatenation, not a named `const` — because a formatted message satisfies the other two rules while putting the identifier straight back inside the message, which is the defect the whole change removed. No behavioural test can hold any of the three: it sees only the call sites that existed when it was written. Field vocabulary is conventional rather than enforced — `component` (two-word snake_case: `http_access`, `outbox_relay`, `recovery_sweeper`, `video_upload`, `readiness_probe`, …), `phase` (`started`, `connected`, `connection_lost`, `stopped`), `job_id`, `user_id`, `delivery_id`, `lease_epoch`, `storage_key`, `source_key`, `event_type`, `channel`, `error` — so match an existing key before inventing one.
- **The HTTP access and recovery records are ours, not gin's.** Each of the three HTTP roots carries its own `logging.go` — a fourth deliberate copy alongside `auth.go` and `ratelimit.go`, since `package main` cannot import `package main`, each with its own tests. The access record carries method, matched route, status, duration, size, and the authenticated subject where one exists; it carries **no** query string, header or body, and **no path when a route matched** — the route template is bounded by the router, and a matched path only adds parameter values the handler already records. An unmatched request records `URL.Path` truncated to 256 bytes and an unrecognized method as a fixed marker, both because they are caller-supplied and reach the record before authentication and before the limiter. The recovery handler is written out rather than delegated to `gin.CustomRecovery` for two reasons verified against the pinned v1.12.0: it prints an ANSI block to `DefaultErrorWriter` *before* calling the supplied handler, and nil-ing that writer to silence the block also skips the handler entirely on the broken-pipe branch (`EPIPE`/`ECONNRESET`/`http.ErrAbortHandler`) — which would leave that one class of panic recorded nowhere at all. Keep gin's branch structure and each branch's response; record both. **Exactly one class of request is exempt from the access record — one that matched `GET /health` or `GET /ready` — as a closed list of those two templates and no general mechanism** (no skip list, no per-route option): a configurable one would let a future route leave the access log without that ever being reviewed. The exemption does **not** reach the recovery record; a panic while serving a probe is recorded like any other, because what is exempt is the routine per-request record and not the report of a failure. In its place each root emits **one record per change of readiness verdict** (`component: readiness_probe`), CAS-guarded so two concurrent probers observing one transition produce one record: `warn` on degradation carrying the failing dependency names joined into a single `slog.String` (rule 1 denies `slog.Any`, so a slice cannot be passed) plus a `dependency_count`, and `info` on recovery, which names nothing because what recovered is the service. A process starts holding **ready** — startup already verified every readiness dependency and is fatal without them — so a healthy start announces no recovery from a degradation it never had. And a **canceled** probe request records nothing at all: every check derives from the request context, so one canceled request fails all of them and would otherwise warn about the entire dependency inventory and then announce a recovery from it on the next live probe. The verdict is left where it stands and the response is still `503`, readiness having not been established.
- **`cmd/worker` and `cmd/notifier` serve nothing, by requirement rather than by omission.** `container-image` already forbids either to expose a port; since `add-health-and-readiness-endpoints` each also carries an **in-package** source test over its own non-test files asserting the package constructs no HTTP server and imports no HTTP framework — strictly stronger than the no-port rule, which a process could satisfy while listening on one, and in-package rather than a cross-root scan so the failure lands where the listener was introduced. A raw `net.Listen` is the stated residual. The cost is accepted and named: neither process has a liveness signal, and **no record fires on an idle stack** for either — the sweeper logs only when it finds something, the notifier's records are all per-message, and a healthy connected consumer is silent — so an idle-but-wedged worker is indistinguishable from an idle-and-healthy one. Do not answer that by giving either one a port.
- The app's *existing* user-facing strings (error messages, HTML) are in Portuguese (pt-BR) — this was the original convention for this pt-BR hackathon audience. It's superseded for new code by the language policy above; existing pt-BR strings are grandfathered in and not being retroactively translated.
- File type validation (`isValidVideoFile`) is by extension only (`.mp4 .avi .mov .mkv .wmv .flv .webm`), not content sniffing. `POST /upload` reads the "video" multipart part via a streaming `MultipartReader`/`NextPart` (`videoFilePart` in `cmd/video-api/video.go`), not `c.Request.FormFile` — `FormFile` calls `ParseMultipartForm` internally, which reads the entire request body before the filename is available, so a large invalid-extension upload would otherwise pay the full transfer cost before being rejected. See `openspec/specs/upload-file-validation/spec.md`.
- The `.owner` sidecar mechanism is gone entirely — the helpers, the suffix constant, and both middlewares. No artifact class uses it: results derive ownership from the `VideoJob` row, and source objects are never served at all.
- `handleDownload` no longer touches the filesystem: the requested `:filename` must parse as `frames_<jobID>.zip`, and the job it names must belong to the caller, be `completed`, and record that exact key. `handleStatus` never accepts a caller-supplied name at all, and its `download_url` still points at `/download/<key>` on this API — minting presigned URLs into the listing was considered and rejected (it would start every TTL at listing time and put one credential per job in a single body). The **result** key deliberately contains no `/` — `cmd/video-api/web/app.js` uses it verbatim as that route's single path segment, and a `%2F` would break the match, so per-user or per-date prefixes on results are not possible without a frontend change. **That constraint did not lapse when the route started returning JSON**: the route survived unchanged and `app.js` still calls it, so re-keying results would still orphan every stored object. **Source** keys do carry an `uploads/` prefix, for exactly the complementary reason: no route exposes them. Anything that re-exposes source objects over HTTP has to drop that prefix in the same change.
- Both uploaded source videos and processed results live in the MinIO bucket, not on local disk — `internal/video/domain.SourceStorage` and `ResultStorage`, implemented by the two adapters in `internal/video/infrastructure/storage` over one client and one bucket. Source keys carry an `uploads/` prefix; result keys are flat. **Source objects are transient, but the API is no longer what disposes of them**: ownership follows the job's outcome. `POST /upload` deletes its own object only on the paths where the job never reached `queued`; once the enqueue commits, the object is the worker's input and the worker deletes it after committing a terminal state (and deliberately *keeps* it when `CompleteJob` will not commit). That deletion is best effort on both sides — one call, no retry — so a failure is logged with the key and does not fail the request or the job; `docs/operations.md` documents the recommended `uploads/`-prefix lifecycle rule as the operator-side backstop. See `openspec/specs/videojob-source-storage/spec.md`. `VIDEO_MINIO_ENDPOINT`/`ACCESS_KEY`/`SECRET_KEY`/`BUCKET` are **required at both binaries' startup**; `VIDEO_MINIO_USE_SSL`, `VIDEO_MINIO_PUBLIC_ENDPOINT`, and `VIDEO_MINIO_PUBLIC_USE_SSL` are optional, the latter two each defaulting to their internal counterpart (`PUBLIC_USE_SSL` to the *resolved* `USE_SSL`, not to `false`). `cmd/video-api`'s `setupVideo` loads, opens, pings, ensures the bucket, then discovers the bucket region and builds a second, presign-only client against the public endpoint — any failure is fatal. It also returns **one** extra value, the object-storage readiness check (`func(context.Context) error`) closed over the client and bucket it just built, rather than handing `main` the raw client or putting it on `videoModule`, which holds use cases and domain ports and no driver handle. **That check is `storage.CheckBucket`, and `storage.Ping` is deliberately not it: do not collapse the two.** `Ping` calls `BucketExists` and *discards* the boolean, so it answers nil for a reachable server whose bucket is gone — which is correct for its one caller, because startup pings *before* `EnsureBucket` creates the bucket, and a presence-asserting `Ping` would make a first start against an empty object store fatal on a bucket the next line was about to create. `CheckBucket` reads the boolean and creates nothing. Two callers, two questions, two operations. `cmd/worker`'s `setupWorker` does the same, presign client included — **not** because it signs anything (issuing download grants is the API's job) but so `ResultStorage` is fully constructed rather than holding a nil that would panic the day something calls the other half of its interface. Its `VIDEO_MINIO_PUBLIC_ENDPOINT` is therefore left unset in `docker-compose.yml` and falls back to the internal endpoint, which is harmless exactly because no URL is ever signed with it. That second client is deliberately never pinged and never used for a bucket or object operation: SigV4 signs `Host`, so presigned URLs must be signed against the browser-facing address from the start, which is generally one the server cannot reach. The region must be passed explicitly or `PresignedGetObject` would try to discover it over the network against exactly that unreachable host. This is **fail-closed**, deliberately unlike every Redis-backed feature below — those degrade to a slower but correct system, whereas a result that cannot be stored cannot be delivered. `GET /download/:filename`'s entitlement lookup deliberately uses the *undecorated* PostgreSQL repository rather than the cached one, so a stale `processing` cache entry can't 404 a result `GET /api/status` is already listing. See `openspec/specs/videojob-result-storage/spec.md`.
- `POST /upload` deduplicates by content: identical bytes uploaded twice by the same authenticated user reuse the first request's `VideoJob` instead of running `ffmpeg` again (`internal/video/domain.IdempotencyStore`, backed by Redis via `internal/video/infrastructure/idempotency.RedisStore`). This requires `REDIS_ADDR` at **both** `cmd/video-api` and `cmd/worker` startup. A `Reserve` error (Redis unreachable/erroring, as opposed to a normal reservation conflict) fails open: the handler logs it and proceeds without a reservation rather than blocking the upload, matching rate limiting's and the status cache's fail-open posture. **Clearing the key is the worker's job, not the API's** — the API cannot know a job's outcome any more, and the key must survive until one exists. The consumer clears it after a failure it committed, and the recovery sweeper does the same when it applies the terminal abandonment write; a fenced or already-present outcome clears nothing. Both use `IdempotencyStore.ClearByJob(key, jobID)`, rebuilding the key from the persisted `content_hash`, so no reservation token is stored and a later upload's reservation is never cleared by an older attempt. See `docs/architecture.md`'s Request pipeline section and `openspec/specs/upload-idempotency/spec.md` for the full protocol.
- Every authenticated route is also rate limited per user: a Redis-backed fixed-window counter (`internal/platform/ratelimit`, mounted as each HTTP service's own `ratelimit.go` right after `requireBearerAuth()`) rejects excess requests with `429` + `Retry-After` before any handler runs. **The counter is one budget per user across the whole system**, not per service: every copy keys it `ratelimit:<userID>`, so exhausting the budget on `GET /api/status` refuses the next `GET /api/notification-preferences` from a different process. Namespacing per service would silently multiply every user's allowance by the number of services, which is also why `RATE_LIMIT_MAX_REQUESTS`/`RATE_LIMIT_WINDOW_SECONDS` must hold the same value everywhere or (as in `docker-compose.yml`) be unset everywhere — unset is one source of truth, the code default. `cmd/identity-api` mounts no limiter at all: its two routes are how a caller obtains a token. This limits **requests to these APIs**, which is not the same as limiting bytes served: `GET /download/:filename` issues a presigned URL and is limited, but the transfer that URL authorizes goes straight to MinIO, which this middleware does not sit in front of. Do not read "every authenticated route is rate limited" as "result egress is rate limited" — bounding that is an object-storage concern. Configurable via optional `RATE_LIMIT_MAX_REQUESTS`/`RATE_LIMIT_WINDOW_SECONDS` (defaults 60/60s) — unlike `REDIS_ADDR`, these are not required at startup. A limiter failure (including its own bounded internal timeout) fails open rather than blocking the request. See `openspec/specs/rate-limiting/spec.md` for the full protocol.
- Transactional outbox relays carry `video_job.*` events to RabbitMQ: one for job dispatch, one for terminal outcomes. `cmd/video-api` opens exactly one AMQP connection, for the dispatch relay; `cmd/worker` opens two — its consumer, the other side of that dispatch topology, and its own terminal-event relay. The terminal relay lives in the worker because the worker is the process that writes those rows (its own terminal writes and the sweeper's abandonment write), so announcing an outcome does not depend on an API replica being up. `internal/platform/rabbitmq` holds the plumbing (`Config`/`LoadConfigFromEnv` reading `RABBITMQ_URL`, `Open`, `Ping`, `Close`, a generic `Topology` descriptor carrying a **set** of work-queue routing keys — an empty set is refused, because a direct exchange with no binding returns every mandatory publish unroutable while the declaration itself still reports success — and `DeclareTopology(conn, topo)`); `internal/video/infrastructure/messaging` holds the names (`JobDispatchTopology()`, `TerminalEventsTopology()`) plus `Publisher` and `Relay`; `internal/video/infrastructure/postgres.OutboxRepository` owns the claim, hiding the `*sql.Tx` behind an `OutboxBatch` so the messaging package never names a database driver. **`RABBITMQ_URL` is required at `cmd/video-api` startup** (loaded as `setupVideo`'s first statement, before any I/O), but a *reachable* broker is not: `main` starts the relay as a goroutine that dials, retries with backoff, and redeclares the topology after every dial. The consumer declares the same topology on every dial too — both sides declare, so neither process's startup order depends on the other's, and a fresh or recreated broker cannot leave a publish landing in a missing exchange or a consume opening on a missing queue. Each cycle claims a bounded batch of rows whose `event_type` is in **that relay's own explicit set** (`event_type = ANY($1::text[])`; the two sets are disjoint, so neither relay's backlog can starve the other's) with `FOR UPDATE SKIP LOCKED`, publishes **mandatory** on a confirm-mode channel under **each row's own `event_type` as the routing key** rather than one key fixed at construction, and stamps `published_at` only for messages that were acknowledged **and** not returned — a confirm means the *exchange* accepted the publish, not that any queue got it. A nack is not an error (a full queue under `reject-publish` is designed back-pressure; the row waits for the next poll), and the claim/publish/stamp all commit together — committing the claim first would lose a dispatch permanently on a crash. The platform/context split is enforced by tests: the platform package may import nothing outside `internal/platform/`, and may contain no context name (`video.jobs`, `video_job.`), because `ddd-architecture` confines that namespace to connection/lifecycle plumbing. Two decisions look like mistakes without their reason — `Open` connects (AMQP has no lazy client, unlike `redis.Open`/`storage.Open`), and the job queue carries **no** message TTL (an expired message is dead-lettered without touching the `video_jobs` row, and the state machine has no edge out of `queued` except to `processing`, so the job would report `queued` forever). The routing key equals the outbox `event_type` string for every published event, coupled across two packages with no compiler enforcement — `TestRoutingKeyMatchesTheOutboxEventType` is what pins all three pairs, over a table. So is the wire payload: `postgres.videoJobQueuedPayload`/`videoJobCompletedPayload`/`videoJobFailedPayload` and `messaging.JobQueuedMessage`/`JobCompletedMessage`/`JobFailedMessage` are separate structs in packages that do not import one another, pinned by `TestJobQueuedMessageDecodesTheOutboxPayload` and `TestTerminalMessagesDecodeTheOutboxPayloads`. The consumer-side terminal structs exist ahead of any consumer precisely to pin what the relay is already publishing.

  The dispatch generation is **`.v2`** — `video.jobs.v2`, `video.jobs.queued.v2`, and the routing key/`event_type` `video_job.queued.v2` (the dead-letter names carry no suffix). Versioning the exchange alone would isolate nothing, because every replica's relay claims from one shared `video_job_outbox` filtered on `event_type`: the generation has to be on the event type too, or a new-generation replica would publish an old-generation replica's rows. What it protects is the **rolling-deploy window**, not stale messages: a `.v1` API replica still deletes its own source object on every exit path, so a `.v1` message consumed by the new worker names an object that is already gone. Retiring the superseded queue and exchange after the deploy is a documented post-deploy step (`docs/operations.md`). See `openspec/specs/videojob-outbox-relay/spec.md`, `openspec/specs/rabbitmq-infrastructure/spec.md`, and `openspec/specs/videojob-messaging/spec.md`.

  The terminal generation is **`.v1`** and is separate: exchange `video.jobs.terminal.v1`, one durable queue `video.jobs.terminal.events.v1` bound under **both** routing keys/`event_type`s `video_job.completed.v1` and `video_job.failed.v1`, sharing the same unversioned dead-letter sink. One queue carries both outcomes because a consumer interested in a job's end is interested in either. It is a second topology rather than two more routing keys on the dispatch exchange so that a dispatch generation bump does not rename the terminal stream. Like the job queue it is bounded by `x-max-length` with `reject-publish` and carries **no** message TTL, but for a different reason: on the job queue an expired message leaves a job reporting `queued` with nothing able to advance it, whereas here the job is already terminal and correct in PostgreSQL — what expiry would discard is the only announcement that outcome ever gets. **`cmd/notifier` consumes this queue** as of `add-notification-webhook-delivery`; it accumulated by design until then, and — unlike the dispatch bump — nothing is superseded, so there is nothing to retire. `internal/notification/infrastructure/messaging` declares the **same** topology from the Notification context's own copy of the names, because `ddd-architecture` forbids importing Video Processing's; both sides declare on every dial, and `TestNotificationTerminalTopologyMatchesTheEmittedTopology` in `internal/contracts` pins the copy field by field — names *and* bounds, since RabbitMQ refuses to redeclare a queue whose arguments differ and a name-only pin would stay green while the notifier could not consume at all. The rows themselves are written by `Repository.Update` inside the same transaction as the fenced terminal `UPDATE`, and **only when that statement affected a row**: a write refused by the fence and a repeat of an outcome already stored each write nothing, so a superseded worker and the sweeper both finishing one job leave exactly one record of how it ended. Delivery stays at-least-once, so deduplicating repeated deliveries is the consumer's obligation. See `openspec/specs/videojob-terminal-events/spec.md`.
- `GetJobStatus` and `EnqueueVideoJob` read through `internal/video/infrastructure/cache.CachedVideoJobRepository`; ownership decisions (`StartProcessing`, `CompleteJob`, `FailJob`, download entitlement, and the sweeper scan) read authoritative PostgreSQL and still write transitions through the decorator. `FindByID` is cache-aside with `SET NX` miss-repopulation. Transition write-through uses an atomic Redis CAS ordered by `(lease_epoch, status rank)`, so a delayed requeue cannot replace its successor's completion; an ambiguous PostgreSQL error invalidates the entry, while `ErrJobFenced` leaves the winner's entry intact. Redis failures remain best effort and the TTL is a fixed five minutes. See `openspec/specs/videojob-status-cache/spec.md` for the full protocol.
- The per-preference **webhook secret is write-only from the API's point of view**, and non-disclosure is the entire control — it cannot be hashed, because HMAC signing at delivery time needs the original bytes, so `internal/identity/infrastructure/password`'s bcrypt is structurally unavailable. The posture is the one `add-presigned-download-urls` established for an issued URL: treat it as a credential. `domain.Secret` holds its value behind an **unexported pointer** and renders `notification.Secret{REDACTED}` from `String`, `GoString`, and `Format`, while `MarshalJSON` **returns an error** rather than a value — so a response struct holding one fails at encode time instead of leaking. Each layer closes what the one before leaves open: `String` is consulted only for `%v %s %q %x %X`, `Format` covers every other verb, and `%p` is the one verb `fmt` answers before looking for a `Formatter` — the pointer field is why reflection reaches an address there rather than the bytes, and is also what protects `PreferenceIntent`/`NotificationPreference`, which hold a `Secret` as a field where `fmt` cannot call methods at all. The bytes come out of exactly one deliberately-named accessor, `Reveal()`. The wire types are built from `application.PreferenceResult`, which has no secret field at all. **A secret is required only where the channel signs**, and `Channel.Signs()` names that property once so four places condition on it: the schema's `CHECK (channel <> 'webhook' OR secret <> '')`, the adapter's choice among three write statements, `RestoreNotificationPreference`'s invariant, and the delivery read's projection. The aggregate one is the one that looks skippable and is not — leaving it unconditional makes an `email` row writable and permanently *unreadable*, and that failure arrives as a `FindDeliverable` error, which `cmd/notifier`'s disposition table reads as *attempted nothing* and **requeues**, blocking the queue at prefetch 1 rather than failing visibly. `ErrSecretRequired` is unchanged for `webhook`, and `NewPreferenceIntent` is untouched: it already declines to enforce the rule, which is exactly what lets the adapter own it. Every read path **except one** projects `secret <> '' AS has_secret` and never selects `secret`, so the value is not loaded where a response is built. The exception is `PreferenceRepository.FindDeliverable`, the single named delivery-path read that returns the full aggregate with its `Secret` — and even there the projection is conditional, yielding one only for a signing row, because an `email` preference may carry a secret and declining to *use* a scanned value is weaker than declining to *load* it — the value has to be loadable for a signature to exist at all, and what keeps the rule true is that the somewhere is singular, named, and provably absent from the HTTP composition root: `TestNoQueryOutsideFindDeliverableSelectsTheSecret` pins the projection at the source level and `TestTheHTTPCompositionRootDoesNotLoadTheSecret` pins that no file under `cmd/notification-api` calls it. `webhook.sign` is its only consumer. Handlers log the triple, never the body. It is plaintext in the column by necessity — `docs/operations.md` records that database access and backups therefore carry it.
- `internal/notification`'s `Migrate` takes a `pg_advisory_xact_lock` on a constant this context owns and runs both its `CREATE TABLE IF NOT EXISTS` statements — `notification_preferences` and `notification_deliveries` — inside that one transaction. This is **deliberately stricter than the identity and video adapters**, which do not take it: `IF NOT EXISTS` is idempotent once the table exists but does not serialize two *first-time* creates, so two replicas starting together can race to a catalog uniqueness violation — which at `cmd/notification-api` or `cmd/notifier` startup means a replica that refuses to boot. Both processes migrate, deliberately: a notifier started against a database no API has yet touched creates what it needs rather than failing. Do not "fix" it back to match the other two; the latent race is in them, not here.
- `internal/notification/domain` declares `video_job.completed.v1`/`video_job.failed.v1` as its **own** constants rather than importing `internal/video/infrastructure/postgres`, because `ddd-architecture` forbids Notification from reaching into Video Processing — a rule about imports that holds at rest, not only while handling an event. The same reason it has its own `UserID` value object. That duplication is pinned rather than left loose: `TestNotificationEventTypesMatchTheEmittedTerminalEventTypes` in `internal/contracts` — the one package that legitimately imports both — asserts the pairs are equal, in the same spirit as `TestRoutingKeyMatchesTheOutboxEventType`. Without it a rename on either side would silently leave the consumer resolving events against a name no preference row carries. `internal/notification/infrastructure/messaging` copies the terminal **topology** and the **payload structs** for the same reason and is pinned the same way (`TestNotificationTerminalTopologyMatchesTheEmittedTopology`, `TestNotificationTerminalMessagesDecodeTheEmittedPayloads`). The import ban is enforced across **every** package of the context, infrastructure included — `internal/notification/dependency_rules_test.go` AST-walks them all — because the infrastructure package holding the copy is exactly where importing the original would be tempting.

- One **destination policy**, `internal/notification/domain.DestinationPolicy`, applied at **two points to a destination that is a connection target**, and neither is redundant. It does **not** apply to an `email` destination, and that is a narrowing of scope rather than a hole: the policy judges a target the *user* supplied, and the e-mail path dials the relay this deployment configures, never the stored address. The branch is taken on the closed `Channel` set, so a value outside it is refused before either rule and no third path applies neither. `CheckDestination` runs in `SetPreference`'s webhook branch when a preference is written (scheme must be `https`, and a hostname of `localhost`/`.localhost` or a literal address is judged there and then); `CheckAddr` runs inside the delivery client's `net.Dialer.Control`, against the **resolved** address, when a connection is opened. Write-time alone cannot survive a hostname that resolves elsewhere later or a policy tightened after the row was stored; dial-time alone silently accepts destinations that will never be delivered to, which to their owner is indistinguishable from one that works. The address rule is a **permission**, not a deny-list — only globally reachable unicast is dialable — and it is an explicit prefix table **in addition to** the stdlib predicates, not instead of them: `IsGlobalUnicast()` answers *yes* for `100.64.0.0/10`, `198.18.0.0/15` and `240.0.0.0/4`, which is the exact gap. IPv6 is its own list built from the IANA Special-Purpose Registry's not-globally-reachable rows, not "the v4 equivalents"; `::ffff:0:0/96` and the **well-known** NAT64 prefix `64:ff9b::/96` are unwrapped and evaluated as the IPv4 address they embed, while `64:ff9b:1::/48`, 6to4 `2002::/16` and Teredo `2001::/32` are refused **as prefixes** rather than unwrapped, because what they embed is reached through a relay or translator this policy does not control. `ErrDestinationRefused` is **one sentinel, not one per rule**, and the `400` says only that the destination was refused: the rules enumerate this deployment's internal address space, so a caller who could tell them apart by resubmitting would have a probe. `DestinationPolicy`'s **zero value is the restrictive posture**, which is why it is passed as a value rather than a port — a composition root that forgets to pass one fails closed. `NOTIFICATION_ALLOW_INSECURE_DESTINATIONS` (optional, default `false`) relaxes the scheme rule and the address rule **together**, and is read by `cmd/notification-api` and `cmd/notifier` through one parser (`webhook.LoadDestinationPolicyFromEnv`): one policy, two readers, and a deployment whose two processes disagree either stores destinations it can never deliver to or refuses at dial what it accepted at write time. `docker-compose.yml` sets it on `notification-api`, `app-test`, and `notifier`; **never set it in production** — it turns the delivery client into an SSRF primitive.
- `internal/notification/infrastructure/smtp` is the e-mail `Deliverer`, and three of its properties are load-bearing rather than incidental. **The attempt's bound is an absolute deadline on the connection, taken before the dial and reused for the conversation** — `net.Dialer` bounds only establishment, and everything after `smtp.NewClient` (greeting, EHLO, STARTTLS, AUTH, MAIL, RCPT, DATA, QUIT) is a blocking read that observes no context, so a relay that completes the handshake and stalls would hold an attempt past `MaxClaimHold()` and past the reclaim bound validated against it; the context is also watched so a cancellation closes the descriptor, which is the only thing that reaches a blocked read. The deadline uses `time.Now`, never the injectable `now` — that clock supplies the `Date` header and a test pins it, so deriving a real-time bound from it sets the deadline in the past. **Every value bound for a header is re-checked** against the same printable-ASCII rule the domain applies to an address, before the message is built and before anything is dialled: `JobID` and `DeliveryID` deliberately enforce only non-emptiness, and a `job_id` arrives inside a consumed message, so a malformed payload on the terminal queue is how CRLF would otherwise reach a header. **Credentials are never offered over an unencrypted session** — that is not the destination policy's question and `NOTIFICATION_ALLOW_INSECURE_DESTINATIONS` deliberately does not reach it, because the relay is operator-supplied and what is protected is this deployment's own credential. The body is base64-encoded (a failure `reason` is unconstrained text and may exceed SMTP's 1000-octet line limit), carries no signature and no link, and the adapter reads no `Secret` at all — asserted at the source level, since a value never read is not observable at runtime. `NOTIFICATION_SMTP_ADDR`/`FROM` are required at `cmd/notifier` startup and `cmd/notification-api` reads neither: it validates an address, it sends nothing.
- The delivery client's transport sets `Proxy: nil` **explicitly** and must never use `http.ProxyFromEnvironment`. `Dialer.Control` guards only the connection the transport opens, so with a proxy in the environment it approves the *proxy's* address and the proxy then resolves the user's hostname itself — the whole prefix table bypassed by an environment variable. Copying `http.DefaultTransport` is how this bug gets in, since that is exactly what it sets. It also refuses every redirect, caps the response body, and bounds each attempt by the configured timeout.
- `notification_deliveries` is keyed on `(user_id, event_type, channel, job_id)` and carries **two** identifiers that are not interchangeable: `delivery_id` is what the receiver deduplicates on and **survives a reclaim**; `claim_token` says which grant is current and is **reissued on every grant**. Claiming is **one atomic statement** — `INSERT ... ON CONFLICT ... DO UPDATE ... WHERE status = 'pending' AND claimed_at < $stale RETURNING delivery_id, claim_token` — which reads no row first, because a check-then-insert loses the race across two processes. Zero rows is a refusal, and the refusal is **classified by a second, deliberately non-authoritative `SELECT status`** into `ClaimAlreadyResolved` (ack) or `ClaimHeldByAnother` (requeue); that read only picks ack versus requeue, so reading it stale costs one extra pass through the handler and never a second outbound request. A vanished row counts as `ClaimHeldByAnother`. `ResolveDelivery` is **fenced** on `delivery_id + claim_token + status = 'pending'` — the reclaim bound proves a claim is *old*, not that its holder stopped — and a refused resolve is acked without retry: the successor owns the outcome.
- The delivery budget lives in `internal/notification/application.DeliveryConfig` and its terms are **not independent**. `MaxClaimHold()` is written as arithmetic over every term — `AttemptBudget()` (`3×5s + 2s + 4s` = 21s) plus `ResolveBudget()` (`3×2s + 1s + 2s` = 9s) = 30s at the defaults — and `Validate()` refuses a `ReclaimBound` below **twice** that (floor 60s; the default bound is 120s). Written as code rather than a constant so lowering a default moves the floor with it. `cmd/notifier` runs `Validate` at startup and a failure is **fatal**, because the claim token fences only the database write and cannot recall a request already on the wire: a bound under the budget produces concurrent requests to one destination in *normal* operation, not only after a crash. Only three of the seven terms are environment-tunable — `NOTIFICATION_WEBHOOK_MAX_ATTEMPTS` (3), `NOTIFICATION_WEBHOOK_TIMEOUT_SECONDS` (5), `NOTIFICATION_DELIVERY_RECLAIM_SECONDS` (120) — and that is deliberate: every variable exposed is another way to reach a combination the validator has to refuse. The arithmetic saturates rather than wrapping, and `Validate` refuses a saturated budget, because a wrapped total is negative and would silently invert every comparison it feeds.
- The recorded reason and every log line on the delivery path are built from a **classified error of ours**, never from a transport error's own text. Go wraps transport errors in `*url.Error`, whose `Error()` renders the full request URL — and a webhook destination may legitimately carry its credential in the query string, so recording one verbatim writes that credential into the database and the logs. Log lines name the triple and the delivery id; never the body, never the destination's query string.
- The delivered body is the **Notification context's own payload**, not the Video Processing wire payload forwarded: forwarding would make an internal contract public and leak the generation suffix out of the system it isolates. It carries a top-level `version` of its own, **independent of the event type's `.v1`** and not derived from it, on the wire rather than in a header so the signature covers it. No `user_id` (the receiver is that user), no secret, no credential. Signing is HMAC-SHA256 over `<unix timestamp>.<body>`, rendered `sha256=<hex>` in `X-FiapX-Signature`, alongside `X-FiapX-Event`, `X-FiapX-Delivery` and `X-FiapX-Timestamp` — the timestamp is inside the signed value so a captured request is not replayable forever.
