# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Go service ("FIAP X - Processador de Vídeos") that accepts a video upload, extracts frames at 1fps via `ffmpeg`, zips them, and hands back a presigned URL. Processing is **asynchronous**: `cmd/api` accepts and reports, `cmd/worker` extracts. It's the code deliverable for a POSTECH/FIAP hackathon (see `docs/project-requirements.pdf` for the assignment brief — a binary PDF, not readable as text).

The HTTP composition root lives in `cmd/api/main.go` (package `main`), alongside `identity.go`, `video.go`, `ratelimit.go` and their `_test.go` files; the **worker** composition root is `cmd/worker/main.go` (also package `main`). `internal/identity` and `internal/video` hold the DDD bounded contexts introduced in later phases, `internal/platform` the cross-cutting connection plumbing (see `docs/architecture.md`). CI runs on GitHub Actions (`.github/workflows/ci.yml`); there is no linter config beyond `go vet` and `gosec`.

## Development workflow

No development methodology is mandatory. Changes may be implemented directly; OpenSpec is used only when the developer explicitly requests it, invokes an `/opsx:*` command, or continues a named active OpenSpec change. Selecting OpenSpec activates its full lifecycle through the `change-lifecycle` skill; the size or complexity of a direct request does not activate it.

Quality and delivery requirements apply independently of methodology. `main` has no direct pushes, and every PR is gated by `Build & Test`, `SAST (gosec)`, and `Vulnerability Scan (govulncheck)`. The `repo-workflow` skill applies whenever a developer requests a PR action or the agent creates a PR. Full quality-gate, branch-protection, review, merge-authorization, commit, and release rules live in `docs/development.md`.

One rule worth restating: **`go test ./... -v` must pass locally before reporting a change complete whenever the diff includes a Go module input (`.go`/`go.mod`/`go.sum`)** — tests require `ffmpeg` on `PATH` **and** a reachable MinIO configured through `VIDEO_MINIO_*`, or run via `docker compose run --build --rm app-test go test ./... -v`, which supplies both.

## Commands

```bash
go run ./cmd/api        # run the API directly (listens on :8080)
go run ./cmd/worker     # run the worker (no HTTP, no port) — WITHOUT IT NOTHING IS PROCESSED
go build -o app ./cmd/api && go build -o worker ./cmd/worker  # build both binaries
go mod tidy             # sync go.mod/go.sum after dependency changes
go test ./... -v        # integration suite (requires ffmpeg on PATH, MinIO via VIDEO_MINIO_*, and RABBITMQ_URL to be set; cmd/api's TestMain exits 1 with an error if any is absent. RABBITMQ_URL only has to be set, not reachable — cmd/api doesn't require a live broker either. A reachable broker via RABBITMQ_TEST_URL is a prerequisite for full coverage only — internal/platform/rabbitmq's and internal/video/infrastructure/messaging's tests skip cleanly without it, so the suite still passes while covering none of those packages)
docker compose up --build   # full stack via Docker (app + worker + PostgreSQL + Redis + MinIO + RabbitMQ)
```

`ffmpeg` must be installed and on `PATH` — `cmd/worker` shells out to it (`exec.CommandContext("ffmpeg", ...)`) and has no fallback or embedded copy. `cmd/api` no longer runs it, but the test suite does. `cmd/api`'s tests additionally require a reachable MinIO: `main_test.go`'s `TestMain` exits 1 when either `ffmpeg` or the `VIDEO_MINIO_*` configuration is missing, deliberately rather than skipping — `POST /upload` stores its result in a bucket, so a skipped suite would report green while covering none of that. If either is unavailable locally, run tests inside Docker instead: `docker compose run --build --rm app-test go test ./... -v` (`app-test` builds from the `Dockerfile`'s `test` stage — the hardened `app` service's image has no Go toolchain to run tests with). `docker-compose.yml` is the sole documented way to build, run, or test the application via Docker **for local development** — there is no separate plain `docker build`/`docker run` workflow documented for that purpose. Container deployment is a separate, intentionally-retained concern documented in `docs/operations.md`.

## Architecture

Request flow across **two** composition roots — `cmd/api/{main,identity,video,ratelimit}.go` and `cmd/worker/main.go`:

1. `setupRouter(identity, video, limiter)` wires a single `gin` router: no static artifact mounts remain (both `/uploads` and `/outputs` are gone), a permissive CORS middleware (allows `*`), and routes `GET /`, `POST /upload`, `GET /download/:filename`, `GET /api/status`, `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/video-jobs`, `GET /api/video-jobs/:id`, `GET /api/video-jobs`. Every route gated by `identity.requireBearerAuth()` (everything except the two `/api/auth/*` routes and static assets) is also gated by a per-user rate-limit middleware (`internal/platform/ratelimit`, see the rate-limiting bullet below). `main()` calls `setupIdentity`/`setupVideo` then constructs the limiter, then `setupRouter(identity, video, limiter)`, then serves it through an explicit `http.Server` under a `signal.NotifyContext(SIGINT, SIGTERM)` — the split exists so `main_test.go`/`identity_test.go`/`video_test.go` can drive the real handlers via `httptest.NewServer` without binding the real port. Shutdown ordering is load-bearing and not alphabetical: `server.Shutdown` → cancel the outbox relay → **join** its goroutine → close the PostgreSQL pools → close Redis. The relay holds a database transaction while it runs, so closing the pool before joining would abort an in-flight claim instead of resolving it. MinIO is deliberately absent — that adapter exposes no teardown. **`cmd/worker` has the same shape for the same reason**: `run` returns only after the consumer goroutine has finished the delivery in hand (bounded by a 5-minute drain), and only then are PostgreSQL and Redis closed — the handler borrows both for the whole of a job, so closing either underneath a running extraction would fail the terminal write rather than the work.
2. `GET /` serves `cmd/api/web/index.html` (with `cmd/api/web/styles.css` and `cmd/api/web/app.js` at `/styles.css` and `/app.js`), embedded into the binary via `go:embed` — an upload form with vanilla JS. There is no separate frontend build; editing the UI means editing the files under `cmd/api/web/`. It still submits to `/upload`, but a `202` carries no result, so `app.js` now **polls** the `status_url` the response names (`GET /api/video-jobs/:id`, 2s initial interval, ×1.5 backoff, 10s cap) until the job reports `completed` or `failed`, then reads `/api/status` for the artifact. So the frontend does consume the job-lifecycle API for reads — what it never does is *create* a job through `POST /api/video-jobs`.
3. `POST /upload` (`(*videoModule).handleVideoUpload` in `cmd/api/video.go`) validates the file extension, streams the upload into the bucket under `uploads/<uploadID>_<original-filename>` while hashing it (SHA-256) on the same pass — nothing touches local disk on the way in — reserves a Redis-backed idempotency key scoped to `UserID` + content hash (see the idempotency bullet below), creates a `VideoJob` via `CreateVideoJob` (carrying that source key **and** the content hash), calls `EnqueueVideoJob` — which commits the `pending → queued` update and a `video_job.queued.v2` outbox row in one transaction — finalizes the reservation, and returns **`202 {job_id, status, status_url}`**. It does **not** call `ProcessVideoJob`, `StartProcessing`, `CompleteJob`, or `FailJob`; no extraction happens in the request, and the body carries no frame count, result key, or download URL because none exists yet. Finalize runs *after* the enqueue, not before — the ordering is specified (`upload-idempotency`), because finalizing first would advertise a job stuck in `pending` for the full 24h window. An `EnqueueVideoJob` failure is handled like a `CreateVideoJob` failure: clear the reservation, `500`, no dispatch. A single `defer`, registered the moment the `Put` succeeds and **guarded on whether the enqueue committed**, deletes that source object only on the paths where the job never reached `queued` — after the enqueue the object is the worker's input and must survive. A duplicate is answered with the same `202` shape naming the existing job, whatever state it is in, so a client needs no duplicate branch.
4. `cmd/worker` consumes `video.jobs.queued.v2` (prefetch **1**) and runs each dispatch to a terminal state. `internal/video/infrastructure/messaging.Consumer` owns only the plumbing — dial, redeclare the topology on every dial, `Ack`/`Reject` a `Handler`'s verdict, requeue on exactly one path (a delivery pulled off the channel after the shutdown signal, which nothing has been done to). `cmd/worker/main.go`'s `handle` holds the whole decision table: undecodable body, missing source key, unknown job, lost claim, and a run that broke before any terminal commit all `Reject` (→ dead-letter exchange, never requeue — a redelivery of a job past `queued` can only lose the claim again). A `failed` result is **acked** (the job reached a terminal state) after deleting the source object and clearing the idempotency key. A success calls `CompleteJob`, retried 4× with backoff on a context detached from shutdown, then deletes the source and acks — gated on the *commit*, not on having won the claim, since a defer registered at claim time would fire on every failure path too. If `CompleteJob` still won't commit, it rejects, **keeps** the source, and logs the result `StorageKey`: an artifact no listing shows. The handler runs on `context.WithoutCancel`, so a shutdown never kills a running `ffmpeg` or aborts the write recording its outcome.
5. `ProcessVideoJob` (`internal/video/application`) is the core pipeline the worker calls: `StartProcessing` → `SourceStorage.Get` → `FrameExtractor.ExtractFrames` → `ResultStorage.Put`. **`StartProcessing` is an atomic conditional claim** — `Repository.ClaimForProcessing` runs `UPDATE video_jobs SET status='processing' WHERE id=$1 AND status='queued'`, and affecting no row returns `ErrJobClaimLost`, which `ProcessVideoJob` propagates unchanged without calling `FailJob`, downloading anything, or deleting anything. That is a *correctness* primitive (dispatch is at-least-once; `Update` is a read-then-unconditional-write, so without it two deliveries would both extract), explicitly **not** a *recovery* one: a job whose worker died mid-extraction is stored as `processing` and no redelivery can re-claim it — `add-worker-job-lock` is what will fence that. It does **not** enqueue — the handler does that (step 3); calling it here would ask the domain for a rejected `queued → queued`. **It takes a source `StorageKey`, not a local path** — a path written by the HTTP handler means nothing to `cmd/worker`, which shares no filesystem with it. It leaves a successful job in `processing` for the worker to complete, and that split now has a real reason: the terminal write is what licenses the acknowledgement, so it has to be in the worker's reach. `ProcessVideoJob` calls `FailJob` itself if the fetch, the extraction, or the storage step fails — the worker never calls `FailJob`. It downloads the source to `temp/<jobID>_source` — no file extension, so no part of that path derives from a user-supplied filename; `ffmpeg` detects the container by probing content — and removes that copy on every path via a `defer` registered *before* extraction. The `ffmpeg` exec/zip work lives in `internal/video/infrastructure/ffmpeg`'s `Extractor`: creates a per-job scratch dir under `temp/<jobID>`, runs `ffmpeg -i <video> -vf fps=1 -y temp/<jobID>/frame_%04d.png` via `exec.CommandContext`, globs the PNGs, zips them into `temp/<jobID>.zip` — beside the frame dir, not inside it, so the `defer os.RemoveAll` can't delete the zip — and returns that local path. `ProcessVideoJob` uploads it under the key `frames_<jobID>.zip` and removes the local copy whether the upload succeeded or not. It does **not** delete the source object — the worker does, once the outcome is committed.
6. `GET /download/:filename` and `GET /api/status` (both `*videoModule` methods in `cmd/api/video.go`) read from the bucket. **Download does not serve bytes**: it parses the `VideoJobID` out of the requested key, loads the job, and — only if the job belongs to the caller, is `completed`, and records that exact key — `Stat`s the object and returns `200 {"url", "expires_at"}` carrying a 5-minute presigned URL the client redeems against MinIO directly. That `Stat` is load-bearing, not vestigial: signing is offline and succeeds for a key holding no object, so without it a missing object would surface as MinIO's own XML `404` at a different origin. Because an issued URL carries no identity, that entitlement check is the *complete* authorization decision, and the URL cannot be revoked before it expires — treat it as a credential (never logged, echoed, or persisted; log the `StorageKey`). Every rejection returns a byte-identical `404`, and **every** response — success and rejection alike — carries `Cache-Control: no-store`. `expires_at` is read off the URL's own `X-Amz-Date`/`X-Amz-Expires`, never computed as `now + TTL`. Status lists the caller's `completed` jobs and takes each result's `size` and `created_at` from a `StatObject` — so `created_at` keeps meaning "when the artifact was written", as it did when it was a file's `ModTime`.
7. `POST /api/video-jobs`, `GET /api/video-jobs/:id`, and `GET /api/video-jobs` (all bearer-authenticated, owner-scoped) wrap `internal/video/application`'s `CreateVideoJob`/`GetJobStatus`/`ListUserJobs` use cases — a preview job-lifecycle API, separate from the legacy flow above. A job created *through this API* has no processing trigger and stays `pending` forever; do not present this as a working end-to-end path (see `openspec/specs/videojob-http-api/spec.md`). Because `/upload` also calls `CreateVideoJob`, though, `GET /api/video-jobs`/`GET /api/video-jobs/:id` do show real `completed`/`failed` jobs for a user who has used `/upload` — same aggregate, same repository.

One directory is created at startup (`createDirs`), and it belongs to **`cmd/worker`**, not to the API — `temp/`, holding the downloaded source copy, the per-job frame directory, and the zip built from it, all always cleaned up. `cmd/api` writes nothing to disk on any path: `POST /upload` streams straight into the bucket, and `POST /api/video-jobs` accepts a JSON filename and never touches the filesystem. There is no `uploads/` and no `outputs/`: both source videos and results are objects in the MinIO bucket, separated by key prefix. `VideoJob`s (created via either `/upload` or `/api/video-jobs`) are persisted in PostgreSQL (`VIDEO_POSTGRES_DSN`, required at startup like `IDENTITY_POSTGRES_DSN`).

Processing is **asynchronous and out-of-request**: `handleVideoUpload` returns `202` as soon as the job is `queued`, and the extraction happens later in `cmd/worker`. No `ffmpeg` process is ever held open by an HTTP request, so upload latency no longer tracks video length. Concurrency is bounded by *worker count*, not by request count: prefetch is 1, so one worker runs one extraction at a time and scaling out means running more worker processes. **The queue is the only trigger** — with no worker running, uploads keep succeeding and every job sits at `queued` forever.

The gap this leaves is *recovery*, not dispatch. `ClaimForProcessing` guarantees two deliveries cannot both extract, but a worker that dies mid-extraction leaves its job stored as `processing` with no lease, no timeout, and no edge back to `queued` — nothing redelivers it and no operator-visible mechanism reclaims it (`docs/operations.md` carries the triage query). `add-worker-job-lock` is the change that fences this; do not describe the current worker as crash-recoverable.

## Language policy: English for new code (as of 2026-07-28)

Code, error messages, and comments in **new or changed code** SHALL be written in English, going forward. This is a change from the project's original convention (see below) — it applies prospectively, not retroactively:

- Do not translate the existing Portuguese (pt-BR) strings already in `cmd/api/main.go` and `cmd/api/web/index.html` (the HTML form, existing JSON `Message`/`error` fields, existing `fmt.Printf`/`log.Printf` calls) just because you're touching a nearby line. Leave them as-is unless a change specifically asks for that.
- Any error message, log line, or other string you add or rewrite from now on should be in English, even inside an otherwise-Portuguese function.
- Comments: default to none. Add one only when it explains something genuinely non-obvious (a hidden constraint, a workaround, a subtle invariant) — not to restate what the code already says. When you do add one, write it in English.
- Exception: new **user-facing UI copy** in `cmd/api/web/index.html` (labels, buttons, status messages shown on the page itself) and user-facing strings in `cmd/api/web/app.js` stay in Portuguese, matching the rest of that page — it's written for the same pt-BR hackathon audience as the existing form, and mixing languages within one UI reads as inconsistent to that audience. This exception is scoped to visible page copy only; error messages, log lines, and comments in the surrounding Go code still follow the English rule above.
- **JSON `Message`/`error` values are Go strings, so the English rule covers them** — the `web/` exception does not reach into `cmd/api/*.go`, even though `app.js` renders `ProcessingResult.Message` straight onto that pt-BR page. Existing pt-BR values stay grandfathered; a value you add or rewrite is English. `handleVideoUpload` therefore carries both languages, and that mix is accepted rather than accidental: translating the grandfathered ones would be the retroactive change this policy explicitly rules out. Stated here because the ambiguity produced a review finding on PR #181 and would otherwise be relitigated by every change that touches one of those strings.

## Notable constraints / gotchas

- The Dockerfile is a multi-stage, non-root build (`builder` → `test` → `runtime`) — it is no longer the intentional single-stage/root anti-pattern this project originally shipped with. One image carries **both** binaries (`/app/app` and `/app/worker`); `CMD` names the API, and the worker is the same image run with `/app/worker` as its command. Keeping them in one image is deliberate: they share every internal package, so a split would let the two drift to different builds of the same domain code.
- The app's *existing* user-facing strings (error messages, HTML) are in Portuguese (pt-BR) — this was the original convention for this pt-BR hackathon audience. It's superseded for new code by the language policy above; existing pt-BR strings are grandfathered in and not being retroactively translated.
- File type validation (`isValidVideoFile`) is by extension only (`.mp4 .avi .mov .mkv .wmv .flv .webm`), not content sniffing. `POST /upload` reads the "video" multipart part via a streaming `MultipartReader`/`NextPart` (`videoFilePart` in `cmd/api/video.go`), not `c.Request.FormFile` — `FormFile` calls `ParseMultipartForm` internally, which reads the entire request body before the filename is available, so a large invalid-extension upload would otherwise pay the full transfer cost before being rejected. See `openspec/specs/upload-file-validation/spec.md`.
- The `.owner` sidecar mechanism is gone entirely — the helpers, the suffix constant, and both middlewares. No artifact class uses it: results derive ownership from the `VideoJob` row, and source objects are never served at all.
- `handleDownload` no longer touches the filesystem: the requested `:filename` must parse as `frames_<jobID>.zip`, and the job it names must belong to the caller, be `completed`, and record that exact key. `handleStatus` never accepts a caller-supplied name at all, and its `download_url` still points at `/download/<key>` on this API — minting presigned URLs into the listing was considered and rejected (it would start every TTL at listing time and put one credential per job in a single body). The **result** key deliberately contains no `/` — `cmd/api/web/app.js` uses it verbatim as that route's single path segment, and a `%2F` would break the match, so per-user or per-date prefixes on results are not possible without a frontend change. **That constraint did not lapse when the route started returning JSON**: the route survived unchanged and `app.js` still calls it, so re-keying results would still orphan every stored object. **Source** keys do carry an `uploads/` prefix, for exactly the complementary reason: no route exposes them. Anything that re-exposes source objects over HTTP has to drop that prefix in the same change.
- Both uploaded source videos and processed results live in the MinIO bucket, not on local disk — `internal/video/domain.SourceStorage` and `ResultStorage`, implemented by the two adapters in `internal/video/infrastructure/storage` over one client and one bucket. Source keys carry an `uploads/` prefix; result keys are flat. **Source objects are transient, but the API is no longer what disposes of them**: ownership follows the job's outcome. `POST /upload` deletes its own object only on the paths where the job never reached `queued`; once the enqueue commits, the object is the worker's input and the worker deletes it after committing a terminal state (and deliberately *keeps* it when `CompleteJob` will not commit). That deletion is best effort on both sides — one call, no retry — so a failure is logged with the key and does not fail the request or the job; `docs/operations.md` documents the recommended `uploads/`-prefix lifecycle rule as the operator-side backstop. See `openspec/specs/videojob-source-storage/spec.md`. `VIDEO_MINIO_ENDPOINT`/`ACCESS_KEY`/`SECRET_KEY`/`BUCKET` are **required at both binaries' startup**; `VIDEO_MINIO_USE_SSL`, `VIDEO_MINIO_PUBLIC_ENDPOINT`, and `VIDEO_MINIO_PUBLIC_USE_SSL` are optional, the latter two each defaulting to their internal counterpart (`PUBLIC_USE_SSL` to the *resolved* `USE_SSL`, not to `false`). `cmd/api`'s `setupVideo` loads, opens, pings, ensures the bucket, then discovers the bucket region and builds a second, presign-only client against the public endpoint — any failure is fatal. `cmd/worker`'s `setupWorker` does the same, presign client included — **not** because it signs anything (issuing download grants is the API's job) but so `ResultStorage` is fully constructed rather than holding a nil that would panic the day something calls the other half of its interface. Its `VIDEO_MINIO_PUBLIC_ENDPOINT` is therefore left unset in `docker-compose.yml` and falls back to the internal endpoint, which is harmless exactly because no URL is ever signed with it. That second client is deliberately never pinged and never used for a bucket or object operation: SigV4 signs `Host`, so presigned URLs must be signed against the browser-facing address from the start, which is generally one the server cannot reach. The region must be passed explicitly or `PresignedGetObject` would try to discover it over the network against exactly that unreachable host. This is **fail-closed**, deliberately unlike every Redis-backed feature below — those degrade to a slower but correct system, whereas a result that cannot be stored cannot be delivered. `GET /download/:filename`'s entitlement lookup deliberately uses the *undecorated* PostgreSQL repository rather than the cached one, so a stale `processing` cache entry can't 404 a result `GET /api/status` is already listing. See `openspec/specs/videojob-result-storage/spec.md`.
- `POST /upload` deduplicates by content: identical bytes uploaded twice by the same authenticated user reuse the first request's `VideoJob` instead of running `ffmpeg` again (`internal/video/domain.IdempotencyStore`, backed by Redis via `internal/video/infrastructure/idempotency.RedisStore`). This requires `REDIS_ADDR` at **both** `cmd/api` and `cmd/worker` startup. A `Reserve` error (Redis unreachable/erroring, as opposed to a normal reservation conflict) fails open: the handler logs it and proceeds without a reservation rather than blocking the upload, matching rate limiting's and the status cache's fail-open posture. **Clearing the key is the worker's job, not the API's** — the API cannot know a job's outcome any more, and the key must survive until one exists. The worker clears it via `IdempotencyStore.ClearByJob(key, jobID)`, rebuilding the key from the `content_hash` column the `VideoJob` now carries (option (c): no reservation token is persisted, and the delete is conditional on the stored value naming *this* job, so a later upload's reservation is never cleared by an older job finishing). See `docs/architecture.md`'s Request pipeline section and `openspec/specs/upload-idempotency/spec.md` for the full protocol.
- Every authenticated route is also rate limited per user: a Redis-backed fixed-window counter (`internal/platform/ratelimit`, mounted as `cmd/api/ratelimit.go`'s `rateLimitMiddleware` on the `videoRoutes` group, right after `requireBearerAuth()`) rejects excess requests with `429` + `Retry-After` before any handler runs. This limits **requests to this API**, which is not the same as limiting bytes served: `GET /download/:filename` issues a presigned URL and is limited, but the transfer that URL authorizes goes straight to MinIO, which this middleware does not sit in front of. Do not read "every authenticated route is rate limited" as "result egress is rate limited" — bounding that is an object-storage concern. Configurable via optional `RATE_LIMIT_MAX_REQUESTS`/`RATE_LIMIT_WINDOW_SECONDS` (defaults 60/60s) — unlike `REDIS_ADDR`, these are not required at startup. A limiter failure (including its own bounded internal timeout) fails open rather than blocking the request. See `openspec/specs/rate-limiting/spec.md` for the full protocol.
- A transactional outbox relay carries `video_job.queued` events to RabbitMQ. It is the only thing `cmd/api` opens an AMQP connection for; `cmd/worker`'s consumer is the other side of the same topology and opens its own. `internal/platform/rabbitmq` holds the plumbing (`Config`/`LoadConfigFromEnv` reading `RABBITMQ_URL`, `Open`, `Ping`, `Close`, a generic `Topology` descriptor, and `DeclareTopology(conn, topo)`); `internal/video/infrastructure/messaging` holds the names (`JobDispatchTopology()`) plus `Publisher` and `Relay`; `internal/video/infrastructure/postgres.OutboxRepository` owns the claim, hiding the `*sql.Tx` behind an `OutboxBatch` so the messaging package never names a database driver. **`RABBITMQ_URL` is required at `cmd/api` startup** (loaded as `setupVideo`'s first statement, before any I/O), but a *reachable* broker is not: `main` starts the relay as a goroutine that dials, retries with backoff, and redeclares the topology after every dial. The consumer declares the same topology on every dial too — both sides declare, so neither process's startup order depends on the other's, and a fresh or recreated broker cannot leave a publish landing in a missing exchange or a consume opening on a missing queue. Each cycle claims a bounded batch with `FOR UPDATE SKIP LOCKED`, publishes **mandatory** on a confirm-mode channel, and stamps `published_at` only for messages that were acknowledged **and** not returned — a confirm means the *exchange* accepted the publish, not that any queue got it. A nack is not an error (a full queue under `reject-publish` is designed back-pressure; the row waits for the next poll), and the claim/publish/stamp all commit together — committing the claim first would lose a dispatch permanently on a crash. The platform/context split is enforced by tests: the platform package may import nothing outside `internal/platform/`, and may contain no context name (`video.jobs`, `video_job.`), because `ddd-architecture` confines that namespace to connection/lifecycle plumbing. Two decisions look like mistakes without their reason — `Open` connects (AMQP has no lazy client, unlike `redis.Open`/`storage.Open`), and the job queue carries **no** message TTL (an expired message is dead-lettered without touching the `video_jobs` row, and the state machine has no edge out of `queued` except to `processing`, so the job would report `queued` forever). The routing key equals the outbox `event_type` string, coupled across two packages with no compiler enforcement — `TestRoutingKeyMatchesTheOutboxEventType` is what pins it. So is the wire payload: `postgres.videoJobQueuedPayload` and `messaging.JobQueuedMessage` are separate structs in packages that do not import one another, pinned by `TestJobQueuedMessageDecodesTheOutboxPayload`.

  The dispatch generation is **`.v2`** — `video.jobs.v2`, `video.jobs.queued.v2`, and the routing key/`event_type` `video_job.queued.v2` (the dead-letter names carry no suffix). Versioning the exchange alone would isolate nothing, because every replica's relay claims from one shared `video_job_outbox` filtered on `event_type`: the generation has to be on the event type too, or a new-generation replica would publish an old-generation replica's rows. What it protects is the **rolling-deploy window**, not stale messages: a `.v1` API replica still deletes its own source object on every exit path, so a `.v1` message consumed by the new worker names an object that is already gone. Retiring the superseded queue and exchange after the deploy is a documented post-deploy step (`docs/operations.md`). See `openspec/specs/videojob-outbox-relay/spec.md`, `openspec/specs/rabbitmq-infrastructure/spec.md`, and `openspec/specs/videojob-messaging/spec.md`.
- `GetJobStatus`/`ListUserJobs`/the state-transition use cases all read and write `VideoJob`s through `internal/video/infrastructure/cache.CachedVideoJobRepository`, a decorator wired into both composition roots ahead of the PostgreSQL adapter — `FindByID` is cache-aside (Redis `SET NX` on miss-repopulation, never a plain `SET`, so a slow reader can't clobber a fresher concurrent write), `Update` is write-through (unconditional `SET` after the PostgreSQL write succeeds). No new required/optional env var — the cache TTL is a fixed 5-minute constant. See `openspec/specs/videojob-status-cache/spec.md` for the full protocol.
